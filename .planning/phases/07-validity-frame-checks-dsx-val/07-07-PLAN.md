<objective>
Create the fixture the roadmap names by filename, write its post-mortem, and resolve the test
conflict that fixture creates — deliberately, in one commit, with the decision recorded.

Purpose: the roadmap's first success criterion requires
`examples/known-bad/weak-identification-mmm-ANALYSIS-SPEC.yaml` to exit non-zero at the plan gate
naming `DSX-VAL-040`. The corpus test module discovers fixtures by globbing that directory and
asserts every match clears the plan and execute gate points, with no escape hatch at that level.
Dropping the new fixture into that directory breaks the test as written. Nothing in the phase
context names this conflict; research found it by reading both documents. It has to be settled on
purpose.

Output: a fourth corpus fixture with the opposite polarity from its three siblings, its sourced
post-mortem, a narrowed corpus assertion that keeps glob discovery and gains a positive
counterpart, and the phase's final proof that every code carries its citation and its test.
</objective>

<recorded_decision>
DECISION NEEDED: How should the corpus's "every fixture clears the plan gate" assertion
accommodate a fixture that is required to block at the plan gate?

Option A: A named exception set inside the corpus test module
  In practice: add a dictionary in `tests/test_known_bad_corpus.py` mapping a fixture's file name
    to the finding code that is expected to block it at the plan gate. The blanket assertion
    consults that dictionary: a listed fixture must exit non-zero at plan with that exact code
    among its critical findings, and must still exit zero at execute; every unlisted fixture is
    asserted exactly as today. Glob discovery is untouched.
  This locks in: the corpus keeps one module-level place where every expected gate outcome is
    written down, and every future fixture whose target code has shipped gets the same treatment.
  Cost later: each future fixture of this kind needs a dictionary entry, and a wrong entry is a
    silent weakening of one fixture's guarantee rather than of all of them.
  Reversibility: cheap to undo

Option B: A sentinel file beside the fixture
  In practice: place a small marker file next to the fixture and have the test skip the blanket
    assertion for any fixture with a sibling marker.
  This locks in: the expectation lives beside the fixture rather than in the test module, so the
    corpus directory becomes self-describing.
  Cost later: the expectation is no longer reviewable in one place, a marker can be added without
    the code it claims, and there is nothing asserting the fixture actually blocks — only that it
    is permitted not to clear.
  Reversibility: cheap to undo

Option C: Move the fixture out of the corpus directory
  In practice: put the file somewhere the glob does not reach and satisfy the roadmap by some
    other path.
  This locks in: nothing, because it does not satisfy the roadmap, which names the file by its
    full path inside the corpus directory.
  Cost later: the roadmap's own success criterion becomes unverifiable as written.
  Reversibility: expensive to undo

Dropped: a fourth option that deletes the blanket assertion entirely. It removes a guarantee that
holds for three fixtures in order to accommodate the fourth, which trades a real invariant for
convenience.

My recommendation: Option A, because it is the only one that replaces a lost assertion with a
stronger one — the listed fixture is not merely excused from clearing the gate, it is required to
block it, on a named code.
If you do not answer: proceed with Option A.

This plan proceeds with Option A. One detail makes it cleaner than it first looks: the validity
frame check is registered in the plan, verify and ship profiles but not in execute, so the new
fixture blocks at plan and clears execute with no special handling at all. Half of the corpus's
positive guarantee therefore survives untouched for this fixture too.
</recorded_decision>
