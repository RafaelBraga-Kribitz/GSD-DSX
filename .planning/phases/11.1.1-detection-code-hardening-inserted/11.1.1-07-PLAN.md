    The group covers exactly four things, each in its own sentence or two:

    First, the deliberate asymmetry between the two reads. A Python file whose
    bytes are not valid UTF-8 is still scanned, with the bytes that would not
    decode replaced, because most of such a file is still readable code. A
    notebook file whose bytes are not valid UTF-8 is REJECTED OUTRIGHT instead
    -- the gate exits 2 with an error message and does not run any check at
    all, rather than exiting 0 with a NOT-scanned pass line -- because a
    notebook must decode as a whole before any of it can be read, and a
    partial decode would let the tool claim it parsed text it could not
    actually read. This is not a NOT-scanned outcome and must not be described
    as one: it is a blocking "could not run" outcome, the same family a
    missing spec file produces, and it predates this plan untouched. Say which
    behaviour belongs to which file type, and say plainly that the two file
    types don't just differ in degree here -- one keeps running and reports a
    pass, the other stops the run and reports an error. A reader who assumes
    they match, or who assumes the `.ipynb` case is a quiet pass like the other
    limits in this section, will be wrong in the more dangerous direction (an
    error is loud, not quiet -- but a reader skimming for "does this pass
    silently" needs to know this ISN'T one of those cases).

    Second, a notebook nested more deeply than the running interpreter allows is
    reported as NOT scanned rather than scanned. This is a guard against a crash,
    and it means a legitimately very deeply nested document reads as unscannable.

    Third, no size limit is applied before the file is read, so a large enough
    declared entrypoint can exhaust memory; where that surfaces as a memory
    error during the read it is reported as NOT scanned, and where it does not,
    it is not caught.

    outcome. It exits 0, it produces no finding, and the line that says the file
    was not scanned prints only when `--verbose` is passed. A notebook that is
    corrupted -- by accident or on purpose -- therefore makes the leak scan go
    quiet rather than loud, and a reader running without `--verbose` sees a
    passing code check that looks like a clean scan. State this as a limit the
    tool currently has. Do not describe it as fixed, and do not describe a fix.
