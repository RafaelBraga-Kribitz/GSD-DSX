## Prose Mask Coverage (the larger of the two measured gaps)

`_prose_line_indices` (plan 01) is correctly implemented -- Rule A masks whole bare-string statements, Rule B masks the strictly interior lines of a multi-line string, sparing the opening and closing lines. But it has exactly **one consumer** in the shipped code: `_first_line_matching`'s `masked` parameter, i.e. the split-marker text scan. Plan 01's own source comment says so explicitly ("In this wave the mask has exactly one consumer"). AST-DESIGN section 3.7 describes a broader vision -- masking applied to `DSX-CODE-002`, `DSX-CODE-003`, `DSX-CODE-020`'s predicate loop, and `DSX-CODE-030`/`031`'s reference window -- and section 3.8 specifically calls for a comment guard on `DSX-CODE-002`/`003`. Neither the broader masking nor the comment guard was implemented by plan 01 or plan 02.

Measured this session against the shipped code:
- A docstring or comment mentioning a fit call closes for `DSX-CODE-001` (structural -- comments and prose never reach `ast.parse` as `Call` nodes at all).
- A comment mentioning `StandardScaler().fit_transform(X)` **still fires `DSX-CODE-002` HIGH**.
- A comment mentioning `SMOTE` **still fires `DSX-CODE-003` HIGH**.
- A cleaning idiom on the interior line of a triple-quoted string **still fires `DSX-CODE-020` CRITICAL** (no masking applies to that code's text loop at all -- interior, opening or closing line all fire identically).

This is not a regression this plan introduced and not something this plan's own scope permits it to fix (its prohibitions explicitly exclude mechanism work, with one named, bounded exception this task did not need). It is pinned as measured reality (`test_comment_mentioning_smote_still_fires_code_003_measured_not_assumed`, `test_comment_mentioning_scaler_fit_transform_still_fires_code_002_measured_not_assumed`, both asserting `assertIn`), named in README.md's "What the entrypoint scan does not catch" section, and raised here for the end-of-phase human check as a candidate for a follow-up phase.

## Decision-Record Coverage Gap (the smaller of the two measured gaps)

Measured this session: `check()` returns before any `record_decision` call on this path -- the same early-return shape as the blank-entrypoint case (where no entrypoint was declared at all, and the retention of silence there is deliberate and named). Pinned by `test_unscannable_entrypoint_also_produces_no_decision_record`, flagged here for the end-of-phase human check.
