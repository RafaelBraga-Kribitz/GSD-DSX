### Gaps Summary

Three of six ROADMAP success criteria are falsified by live, independently-reproduced evidence,
not by inference from the review document alone:

1. **SC2 (DSX-CODE-021 "whatever the call's shape")** — the fallback text scanner misses a real,
   unambiguous post-split leak whenever the recognised keyword argument is not the first one in
   the call. This is a false negative on a BLOCKING CRITICAL check: the gate can exit 0 over a
   file that leaks, contingent only on whether some unrelated line elsewhere in the file happens
   to parse. The shipped code's own comment overclaims agreement between the two paths.

2. **SC4 (identical verdict regardless of docstrings/comments)** — DSX-CODE-020 and
   DSX-CODE-030/031 (CRITICAL/HIGH, blocking) never received the prose-mask treatment
   DSX-CODE-001/021 got. A docstring alone still triggers these findings on the primary,
   parsed path — the exact false-positive class this phase's re-scope was chartered to close,
   left open for three of the module's detection codes. Plan 01 explicitly assigned this to
   plan 02 as follow-on work ("Extending it to DSX-CODE-002/003/020/030's loops is plan 02's
   work"); plan 02 shipped no such task, and plan 03 discovered the gap by measurement but
   declared it outside its own scope rather than closing it or fully disclosing it (README
   names the narrower DSX-CODE-002/003 comment-mention case, not the DSX-CODE-020/030
   docstring/CRITICAL case).

3. **SC5 (visible degradation, never silent)** — a structurally-malformed-but-valid-JSON
   `.ipynb` file crashes `check()` with an uncaught `AttributeError` rather than reaching any
   of the four documented degrade-signalling channels. This is a regression against the
   module's own stated contract ("Missing / non-text / unscannable entrypoints are named as NOT
   scanned rather than silently skipped") and produces an exit code indistinguishable from a
   legitimate gate block.

All three gaps were reproduced directly against the current codebase during this verification
(not merely cited from `11.1.1-REVIEW.md`), and none is disclosed in README.md's "What the
entrypoint scan does not catch" section, which the phase's own prohibitions require for anything
shipped unfixed. SC1, SC3 and SC6 hold and were independently spot-checked. Two further items
(WR-01, WR-02, and the D7/D8 honesty-prose judgment) are non-blocking and were routed to
warnings / human verification respectively, consistent with the review's own severity
classification and the phase's own self-flagged deferrals.

**This looks like real, unresolved detection-coverage regression, not an intentional
deviation.** No override is suggested — the phase's own plan 01 (Decision 4) and plan 03's
SUMMARY both independently identify the SC4 gap as follow-on work that was never picked up, and
CR-01/CR-03 were not identified or discussed as accepted trade-offs anywhere in the phase's own
artifacts. A human could still choose to accept these as documented follow-on debt rather than
requiring a closure plan — but that acceptance does not currently exist as a recorded override
per `.planning/phases/11.1.1-detection-code-hardening-inserted/11.1.1-VALIDATION.md`'s or any
plan's prohibitions, so this report leaves them as gaps rather than assuming acceptance.
