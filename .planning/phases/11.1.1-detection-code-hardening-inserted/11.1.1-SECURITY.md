# Phase 11.1.1 — Security

> Per-phase security contract: threat register, accepted risks, and audit trail.

Built from the `<threat_model>` block in each of the five executed plans
(11.1.1-01 through 11.1.1-05-PLAN.md, all authored at plan time — `register_authored_at_plan_time: true`),
then independently verified by `gsd-security-auditor` against the live tree and test suite

## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|----------------|
| analyst-authored entrypoint file → parser and line scanner | Untrusted text of unbounded length, read from a path the analyst names in the specification, fed to `ast.parse` and to the retained regex patterns. Which path runs is attacker-controlled — one stray character forces the fallback. | Source code / notebook JSON |
| README.md → an operator deciding whether to trust a clean scan | Prose crosses here; a sentence that reads as reassurance becomes an operational decision to ship a model. | Documentation claims about coverage |
| degraded or skipped scan → operator's belief that a scan ran | A fallback verdict that reads like a parsed verdict, or an unscannable entrypoint that reads like a clean one, repudiates the gate's own evidence. | Pass/fail signal, exit code, decision record |
| `_read_source`'s return value → `check()`'s `source is None` branch | The only channel distinguishing "scanned clean" from "not scanned at all." | Parsed source text or `None` |

**Correction surfaced by this audit, relevant to executing plan 06 as currently written:** plan 06's threat entry T-11.1.1-19 justifies its `.ipynb` `UnicodeDecodeError` fix by claiming the exception "ends the process with Python's default exit code 1." Live reproduction shows this is false: `dsx/cli.py:799` catches bare `ValueError` (which `UnicodeDecodeError` subclasses) and returns `EXIT_ERROR` (2) with a clean `dsx: invalid input — ...` message — already matching the documented "could not run" contract, via a different path (the CLI's top-level handler) than the `.py` branch's local `errors="replace"` recovery. Plan 06 as written would catch `UnicodeDecodeError` locally inside `_read_source` and route it to the "NOT scanned" `report.ok(...)` branch instead — converting a correct, loud exit 2 into a silent exit-0 pass whose line prints only under `--verbose`. That is exactly the failure mode the codebase's own comment at code.py:1080-1089 rejects for the analogous `.py` case: *"swallowing it to None instead would convert that loud failure into a silent exit-0 pass ... worse than either."* This does not change that the two `TypeError` root causes (non-iterable `cells`, non-string `source` element) are real, unambiguous bugs that plan 06 should still fix as written. **Resolved 2026-08-22, by the user, before either plan executed:** Option A — leave the non-UTF-8 case alone; drop the sub-fix from plan 06's scope entirely rather than extending the `.py` branch's `errors="replace"` pattern to `.ipynb`. Both `11.1.1-06-PLAN.md` and `11.1.1-07-PLAN.md` were edited to match: the exception tuple plan 06 adds is now four members (`OSError`, `json.JSONDecodeError`, `RecursionError`, `MemoryError`), not five; threat T-11.1.1-19 no longer claims the non-UTF-8 shape reaches exit 1; the malformed-notebook enumeration plan 07 was going to add to README no longer claims a non-UTF-8 `.ipynb` is "reported as NOT scanned" (it is not — it is rejected outright at exit 2, a different outcome, now disclosed as such in the residual-limits section instead); and every shape count across both plans (five → four) was corrected to match. Neither plan has executed yet, so no shipped code or documentation was ever wrong — this was caught and fixed at the planning stage. Both corrected plans committed at `1673bd3`.
