## Summary

Plan 04's widening of `FIT_CALL_RE` and the `_first_argument`/`_stat_test_lines_referencing`
mask wiring were traced by hand against representative inputs (reordered keywords,
`a==b` guards, prose masking in both consumers of `masked`) and hold up: the `{0,8}`/`{0,80}`
bound is genuinely linear (backtracking is bounded by the product of the two caps), and the
skip fragment's greedy-then-backtrack interaction with the allowlisted-keyword branch
resolves to the correct VALUE token in every traced case, never a keyword NAME — confirmed
against `test_reordered_keyword_leak_verdicts_agree_across_both_paths` and
`test_several_unrecognised_keywords_before_an_allowlisted_one_resolve_the_allowlisted_value`.
`_first_argument`'s new `ast.Compare` exclusion is applied uniformly whether the resolved
node came from a positional argument or an allowlisted keyword's value.

The scan for this round concentrated on plan 04's other headline claim — that `_read_source`'s
`.ipynb` branch cannot crash on a malformed-but-syntactically-valid document, only return
`None` — because that is exactly the class of defect (an uncaught exception where the module's
own contract promises a graceful "could not be read" pass) the earlier GAP-3 fix targeted.
Three inputs, none matching the two shapes plan 04's own tests cover (`cells` as a dict,
`cells` containing a bare-string entry), still reach an unhandled exception out of `check()`
today, verified by direct execution against the shipped module. This is the same failure mode
GAP-3 fixed for `AttributeError` on `nb.get("cells")`, just not closed for every JSON shape
that reaches this branch. README.md's account of the fix (lines 258-269) states the general
case ("a document shaped like that... is now reported as NOT scanned") more broadly than the
shipped code supports.

## Critical Issues

### CR-01: `.ipynb` read crashes with `UnicodeDecodeError` on non-UTF-8 bytes

**File:** `dsx/checks/code.py:1101` (inside the `try` at line 1091, guarded by the `except` at
line 1102)
**Issue:** The `.ipynb` branch reads the file with
`path.read_text(encoding="utf-8-sig")` and feeds the result straight into `json.loads`, all
inside a `try` that only catches `(OSError, json.JSONDecodeError)`. `path.read_text` raises
`UnicodeDecodeError` (a `ValueError` subclass, not a `json.JSONDecodeError`) when the file's
bytes are not valid UTF-8. That exception is not caught anywhere between here and `main()` —
`dsx/cli.py::main` only catches `(CheckError, SpecParseError, ValueError...)` — wait: `main`
*does* catch bare `ValueError`, but the module's own contract (stated at
`dsx/checks/code.py:1108-1112`, "routes into check()'s existing `source is None`... branch
instead of letting `nb.get("cells")` raise ... uncaught out of check()") is that a malformed
notebook produces a controlled `report.ok("... could not be read ...")`, not a bare
process-level error path. Confirmed live: a `.ipynb` file containing invalid UTF-8 bytes
(`b'{"cells": [{"cell_type": "code", "source": "\xff\xfe bad bytes"}]}'`) raises
`UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 44: invalid start byte`
straight out of `code.check(spec, None)` — reproduced directly against the shipped module.
This is a materially more likely real-world input than the crafted JSON shapes GAP-3's tests
cover (a corrupted, truncated, or non-UTF-8-saved notebook file is an ordinary occurrence, not
an adversarial construction). The `.py` branch already handles the analogous case at
`dsx/checks/code.py:1078-1089` by decoding with `errors="replace"` instead of raising; the
`.ipynb` branch has no equivalent guard.
**Fix:**
```python
try:
    nb = json.loads(path.read_text(encoding="utf-8-sig"))
except (OSError, json.JSONDecodeError, UnicodeDecodeError):
    return None
```

### CR-02: `.ipynb` read crashes with `TypeError` when `cells` is a non-iterable JSON scalar

**File:** `dsx/checks/code.py:1116`
**Issue:** `for cell in nb.get("cells") or []:` assumes `nb.get("cells")` is either falsy or
iterable. The GAP-3 fix added `isinstance(nb, dict)` (line 1113) and
`isinstance(cell, dict)` (line 1128) guards, and its own tests cover `cells` as a dict
(iterates over string keys, each caught by the `isinstance(cell, dict)` guard) and `cells`
as a list containing a bare string. Neither guard covers `cells` being a *truthy,
non-iterable* JSON scalar — an integer, float, or `true` — which is exactly as valid a JSON
document as the covered shapes. `for cell in 5:` raises `TypeError: 'int' object is not
iterable`, uncaught by anything between here and `main()`. Confirmed live:
`{"cells": 5}` written to a `.ipynb` file and passed through `code.check(spec, None)` raises
`TypeError: 'int' object is not iterable` directly out of `check()`.
**Fix:**
```python
cells = nb.get("cells")
if cells is not None and not isinstance(cells, list):
    return None
for cell in cells or []:
    ...
```

### CR-03: `.ipynb` read crashes with `TypeError` when a cell's `source` list contains a non-string element

**File:** `dsx/checks/code.py:1137-1138`
**Issue:** `src = cell.get("source") or ""` followed by
`chunk = "".join(src) if isinstance(src, list) else str(src)` assumes every element of a
list-typed `source` is a string (the ordinary nbformat shape). JSON permits a list containing
any mix of types, and `"".join([...])` raises `TypeError: sequence item N: expected str
instance, int found` when any element is not a string — again uncaught anywhere between here
and `main()`. Confirmed live: a cell shaped
`{"cell_type": "code", "source": ["import pandas", 5]}` raises exactly this `TypeError`
straight out of `code.check(spec, None)`. This crash sits directly inside the loop the GAP-3
`isinstance(cell, dict)` guard was added to protect and applies to both code and markdown
cells (the markdown branch's `re.sub(r"[^\r\n]", "", chunk)` at line 1158 runs on the same
already-crashed `chunk`, so it does not add a second failure mode — the crash happens first,
at the join).
**Fix:**
```python
src = cell.get("source") or ""
if isinstance(src, list):
    if not all(isinstance(part, str) for part in src):
        return None
    chunk = "".join(src)
else:
    chunk = str(src)
```

## Warnings

### WR-01: README overclaims the notebook-read hardening's coverage

**File:** `README.md:258-269`
**Issue:** This section states, without qualification: "A Jupyter notebook file can be valid
JSON and still not be a notebook — for example, the two characters `[]`, or a document whose
list of cells contains something that is not itself an object... It is now reported as NOT
scanned, the same outcome the tool already gives a file it cannot open at all, so the exit
code and the report both say what actually happened." This is true for the two shapes plan
04's tests exercise (a non-dict top-level document; a `cells` entry that is not itself an
object) but false for at least three other JSON-valid, equally plausible notebook shapes
(CR-01: non-UTF-8 bytes; CR-02: `cells` as a non-iterable scalar; CR-03: a `source` list
containing a non-string element) — all three still crash the whole run with a raw Python
traceback and a non-1/non-2 exit code, the exact failure mode this paragraph says was fixed. A
reader who takes this paragraph at face value will not expect `dsx` to crash on a corrupted or
hand-edited notebook file, and will be wrong.
**Fix:** Either close CR-01 through CR-03 so the paragraph's claim is accurate, or narrow the
wording to name the specific shapes actually covered (non-dict top-level document, non-object
cell entry) rather than the general "a document shaped like that" framing, until the remaining
gaps are closed.
