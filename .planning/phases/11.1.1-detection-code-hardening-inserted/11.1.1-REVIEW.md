# Phase 11.1.1: Code Review Report

**Reviewed:** 2026-08-21T00:00:00Z
**Depth:** deep

## Summary

Reviewed `dsx/checks/code.py`, its accompanying `tests/test_dsx.py` additions, and the new
`README.md` sections at deep depth, with call-chain tracing between the AST (primary) path and
the text (fallback) path for DSX-CODE-001/DSX-CODE-021, and empirical reproduction of every
finding below against the actual `check()` entry point (not just static reading).

The engineering in this phase is unusually well self-documented — most of its own known gaps are
named in code comments and in dedicated "stays uncaught by design" tests. That diligence is real,
but it also means several of the defects below were *already known to the executor* and were
either left undocumented in the user-facing `README.md`, or documented internally (in a plan
`SUMMARY.md` this review did not have in scope) without a corresponding fix or public disclosure.
Per the review brief, "known to an internal planning doc" does not reduce severity for a BLOCKING
CRITICAL gate check that ships silently wrong.

Three reproducible correctness defects were found, all directly on the DSX-CODE-001/020/021/030
detection path this phase concerns itself with:

1. A false **negative** on the fallback path for DSX-CODE-021 (a real post-split leak on a
   reordered-keyword `.fit(...)` call is silently missed only when the file happens to require
   the fallback scanner — i.e. gate exit 0 on a leaking file).
2. A false **positive** on the *primary* (AST) path for DSX-CODE-020/030/031 (a docstring merely
   describing a full-frame-cleaning or target-referencing idiom still fires CRITICAL/HIGH, even
   though this phase's whole headline claim is that docstrings no longer block).
3. An unhandled crash (`AttributeError`, uncaught anywhere up to `main()`) on a syntactically-valid
   but structurally-malformed `.ipynb` file, which turns a "declared but unscannable → NOT scanned,
   exit gracefully" contract into a raw Python traceback and exit code 1 — coincidentally the same
   numeric exit code the project uses for "gate blocks", which is exactly the kind of ambiguity a
   deterministic gate is supposed to prevent.

Two further findings are quality/documentation issues that materially affect how much a reader can
trust the audit trail and the new README section.

## Critical Issues

### CR-01: Fallback `FIT_CALL_RE`/`_fit_call_arguments` silently misses a real post-split leak when the recognised keyword is not the first keyword — disagrees with the AST path

**File:** `dsx/checks/code.py:184-188` (`FIT_CALL_RE`), `dsx/checks/code.py:1167-1199` (`_fit_call_arguments`), consumed at `dsx/checks/code.py:637-642`

**Issue:** `FIT_CALL_RE` only inspects the token immediately following the opening parenthesis of
a `.fit(`/`.fit_transform(`/`.partial_fit(` call, optionally preceded by *one* keyword name drawn
from `FIT_FIRST_PARAM_NAMES`. It has no way to find a recognised keyword (`X=`, `data=`, …) that
appears *after* another keyword in the same call. The AST path's `_first_argument` does not have
this limitation — it scans **all** keywords in source order and takes the first one whose `arg` is
in `FIT_FIRST_PARAM_NAMES`, regardless of position.

Reproduced end to end through `check()` (not just the regex in isolation). Same source line,
`model.fit(y=y_train, X=full_frame)`, placed after a split marker:

- File that parses cleanly (AST/primary path) → `DSX-CODE-021` CRITICAL fires correctly:
  `Line 3 fits on 'full_frame', which is not a recognised training frame`.
- The exact same line, in a file that fails to parse for an *unrelated* reason elsewhere (forcing
  the fallback path) → **zero findings**. `DSX-CODE-021` does not fire at all.

```
$ python -c "... model.fit(y=y_train, X=full_frame) after a syntax error elsewhere ..."
PASS: entrypoint NOT parsed — text-only fallback scan (syntax error at line 2)
PASS: entrypoint split marker at line 5
# no DSX-CODE-021 finding
```

This is precisely the class of bug the phase's own docstrings (`dsx/checks/code.py:167-183`)
claim was eliminated ("Widened so the FALLBACK agrees with the AST path instead of contradicting
it"), and precisely the scenario `tests/test_dsx.py`'s
`test_out_of_allowlist_keyword_draws_nothing_on_both_paths` was written to guard against — but
that test only exercises a *single* non-allowlisted keyword (`model.fit(y=y_test)`), never a
recognised keyword preceded by an unrecognised one. No test in the diff covers keyword order.
Whether a real, unambiguous leak is caught now depends on whether some *other*, unrelated line in
the same file happens to be syntactically valid Python — a property with no relationship to
whether this particular call leaks.

Per the phase brief: this is a false negative on a CRITICAL, blocking finding code — the gate
exits 0 over a file that leaks.

**Fix:** Either (a) make `_fit_call_arguments` AST-shaped instead of regex-shaped for the keyword
case (scan every `name=value` pair textually and pick the first name in `FIT_FIRST_PARAM_NAMES`,
not just the first positional slot), or (b) explicitly document this as a known fallback miss in
`README.md`'s "What the fallback text scan additionally misses" paragraph, the same way the
backslash-continuation and trailing-comment misses are already disclosed there, and add the
missing test:

```python
def test_reordered_keyword_leak_still_fires_on_the_fallback(self):
    # model.fit(y=y_train, X=full_frame) after the split: AST path fires
    # DSX-CODE-021; fallback (forced by an unrelated syntax error) must too.
    ...
```

### CR-02: DSX-CODE-020/030/031 have no prose masking at all — a docstring alone still fires CRITICAL/HIGH on the *primary* (parsed) path, contradicting this phase's headline claim, and undocumented in README

**File:** `dsx/checks/code.py:592-610` (DSX-CODE-020), `dsx/checks/code.py:710-764` (DSX-CODE-030/031),
`dsx/checks/code.py:1150-1164` (`_first_full_frame_cleaning_line`, no `masked` parameter),
`dsx/checks/code.py:1210-1257` (`_stat_test_lines_referencing`, no `masked` parameter);
`README.md:154-234`

**Issue:** `_prose_line_indices` (`dsx/checks/code.py:336-382`) exists specifically to stop a
docstring/prose line from deciding a verdict, but per its own docstring it "has exactly one
consumer in this wave: the split-marker text scan" (`_first_line_matching` via `masked=`, used
only for `text_split` at `dsx/checks/code.py:551`). `_first_full_frame_cleaning_line` (feeds
DSX-CODE-020) and `_stat_test_lines_referencing` (feeds DSX-CODE-030/031) are still pure
per-physical-line text scans with only a leading-`#` comment guard — they run **unconditionally**,
on the primary AST path exactly as much as the fallback, and never receive `prose_mask`.

Reproduced against unmodified `dsx/checks/code.py` (AST path taken — `"entrypoint parsed with ast
(call-level scan)"`):

```python
'''
We deliberately avoid df.fillna(df.mean()) before splitting.
'''
from sklearn.model_selection import train_test_split
train_test_split(df)
```
→ `DSX-CODE-020 CRITICAL "Line 2: We deliberately avoid df.fillna(df.mean()) before splitting."`
even though the file correctly splits before doing anything and never calls `.fillna(` for real.

The identical shape reproduces for DSX-CODE-030 with a docstring mentioning `ttest_ind(df['target'], ...)`.

This is the exact false-positive class ("a docstring merely mentions a fit call... it no longer
does [block]") that `README.md:154-234` announces as fixed project-wide for "the entrypoint leak
scan (`DSX-CODE-001`, `DSX-CODE-021` and their siblings)" — but it is only actually fixed for
DSX-CODE-001/021. `README.md:497-641` ("What the entrypoint scan does not catch") is otherwise
careful to name known persisting limits precisely — it explicitly calls out DSX-CODE-002 and
DSX-CODE-003's comment-only guard gap (`README.md:567` onward: "Two related limits stay open on
the primary (non-fallback) text checks that never moved to the parser") — but says nothing about
DSX-CODE-020/030/031 at all. `tests/test_dsx.py`'s own comment inside
`test_multiline_string_interior_line_stays_uncaught_by_design` (search "prose mask coverage")
already states this exact fact internally ("measured against the shipped code, DSX-CODE-020's own
text loop applies NO masking at all... which is the larger, separately-documented finding of this
plan") — so the gap was known to the executor before this review, but the public-facing
`README.md` limitations section, which is precise about the sibling codes' gaps, omits it.

Given DSX-CODE-020 and DSX-CODE-030 are both CRITICAL severity blocking codes, this is a real,
demonstrable false-positive that can block a correct pipeline on prose alone — squarely the
category the review brief asked to weight heavily.

**Fix:** Thread `prose_mask` into `_first_full_frame_cleaning_line` and
`_stat_test_lines_referencing` the same way it is already threaded into `_first_line_matching`
(all three already receive `lines` computed the same way; only the mask parameter is missing), and
add the `README.md` disclosure for whichever gap remains after the fix (or before, if the fix is
deferred to a later phase — but then it belongs in the same "does not catch" enumeration that
already itemizes DSX-CODE-002/003).

### CR-03: Malformed-but-syntactically-valid `.ipynb` JSON crashes the whole gate with an unhandled `AttributeError` instead of the documented "NOT scanned" / exit-2 contract

**File:** `dsx/checks/code.py:1047-1093` (`_read_source`, `.ipynb` branch), `dsx/cli.py:791-804` (`main`)

**Issue:** The `try/except (OSError, json.JSONDecodeError)` around `json.loads(...)` only guards
the parse itself. `nb.get("cells")` (`dsx/checks/code.py:1062`) and every `cell.get(...)` call
inside the loop (`dsx/checks/code.py:1063` onward) run **outside** that guard and assume `nb` is a
`dict` and every element of `nb["cells"]` is a `dict`. Neither is guaranteed by "valid JSON."

Reproduced twice against unmodified `check()`:

```python
# entry.ipynb containing the two characters "[]" — valid JSON, not an object
codemod.check(spec, phase_dir=d)
# -> AttributeError: 'list' object has no attribute 'get'
```

```python
# entry.ipynb containing {"cells": ["not-a-dict-cell"]}
codemod.check(spec, phase_dir=d)
# -> AttributeError: 'str' object has no attribute 'get'
```

Neither exception is caught anywhere between `code.check()` and `dsx.cli.main()`.
`dsx/cli.py:791-804`'s top-level handler only catches `CheckError`, `SpecParseError`, `ValueError`,
and `KeyboardInterrupt` — an `AttributeError` propagates all the way out, producing a raw Python
traceback and Python's default uncaught-exception exit code (1). This directly violates the
project's own documented exit-code contract in `dsx/findings.py:7-10` ("2 -> the check itself
could not run -> gate errors -> onError"): the check *did* fail to run, but the process exits with
1 — the same numeric code `EXIT_BLOCK` uses for "at least one finding at/above threshold" — rather
than exit 2. A caller that only inspects the exit code (as the project's own contract instructs)
cannot distinguish "the gate legitimately blocked" from "the entrypoint scanner crashed on
malformed input and produced no report at all." The module's own docstring
(`dsx/checks/code.py:26-27`) claims "Missing / non-text / unscannable entrypoints are named as NOT
scanned rather than silently skipped" — a structurally-malformed-but-parseable notebook is neither
named nor skipped; it crashes.

**Fix:** Guard the structural assumptions the same way the parse itself is guarded:

```python
if not isinstance(nb, dict):
    return None
...
for cell in nb.get("cells") or []:
    if not isinstance(cell, dict):
        continue
    cell_type = cell.get("cell_type")
    ...
```

Add a regression test alongside `test_notebook_degenerate_shapes_produce_no_finding_no_exception`
covering a non-dict top-level document and a non-dict cell entry.

## Warnings

### WR-01: `PIPELINE_FIT_TRAIN_RE`'s catastrophic-backtracking fix is functionally inert on the fallback it was fixed for, and its own comment overstates the miss it trades away

**File:** `dsx/checks/code.py:77-103`, consumed at `dsx/checks/code.py:1134`

**Issue:** `PIPELINE_FIT_TRAIN_RE` is used exactly once, inside `_first_fit_leak_line`:

```python
if PIPELINE_FIT_TRAIN_RE.search(line):
    return index
for pattern in FIT_LEAK_MARKERS:
    if re.search(pattern, line):
        return index
```

Both branches return the identical value (`index`) for the identical line. Any line matched by
`PIPELINE_FIT_TRAIN_RE` (`Pipeline(...).fit(X_train`) necessarily also contains the substring
`.fit(`, which `FIT_LEAK_MARKERS[0]` (`\.fit\s*\(`) already matches — for the overwhelming
majority of real code (no whitespace between the `.` and `fit`), deleting `PIPELINE_FIT_TRAIN_RE`
entirely would not change `_first_fit_leak_line`'s output for any of the 14 probe shapes the new
tests enumerate. The pattern is only functionally distinguishing in an unusual style
(`obj . fit ( x )`, whitespace around the dot), which none of the added tests exercise.

Separately, the extensive comment at `dsx/checks/code.py:83-100` frames the `{0,200}` bound as
trading "one real miss" (a `Pipeline(...)` argument list containing a nested `)`, e.g. any
`Pipeline([('name', Transformer())])` — which is the standard, idiomatic way to construct a
sklearn `Pipeline`). Because of the redundancy above, that "miss" does not actually change
DSX-CODE-001's verdict on the fallback path in practice — the generic `.fit(` marker still catches
the same line and reports the same index — so the comment's own framing ("The bound trades one
real miss for that guarantee") overstates what is actually being traded, in a way a future
maintainer relying on the comment would not be able to tell.

**Fix:** Either delete `PIPELINE_FIT_TRAIN_RE` and its dedicated timing/probe tests (nothing
downstream depends on its distinguishing behaviour) and note in the comment history why, or — if
it is kept for the whitespace-around-dot edge case — narrow the docstring's claim to that actual
case instead of the nested-parenthesis one, since the nested-paren case is masked by
`FIT_LEAK_MARKERS` regardless.

### WR-02: A declared entrypoint that resolves but cannot be scanned produces no `DecisionRecord` at all, and its explanatory pass line is invisible without `--verbose`

**File:** `dsx/checks/code.py:501-518`, `dsx/decisions.py:200-221` (`record_decision`),
`dsx/findings.py:123-125` (`Report.ok`), `dsx/findings.py:162-179` (`Report.render`)

**Issue:** When `entry` resolves to a path that does not exist, or resolves but cannot be read
(unsupported suffix, unreadable, or structurally invalid `.ipynb` — see CR-03 above), `check()`
returns before either of the two `record_decision(...)` calls (`dsx/checks/code.py:666`,
`dsx/checks/code.py:771`) ever run. `report.ok(...)` is the *only* channel that fires. Two things
compound this:

1. `Report.render()` only prints `passed_checks` under `verbose=True`
   (`dsx/findings.py:171-173`), and `dsx/cli.py`'s `--verbose` flag defaults to `False`
   (`dsx/cli.py:695`). By default, `dsx gate` prints nothing at all about this check when it never
   ran — the render shows a bare `code: PASS ... — CRITICAL=0 ...` line indistinguishable from a
   real clean scan.
2. `DECISIONS.jsonl` — the durable, `dsx explain`-replayable audit trail this phase's own comments
   describe as the project's D-04 deliverable — gets zero entries for this run of the code check,
   even though a real judgment ("this entrypoint could not be scanned, so nothing here can be
   trusted as clean") was in fact made.

This is a pre-existing pattern (confirmed against the pre-phase revision of `code.py`, not
introduced here), and it is explicitly self-flagged by this phase's own test,
`test_unscannable_entrypoint_also_produces_no_decision_record`
(`tests/test_dsx.py`, search "Flagged here for the end-of-phase human check as a possible gap
between design and ship"). The test pins the current (gap) behaviour rather than closing it. Given
this phase's stated design intent (`11.1.1-AST-DESIGN.md`'s blocker B4/B6 table, per the same test's
docstring) called for a `scan_path:not-scanned:<reason>` decision input specifically for this case,
and it was not shipped, this is worth surfacing at review time rather than letting the self-flag
sit unread in test comments only.

**Fix:** Append a `DecisionRecord` (or at minimum a `scan_path:not-scanned:<reason>` decision
input, as the design doc specifies) on every early-return branch of `check()`, not only the two
that currently fire after `call_sites`/`prose_mask` are built. Consider also printing
`passed_checks` unconditionally when `findings` is empty and `passed_checks` names an explicit
"NOT scanned" reason, so a user without `--verbose` is not told nothing at all about a check that
never ran.
