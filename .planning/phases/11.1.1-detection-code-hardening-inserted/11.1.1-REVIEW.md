## Warnings

### WR-01: README's "prints only when `--verbose` is passed" claim is false for `--json` and `--report` output

**File:** `README.md:637`
**Issue:** The paragraph added by this phase (commit `25dee19`, "disclose the four
residual limits of the notebook read") states:

> the line that says the file was not scanned prints only when `--verbose` is passed.
> A notebook that is corrupted — by accident or on purpose — therefore makes the leak
> scan go quiet rather than loud, and a reader running without `--verbose` sees a
> passing code check that looks like a clean scan.

This is true only for the default plain-text `render()` path (`dsx/findings.py:171`,
`if verbose and self.passed_checks:`). It is false for the other two output shapes the
project itself documents as first-class (`README.md`: "Add `--json` anywhere for
machine-readable output"):

- `Report.to_dict()` (`dsx/findings.py:151-160`) includes `passed_checks`
  unconditionally — `verbose` is not even a parameter of `to_dict`. `dsx check code
  --json` (no `--verbose`) on a corrupted notebook therefore DOES surface the
  `"entrypoint NOT scanned — ..."` line, inside `passed_checks`, every time.
- `_markdown_report()` (`dsx/cli.py:665-668`) writes a `## Passed` section from
  `report.passed_checks` unconditionally whenever `dsx audit --report FILE.md` is used
  — again with no `--verbose` gate.

Reproduced directly against the code in this review (verbose left at its default
`False`, no `--json`/`--report` flag simulated beyond calling the same methods the CLI
calls):

```python
report.to_dict(Severity.CRITICAL)["passed_checks"]
== ["entrypoint NOT scanned — could not be read (... ) (no leak scan ran)"]
# present with verbose=False
report.render(Severity.CRITICAL, verbose=False)
== "\ncode: PASS (blocking at CRITICAL) — CRITICAL=0 HIGH=0 MEDIUM=0 LOW=0 INFO=0"
# absent with verbose=False — this is the only path the README's claim is true for
```

No test in `tests/test_dsx.py` exercises `report.to_dict()`, `report.render(...,
verbose=False)`, or `_markdown_report()` against a NOT-scanned report to check this
claim's substance — `test_entrypoint_scan_scope_boundary_is_documented`
(`tests/test_dsx.py:5566`) only asserts the literal substring `"--verbose"` appears
somewhere in `README.md`, which is satisfied by the current (inaccurate) wording just
as it would be by an accurate one. Every other test that touches `passed_checks`
(e.g. `tests/test_dsx.py:5909`, `:5929`, `:5988`, `:6118`) reads the in-memory
`report.passed_checks` list directly, never through the `--verbose`-gated text
renderer, so none of them would catch a regression in the gating logic either way.

This is a documentation-accuracy defect newly introduced by this phase, not a defect
in `dsx/checks/code.py` itself — the underlying `to_dict`/`_markdown_report` behavior
predates the phase and is not itself wrong. But it undercuts the exact point the
paragraph exists to make: a reader relying on this sentence could wrongly conclude
that `--json`-based automation (which README elsewhere recommends: "Add `--json`
anywhere for machine-readable output") has no visibility into a corrupted-notebook
NOT-scanned outcome, when in fact it does. Given how much of this README is built on
the premise that a claim's own text must not contradict what a reader can observe
(the project's own words: "a finding's own text is not the place to discover a
contradiction"), this should be corrected before it ships.

**Fix:** Scope the claim to the specific rendering path it is actually true for, e.g.:

```markdown
Fourth, and most important to state plainly: NOT scanned is a passing outcome. It
exits 0 and produces no finding. In the DEFAULT plain-text render (no `--json`, no
`--report`), the line that says the file was not scanned prints only when
`--verbose` is passed — a reader running the default renderer without `--verbose`
sees a passing code check that looks like a clean scan. `--json` output and an
`--report FILE.md` markdown report both include this line unconditionally, inside
`passed_checks` / the `## Passed` section, regardless of `--verbose` — a
machine-readable or archived report therefore always carries the signal, even when
the terminal does not.
```

Optionally, strengthen `test_entrypoint_scan_scope_boundary_is_documented` (or add a
sibling test) to assert the substantive claim rather than a substring match — e.g.
that `report.to_dict(...)["passed_checks"]` is non-empty for a NOT-scanned report with
`verbose` unset, so a future change to `to_dict`'s gating (in either direction) forces
this paragraph to be re-checked rather than silently drifting again.

## Info

### IN-01: Module docstring not updated for plan 06/07's `.ipynb` shape hardening

**File:** `dsx/checks/code.py:1-30`
**Issue:** The module-level docstring describes the `.ipynb` read as "read the same
way (also `utf-8-sig`) and contributes CODE cells verbatim, blanking markdown cells
CHARACTER-WISE ... a Jupyter magic or shell escape ... is repaired in-place ... then
re-parsed once." It does not mention the plan 06 shape guards (`cells` must be a
list, each cell must be a dict, `source` must be absent/string/list-of-strings) or
that a document nested past the recursion limit is now caught. A reader who only
reads the module docstring (rather than the inline comments at the `_read_source`
call site, which are thorough) would not learn that these shapes are now handled as
NOT-scanned rather than as a crash. This is not a functional defect — every
individual guard is documented in detail at its own call site and pinned by tests —
but it is a case where the single highest-level summary of the module has drifted
slightly behind the code it summarizes.

**Fix:** Add one sentence to the module docstring, e.g.: "A `.ipynb` document that is
valid JSON but not a cell-bearing object in the shape the notebook format defines
(non-dict document, non-list `cells`, non-dict cell, or a `source` that is not
text/list-of-text), or one nested past the interpreter's recursion limit, is also
named as NOT scanned rather than raising."
