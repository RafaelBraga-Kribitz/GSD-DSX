A declared entrypoint that resolves but cannot be scanned makes `check()` return before either `record_decision` call runs, so `DECISIONS.jsonl` gets no entry for that run and `dsx explain` can replay nothing for a judgment that was genuinely made. Its pass line (`entrypoint NOT scanned — ...`) prints only under `--verbose` (confirmed: `Report.render()` gates passed-check lines on `verbose and self.passed_checks`, `dsx/findings.py:171`).

Plan 06 made this path reachable for four more input classes (non-list `cells`, non-string-list `source`, non-string/non-list `source`, and recursion-limit-deep JSON) — a fifth, non-UTF-8 bytes, was found by a pre-execution security audit to already exit 2 rather than reach this path at all, per plan 06's CORRECTION truth. This raises how often the gap matters without changing the gap itself.

**Evidence:** `grep -v '^#' dsx/checks/code.py | grep -c "scan_path:not-scanned"` returns **0** — no task in plans 04, 05, 06 or 07 implemented the `scan_path:not-scanned:<reason>` decision input `11.1.1-AST-DESIGN.md`'s blocker table specified for this case.

**Decision required:** is this an acceptable known gap to ship, or must it close before the phase counts as done? If it must close, it is a new plan — not an edit to this one or to plan 06.
