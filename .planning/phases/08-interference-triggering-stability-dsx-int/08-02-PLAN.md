<objective>
Make the known-bad corpus safe for the four `DSX-INT-*` codes before any of them ships: declare
each fixture's stability block honestly, replace the corpus's family-prefix guarantee with a
per-fixture target-defect map that can express one code per fixture, and commit the new
triggering-dilution fixture pair.

Purpose: three separate corpus tests break the moment `DSX-INT-010` and `DSX-INT-040` start
firing, and the obvious repair is forbidden by construction — `_TARGET_CODE_FAMILIES` already
contains `"DSX-INT-"`, so no `DSX-INT-*` code can be added to the incidental allow-list. Doing
this work first means the suite is never red between plans, and plans 08-03 and 08-04 add one map
entry each instead of carrying a test-suite redesign.

Output: a per-fixture corpus contract with a proof that it fires, three honest stability
declarations, and the fixture `DSX-INT-030` will be measured against.
</objective>

<corrections_applied>
Four corrections to `08-CONTEXT.md` were supplied to the planner, and the planner verified all
four plus two more against the live tree. The two that bear on this plan:

**Correction 4, and it is larger than stated.** `08-CONTEXT.md` decision D-15 sized the corpus
rewrite around one code on one fixture. `08-RESEARCH.md` found a second code on that same fixture.
The planner ran `dsx.loader.load` over every fixture and found the collision is on **three**
fixtures, not one:

| Fixture | Declares | Code it would trip |
|---|---|---|
| `interference-shared-budget` | `novelty_primacy_assessed: false`, `evidence: ""` | `DSX-INT-040` at ship, on top of its intended `DSX-INT-010` at plan |
| `bayesian-continuous-monitoring` | `novelty_primacy_assessed: false`, `evidence: ""` | `DSX-INT-040` at ship |
| `frequentist-uncontrolled-continuous` | `novelty_primacy_assessed: false`, `evidence: ""` | `DSX-INT-040` at ship |

The resolution chosen, and the reason: **fix it at the fixture on all three.** A known-bad fixture
that trips two unrelated code families tests neither cleanly, and this module's own docstring says
each fixture encodes one defect. Documenting the second code instead would need a per-fixture
*set* of incidental codes rather than the simpler target-code map, for no gain — none of these
three fixtures exists to demonstrate a novelty or primacy failure.

**A related near-miss the planner also measured, worth recording because it is fragile.** The
two monitoring fixtures both declare `analysis_population: eligible` with `dilution_adjusted:
false`, which is two of `DSX-INT-030`'s three trigger conditions. They escape only because each
declares a single metric of `type: ratio`, which is outside the additive partition. If either
fixture ever gains a metric of type `count`, `sum` or `average`, it will start blocking
`dsx gate plan` on `DSX-INT-030`. Task 2 records this in a comment beside the map so the next
person to edit those fixtures sees it.

**Correction 3 is confirmed, and the concern raised in `08-PATTERNS.md` is dismissed.**
`08-PATTERNS.md` warned that `_D05_ALLOWLIST_PREFIXES` in `scripts/gen-finding-catalogue.py` might
be an exemption list, so adding `"DSX-INT-"` would switch enforcement off. The planner read
`check_d05` directly. It computes `covered = [row for row in rows if
row[0].startswith(_D05_ALLOWLIST_PREFIXES) or row[0] in _D05_ALLOWLIST_CODES]` and then requires
each covered code to carry a citation, a reference value or structural criterion, and a test
marker. Codes matching those prefixes are the ones **checked**, not the ones excused. The variable
name is confusing and the comment above it reads ambiguously, but the behaviour is unambiguous.
Decision D-04 is correct as written; plan 08-03 adds the prefix. This plan changes nothing in that
script.
</corrections_applied>
