## Summary

This is not an analysis phase — it is a tooling phase that adds eight new finding codes (three
reused, five minted) into the existing `dsx` gate machinery. `11.3-CONTEXT.md` already carries 15
locked decisions (D-01…D-15), each grounded to specific `file:line` anchors. This research's job
was to re-verify every one of those anchors against the live tree (all confirmed accurate, drift
noted below where line numbers shift by 1–3 lines due to normal file growth) and to surface the
landmines a planner would otherwise discover mid-execution.

The single highest-value finding is a **pre-existing SHA256 content-lock test**,
`tests/test_frame_val.py::TestValSamplingMissingnessMeasurement::test_design_checks_py_content_is_unmodified_since_phase_start`
(`test_frame_val.py:1038-1044`, comparing against `_DESIGN_PY_SHA256` at `:627`), which pins the
CRLF-normalized SHA256 of the entire `dsx/checks/design.py` file. REQ-01/02 (D-01/D-02) require
editing that exact file (dropping the early-return at `design.py:403-404`, rebasing the family
count, adding `DSX-EXP-053`). **Without updating `_DESIGN_PY_SHA256` in the same commit, the full
suite goes red on an assertion whose failure message is easy to misread as "you broke Phase 7."**
This guard has been deliberately updated once before (2026-08-24, unrelated tech-debt fix) with a
documented precedent for how to do it: update the constant, add a dated comment explaining why,
in the same commit as the edit.

The second-highest-value finding is a **catalogue-rendering gap, not a citation gap**:
`scripts/gen-finding-catalogue.py`'s `PREFIX_GROUPS` list (`:25-58`) controls which markdown
section a code's row is rendered under in `references/finding-codes.md`; it is separate from
`_D05_ALLOWLIST_PREFIXES` (`:76`, which controls D-05 citation *enforcement*). `dsx/checks/chart_review.py`
(D-12) is a brand-new module/family, so it needs entries in **both** lists — omitting the
`PREFIX_GROUPS` entry silently drops the four `DSX-CRV-*` rows from the rendered catalogue body
(while the `Total: N codes` count at the top still includes them, so nothing looks wrong at a
glance); omitting the `_D05_ALLOWLIST_PREFIXES` entry means `--check` passes green even if the
four codes carry no `Citation:`/`Structural criterion:` docstring line — the opposite failure mode
from what "allowlist" suggests, since this list is opt-in enforcement, not opt-out exemption.

No package legitimacy audit applies — this phase installs no external packages (D-01: stdlib-only
on the gate path).

**Primary recommendation:** Follow the 15 CONTEXT.md decisions exactly as anchored; the three
non-obvious execution risks a plan must explicitly schedule as tasks are (1) updating
`_DESIGN_PY_SHA256` in the same commit as the `design.py` edit, (2) adding `chart_review` to
**four** separate registries (`PREFIX_GROUPS`, `_D05_ALLOWLIST_PREFIXES`, `cli.py`'s `CHECKS` dict
+ import block, `cli.py`'s `GATE_PROFILES` verify/ship tuples), and (3) writing the `exclusions`
closed-key guard (D-09) from scratch — no reusable "unknown-key" helper exists anywhere in the
codebase today.

### Pattern 1: Frame-check guarded on block presence (D-08's required shape)

**What:** A new frame-layer check that fires only when the sub-block is a declared dict/list, and
returns silently otherwise — never treats absence as a defect (that is Phase 6's `DSX-SPEC-081`
territory).
**When to use:** Any new `validity_frame.*` sub-field check.
**Example (existing precedent to clone, `dsx/frame/val.py:1007-1071`, `_check_sampling_frame`):**
```python
# Source: dsx/frame/val.py:1033-1035 (existing pattern D-08 explicitly names as the template)
sampling_frame = frame.get("sampling_frame")
if not isinstance(sampling_frame, dict):
    return
```
D-08's new `_check_exclusions` should open identically: `exclusions = frame.get("exclusions"); if
not isinstance(exclusions, (dict, list)): return` (CONTEXT.md D-08 says "fires only when
`exclusions` is a declared dict/list carrying a rule" — confirm the exact declared shape, singular
dict vs list-of-rules, at plan time; D-15(d) fixtures should exercise whichever shape is chosen).

### Pattern 2: Membership-loop vocabulary addition (D-04's required shape)

**What:** Adding a new closed vocabulary as one more `(block, field, vocab)` tuple row.
**Example (`dsx/spec.py:1116-1126`):**

```python
# Source: dsx/spec.py:1116-1126 — add one row, mint no code (D-04)
_VALIDITY_FRAME_MEMBERSHIP: "tuple[tuple[str, str, Any], ...]" = (
    ("estimand", "type", ESTIMAND_TYPES),

```
`MISSINGNESS_METHODS` (new module-level constant, place near `MISSINGNESS_MECHANISMS` at

### Pattern 3: Literal-severity-string constraint on `report.add()` (mandatory for the D-05 split)

**What:** `scripts/gen-finding-catalogue.py`'s AST extractor (`extract()`, `:164-180`) only
recognises a `report.add(CODE, SEVERITY, TITLE, ...)` call whose **second positional argument is
itself a string literal** — a variable there makes the code invisible to the generated catalogue
(the existing `dsx/frame/val.py:1140-1144` comment documents this explicitly for `DSX-VAL-060`
today, which is already split HIGH/CRITICAL by mechanism).
**When to use:** Any place emitting a finding whose severity depends on a runtime branch.
**Example — the per-method severity split (D-05) must keep this shape, adding a third branch:**
```python
# Source: dsx/frame/val.py:1145-1177, existing two-branch shape to extend to three
if severity == "HIGH":
    report.add("DSX-VAL-060", "HIGH", ...)      # complete_case / available_case under MAR
elif <single_imputation-under-MAR branch>:
    report.add("DSX-VAL-060", "CRITICAL", ...)  # NEW — D-05/D-06, its own citation+remedy
else:
    report.add("DSX-VAL-060", "CRITICAL", ...)  # existing MNAR-unlicensed-method branch
```
Both CRITICAL branches emit the same code with a literal `"CRITICAL"` — that is fine for the AST
extractor (duplicate literal severities for one code are already how `DSX-VAL-060` HIGH is
extracted once despite two call sites in other checks... actually here it's the same code, two
call sites, same severity, different remedy/citation text; `collect()`'s de-dup (`:225-229`)
keeps the *last*-sorted row and only *warns* — not fails — when two call sites for the same code
disagree on severity/title text, so this is safe but worth a planner's awareness).

### Pattern 4: Registering a new checks-layer module reading a non-spec artifact (D-12's integration)

**What:** `dsx/checks/figures.py::check(spec, phase_dir, *, strict=False)` is the existing
precedent for a checks-layer module that resolves an on-disk sibling artifact via `phase_dir`/
`root` rather than reading structured content out of `spec` itself.
**Four registries `chart_review` must be added to (all in `dsx/cli.py` unless noted):**
1. Import block `from .checks import (..., chart_review, ...)` (`cli.py:23-38`) — alphabetically
   before `claims` (`ch` < `cl`).
2. `CHECKS` dict (`cli.py:63-83`) — `"chart_review": chart_review.check` is not quite right if the
   function needs `root`/`phase_dir` like `figures.check` does; if so it needs its own explicit
   branch in `run_checks()` (`cli.py:187-234`, mirroring the `elif name == "figures":` branch at
   `:196-197`), not a bare `CHECKS[name](spec)` dispatch.
3. `GATE_PROFILES["verify"]` and `GATE_PROFILES["ship"]` tuples (`cli.py:119-128`) — **not**
   `plan` or `execute`: `CHART-REVIEW.md` is a post-execution artifact, mirroring `figures`,
   `narrative`, `claims`, `smells` (all absent from `plan`/`execute` for the identical reason —
   nothing to read before the audit runs).
4. `scripts/gen-finding-catalogue.py`'s `PREFIX_GROUPS` (`:25-58`) and `_D05_ALLOWLIST_PREFIXES`
   (`:76`) — see Common Pitfalls below; both are silent-failure modes, not loud ones.

### Anti-Patterns to Avoid
- **Retrofitting the closed-key shape guard to legacy blocks:** D-09 explicitly blocks widening
  the new `exclusions` guard to the pre-existing tolerant `inference`/`validity_frame` blocks
  (`spec.py:1262-1269` documents today's deliberate tolerance for `inference`). Scope the guard to
  `exclusions` only.
- **Using a `try/except ValueError` around `interpret_effect`:** D-11 explicitly forbids this — a
  caught exception still routes an exception through the gate path (D-01 violation in spirit); use
  a membership guard *before* the call instead.
- **Reusing `DSX-FIG-*` for chart-review conformance:** D-12 names this the specific trap to
  avoid — the schema's own Gate-D proxy (`chart-review-schema.md:53`) wildcards `DSX-FIG-*` at
  CRITICAL/HIGH, so a malformed report minting a `DSX-FIG-*` code would be swept into the very
  gate the report is supposed to be reporting on (circular).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|

## Common Pitfalls

### Pitfall 1: `_DESIGN_PY_SHA256` content lock breaks silently on the D-01/D-02 edit
**What goes wrong:** The full suite (`scripts/check.sh` / `python3 -m unittest discover -s tests`)
fails at `tests/test_frame_val.py::test_design_checks_py_content_is_unmodified_since_phase_start`
with a message that reads "REQ-P7-03 requires it unmodified" — easy to misdiagnose as a Phase 7
regression rather than an expected Phase 11.3 edit.
**Why it happens:** `tests/test_frame_val.py:613-627` hashes the CRLF-normalized bytes of
`dsx/checks/design.py` and pins the digest as a Phase-7 invariant ("this family must never be
edited during Phase 7"); Phase 7 is long since shipped, but the guard was never removed and has
already been deliberately updated once (2026-08-24, unrelated tech-debt fix) using the documented
"update the constant + explain why in a comment + commit message" procedure.
**How to avoid:** In the same commit that edits `dsx/checks/design.py` for D-01/D-02, recompute
the hash (`hashlib.sha256(path.read_bytes().replace(b"\r\n", b"\n")).hexdigest()`) and update
`_DESIGN_PY_SHA256` at `tests/test_frame_val.py:627`, with a dated comment block (matching the
existing 2026-08-24 precedent's style) naming Phase 11.3 / D-01 / D-02 as the reason.
**Warning signs:** A green suite before the `design.py` edit and a single red test after — this is
the tell, not a sign the edit broke something else.

### Pitfall 2: New `DSX-CRV-*` family silently vanishes from the rendered catalogue (not from the count)
**What goes wrong:** `references/finding-codes.md`'s `Total: 256 codes.` header line is correct,
but the four `DSX-CRV-*` rows never appear under any `## heading` section in the body — because
`render()` (`scripts/gen-finding-catalogue.py:233-263`) iterates `PREFIX_GROUPS` and only emits a
section `if group:` (non-empty); a code whose prefix has no `PREFIX_GROUPS` entry is silently
excluded from every section while still counted in `len(rows)`.
**Why it happens:** `collect()` (`:213-230`) extracts *any* `report.add(CODE, ...)` call whose code
starts with `"DSX-"`, regardless of whether the prefix is registered anywhere else — extraction and
rendering are two independent passes over the same `rows` list.
**How to avoid:** Add `("DSX-CRV", "Chart review conformance", "<blurb>")` to `PREFIX_GROUPS`
(`:25-58`) in the same commit as the new module. Precedent: `tests/test_gen_finding_catalogue.py:171-172`
asserts `"DSX-PAR"` is present in `[p for p, _, _ in PREFIX_GROUPS]` — a parallel test for
`"DSX-CRV"` is worth adding to make this a loud failure instead of a silent one.

### Pitfall 3: New `DSX-CRV-*` family silently exempt from D-05 citation enforcement
**What goes wrong:** `--check` passes green even though the four new codes carry no `Citation:` /
`Structural criterion:` docstring line and no `# D-05: DSX-CRV-0xx` test marker — the opposite of
what "allowlist" suggests.
**Why it happens:** `check_d05()` (`scripts/gen-finding-catalogue.py:323-353`) only inspects codes
matching `_D05_ALLOWLIST_PREFIXES` or `_D05_ALLOWLIST_CODES` — this is an **opt-in** enforcement
list (`covered = [row for row in rows if row[0].startswith(_D05_ALLOWLIST_PREFIXES) or ...]`), not
an opt-out exemption list. A prefix that is simply absent from both sets produces zero D-05
failures no matter how uncited its codes are.
**How to avoid:** Add `"DSX-CRV-"` to `_D05_ALLOWLIST_PREFIXES` (`:76`) in the same commit —
precedent: every wholly-new-in-this-milestone family (`DSX-VAL-`, `DSX-INT-`, `DSX-PRE-`,
`DSX-ADM-`) was added this way, as opposed to `_D05_ALLOWLIST_CODES` (used only when a new code
lives inside a pre-existing family with uncited legacy siblings — not this case, since
`chart_review.py` is a brand-new file with zero legacy siblings).
**Warning signs:** `--check` passes despite the new module's docstrings genuinely lacking a
`Citation:` line — the false-negative case this pitfall describes has no visible symptom by
design; only a deliberate re-read of `check_d05()`'s allowlist membership catches it.

### Pitfall 4: `interpret_effect`'s recognised-kind set is not actually single-sourced today
**What goes wrong:** A planner might assume `stats.py`'s `if kind in ("d", "h", "r"):` guard
(`stats.py:279`) is already derived from `mathx.py`'s `interpret_effect` table (`mathx.py:295-299`)
because the two lists happen to agree — they are two independent literals that could silently
drift apart in a future edit to either file.
**Why it happens:** No shared constant exists; `table` (`mathx.py:295-299`) is a local variable
inside `interpret_effect`'s function body, not a module-level export.
**How to avoid:** D-11 permits either fix: (a) hoist `table`'s keys to a module-level constant in
`mathx.py` (e.g. `EFFECT_SIZE_KINDS = frozenset({"d", "h", "r"})`) imported by both functions, or
(b) leave both literals in place and add a test asserting `set(stats._RECOGNISED_EFFECT_KINDS) ==
set(mathx._EFFECT_SIZE_TABLE_KEYS)` (whatever internal names are chosen) so any future drift fails
loudly. CONTEXT.md leaves the choice to the planner; either satisfies D-11's requirement, but the
plan must pick one explicitly — "do nothing" leaves the guard exactly as fragile as it is today.
**Warning signs:** A new effect-size kind gets added to `interpret_effect`'s table without a
matching update to `stats.py`'s guard (or vice versa) — the two would silently disagree about
which kinds are "recognised," defeating REQ-05's own guarantee.

### Pitfall 5: No reusable closed-key/unexpected-key helper exists anywhere in `dsx/`
**What goes wrong:** A planner might search for an existing generic "reject unknown dict keys"
utility to reuse for D-09's `DSX-SPEC-083` guard and not find one, wasting a task cycle.
**Why it happens:** Confirmed by repo-wide grep — no such helper exists. Every closed-vocabulary
check in the codebase validates a single *value* against a vocabulary (`_VALIDITY_FRAME_MEMBERSHIP`'s
pattern); none validates a dict's *key set* against a closed set of allowed keys. `_INFERENCE_FIELDS`
(`spec.py:1273-...`) documents the closest sibling ("this tuple is not an enforced closed set")
precisely because no such enforcement mechanism was ever built.
**How to avoid:** Budget this as genuinely new code (a short function, e.g. `set(exclusions.keys())
- {"rule", "action", "applied_before_split", "justification"}`, iterated if `exclusions` is
declared as a list of rule-dicts rather than a single dict — confirm the exact shape at plan time),
placed alongside `_validate_validity_frame_shape` (`spec.py:1220-1239`) per D-09's own text ("added
alongside the existing membership loop").
**Warning signs:** None at review time — this is a scoping risk (plan underestimates the task),
not a runtime risk.
