Register `prereg` at verify and ship, thread the project root into it, and absorb the blast radius
that registration creates across the existing test suite.

Purpose: this is the highest-risk plan in the phase. The moment `prereg` joins
`GATE_PROFILES["verify"]` and `["ship"]`, the missing-plan-header rule from plan 03 fires against
every existing call site that reaches those points without a prior plan run — and because a
`CheckError` prints plain text even under `--json`, the failure surfaces as an unrelated decoding
error rather than a legible assertion. The registration and the harness repair therefore land in one
commit, not two.

call site repaired, and the registration and reachability tests ROADMAP Success Criterion 5 requires.

## Settled decision: which invocations reconcile the trail

CONTEXT leaves to the planner whether `dsx check`, which bypasses `GATE_PROFILES`, should run
`prereg`. Research recommended accepting the existing behaviour on the premise that `cmd_check` and
`cmd_audit` call `CHECKS[name](spec)` directly. **That premise is wrong**, verified by direct read:
both call `run_checks(...)` with `tuple(CHECKS) + ("repro",)` (`dsx/cli.py:203-214` and `:217-234`),
so they route through the same elif chain and would receive the root argument correctly.

The real consequence is different and more serious. `cmd_audit` passes `gate_point="ship"`
(`dsx/cli.py:224`) but **never calls `_write_decision_trail`** — that function's own docstring states
only `dsx gate` calls it, and that `validate`, `check` and `audit` are read-only inspection commands.
An operator running only `dsx audit` could therefore never satisfy a trail precondition, at any point,
by any sequence of commands. That is a dead end, not a discipline nudge. It would also break
`tests/test_dsx.py:1636-1643`, which audits a specification written into a fresh temporary directory
that has no trail and never will.

So trail reconciliation is scoped to a real gate invocation: `run_checks` gains a `gate_invocation`
keyword defaulting to `False`, `cmd_gate` alone passes `True`, and the trail-dependent half runs only
when that flag is set and the gate point is verify or ship. `dsx check` and `dsx audit` still run
`prereg`'s trail-independent half — the rule resolution and the procedure reconciliation — which is
consistent with every other check they run.

This does not soften D-09. At `dsx gate verify` and `dsx gate ship` a missing plan-time header still
exits 2 with the `suppressions[]` route named. The line drawn here is the one the codebase already
draws in prose, between the trail's participants and its read-only inspectors.
