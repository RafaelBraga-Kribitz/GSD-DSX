# Phase 11.1 Plan 06: Baseline Score Provenance and Fold-Spread Margin (DSX-ML-052/053) Summary

**Added two optional `results` fields — `model_score_source` and `fold_scores` — so a baseline comparison can state where its reported score came from and how much its own folds vary; a blank, disqualifying (best-fold/unknown) or unrecognised source draws DSX-ML-052 at HIGH, and a margin over baseline strictly smaller than the model's own fold spread draws DSX-ML-053 at MEDIUM naming both numbers, both gated on the model already beating its baseline.**

- **Tasks:** 2

## Accomplishments

- `SCORE_SOURCES = frozenset({"cv_mean", "holdout", "nested_cv", "best_fold", "unknown"})` added to `dsx/checks/ml.py`: five declared answers to "where did this score come from", with a comment above the constant stating the three-accepted/two-disqualifying split explicitly, so a reader does not assume all five members pass a membership test.
- `_check_baseline` extended, both new checks living inside the branch where the model already beats its baseline (a model that loses still gets the pre-existing DSX-ML-051 CRITICAL and neither new code):
  - `DSX-ML-052` (HIGH) fires when the normalised `results.model_score_source` is not a member of `SCORE_SOURCES` at all (covers blank and any misspelling) or is a member of the disqualifying pair (`best_fold`, `unknown`) — one boolean expression covers all four failing cases without a second constant.
  - `DSX-ML-053` (MEDIUM) fires when at least two `results.fold_scores` entries parse via `as_number` and the margin (`model_score − baseline_score`) is strictly less than the spread (`max − min` of the parseable scores); the comparison is strictly less-than by design, documented inline so a future reader does not widen it to `<=`.
- Both `report.add` calls sit inside the beats-baseline branch, followed by a shared deterministic decision record naming the declared source and the parsed fold count as inputs, and the counterfactual (a source inside the accepted three, a margin at or above the spread) that would have cleared both codes.
- `_check_baseline` gained its first-ever docstring: a Varma, S. and Simon, R. (2006), "Bias in Error Estimation When Using Cross-Validation for Model Selection" (BMC Bioinformatics, 7, article 91) citation naming the paper's Abstract/Conclusions as the locator for the biased-best-of-several-folds result (exact page locator marked UNVERIFIED, not invented, per D-05), plus a structural-criterion paragraph naming both codes as a membership test and a subtraction-based ordering comparison respectively.
- `templates/ANALYSIS-SPEC.yaml`'s `results` block gained `model_score_source: null` and `fold_scores: []`, following the existing uncommented/null convention the surrounding score fields already use — confirmed against `dsx/spec.py`'s `REQUIRED_TOP_LEVEL` and the validity-frame required-field lists that neither field appears in any required list (no change needed there).
- `DSX-ML-052` and `DSX-ML-053` added to `_D05_ALLOWLIST_CODES`; `DSX-ML-050`/`051` (the legacy codes sharing `_check_baseline`, the function this plan extended) deliberately excluded, matching the precedent plans 11.1-04 and 11.1-05 set for their own extended functions' legacy siblings. `references/finding-codes.md` regenerated: 238 → 240 total codes, exactly +2.

## Decisions Made

- Placed both new checks and the shared decision record entirely inside `_check_baseline`'s pre-existing beats-baseline branch (not evaluated when the model fails to beat its baseline, and not evaluated across the two earlier early returns) — the plan's action text was explicit about this branch placement, and it matches the `<behavior>` list's own framing that a negative margin is a different finding than a small one.
- Chose one boolean condition (`score_source not in SCORE_SOURCES or score_source in ("best_fold", "unknown")`) over introducing a second "accepted three" constant — `SCORE_SOURCES` alone, split by that one condition, correctly separates all four failing cases (blank, misspelled, best_fold, unknown) from the three passing ones, so a second constant would only add a place for the two lists to drift apart.
- Rewrote `DSX-ML-052`'s finding title from a ternary expression to a single unconditional f-string with a pre-computed `score_source_display` variable (`"not stated"` when blank) — the ternary form runs correctly at request time but is invisible to `gen-finding-catalogue.py::extract()`'s AST walk, which only recognises a literal string or a plain f-string in the title argument position. Left uncaught, this would have silently excluded `DSX-ML-052` from the generated catalogue and from D-05 citation/test-marker enforcement, while the finding itself kept firing correctly — the kind of drift the catalogue script exists to prevent. Documented inline at the call site so the next reader adding a conditional title elsewhere in this file does not repeat it.
- Followed `templates/ANALYSIS-SPEC.yaml`'s uncommented/null field convention (matching `model_score`, `baseline_score`, …) rather than plan 11.1-05's commented-scaffold convention (used for the `data[].cleaning[]` block) — the plan's own `read_first` pointer specified which convention applied here.

## Deviations from Plan

**1. [Rule 1 - Bug] `DSX-ML-052`'s finding title was an AST-invisible ternary expression**
- **Found during:** Task 2, running `python scripts/gen-finding-catalogue.py --check` and then `python -m unittest discover -s tests`, which surfaced `tests/test_gen_finding_catalogue.py::test_d05_covered_code_set_on_the_real_tree_is_exactly_the_documented_set` failing with `DSX-ML-052` present in `_D05_ALLOWLIST_CODES` but absent from `collect()`'s extracted rows.
- **Issue:** Task 1's implementation passed a Python conditional expression (`f"..." if score_source_raw else "..."`) as `report.add()`'s title argument. `scripts/gen-finding-catalogue.py::extract()` reads this argument straight off the AST and only recognises `ast.Constant` (a plain string) or `ast.JoinedStr` (a plain f-string) — a conditional expression (`ast.IfExp`) returns `None` from `_literal()`, so the whole `report.add()` call was silently skipped during catalogue collection. The finding itself fired correctly at runtime (proven by Task 1's own passing tests); only the catalogue-generation and D-05-enforcement tooling could not see it.
- **Fix:** Replaced the ternary with a single unconditional f-string, folding the blank case into a `score_source_display` variable computed one line earlier (`score_source_raw if score_source_raw else "not stated"`), still naming the declared value when there is one per the plan's title instruction.
- **Files modified:** `dsx/checks/ml.py`
