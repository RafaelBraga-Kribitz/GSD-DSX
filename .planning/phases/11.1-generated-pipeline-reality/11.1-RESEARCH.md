## Summary

Phase 11.1 widens two already-shipped, already-gate-wired check families —
`dsx/checks/code.py` (`DSX-CODE-*`, registered at execute/verify/ship) and `dsx/checks/ml.py`
(`DSX-ML-*`, registered at execute/verify/ship) — plus adds one new optional contract sub-block.
No new gate points, no new CLI commands, no new external dependency: this is stdlib-only
regex/AST-adjacent text scanning over the same entrypoint-resolution machinery `code.py`
already has, and dict/field reads inside the same `spec.py` access-helper idioms `ml.py`
already uses.

The corpus case this phase must ship (REQ-P11.1-07) has an unusually strong, already-committed
source: `references/The AI Data Scientist.md` is the full text of the arXiv paper (2508.18113v1)
whose autogenerated 6-subagent pipeline is the "2026-08-20 paper evaluation" reproduction named
throughout `brief.md` and `ROADMAP.md`. Its own worked code samples (Table 1, Table 2) are the
precise failure mode this phase must catch: the Data Cleaning Subagent imputes mean/median and
detects z-score/IQR outliers over the **full** dataframe before any split exists in the
pipeline; the Hypothesis Subagent runs `chi2_contingency` directly against the declared target
column (`dataset['Exited']`) with no split in sight; the Preprocessing Subagent calls
`min_max_scaler.fit_transform(data[['Balance']])` on the full frame, not `X_train`; and the
Model Training Subagent selects from an 18-model roster via k-fold CV and combines the "best"
into a stacking/voting ensemble with no declared selection ledger. This is not a hypothetical
fixture design — it is a direct transcription opportunity.

D-05's mechanical citation gate (`scripts/gen-finding-catalogue.py::_D05_ALLOWLIST_PREFIXES`)
does **not** currently cover `DSX-CODE-*` or `DSX-ML-*` — both are pre-existing (v1.3.0/v1.0.0)
families outside the milestone's enforcement boundary (D-20). Every new code Phase 11.1 adds
lives inside one of these two pre-existing families, so the correct extension point is
`_D05_ALLOWLIST_CODES` (the exact-code path Phase 6 used for `DSX-SPEC-080`-`086`), never
`_D05_ALLOWLIST_PREFIXES` (which would retroactively drag ~90 legacy DSX-CODE-*/DSX-ML-* codes
into citation enforcement with no docstring update to satisfy it, breaking the build).

**Primary recommendation:** Extend `code.py` and `ml.py` in place (no new modules), enumerate
every new code individually in `_D05_ALLOWLIST_CODES`, model the known-bad fixture verbatim on
`references/The AI Data Scientist.md`'s own code samples, and resolve the training-frame lexicon
and exact numeric codes at plan time using the options below — both are explicitly marked
"fixed at discuss" in `ROADMAP.md` and no discuss pass has run for this phase.

## Standard Stack

### Core

No new libraries. This phase is stdlib-only, matching the project's existing constraint
(`dsx/checks/code.py`'s own docstring: "Stdlib-only: `.py` as text; `.ipynb` via json cell
source concat"). `re`, `json`, `ast` (already imported elsewhere in `dsx/`, e.g.
`scripts/gen-finding-catalogue.py`) are the only modules the widened scan needs.

| Library | Version | Purpose | Why Standard |
|---------|---------|---------|--------------|
| `re` (stdlib) | Python 3.x builtin | Line-based idiom matching against entrypoint source text | Matches the existing `code.py` pattern exactly — `FIT_LEAK_MARKERS`, `SCALER_FULL_RE`, `RESAMPLE_BEFORE_RE`, `PIPELINE_FIT_TRAIN_RE` are all `re` |
| `json` (stdlib) | Python 3.x builtin | `.ipynb` cell source concatenation | Already used by `code.py::_read_source` |

### Supporting

None. No AST parsing of the *target* entrypoint is used anywhere in `dsx/checks/code.py` today
— detection is line-text regex only, deliberately (an entrypoint may not even be valid Python
at scan time, e.g. a `.ipynb` cell fragment). Introducing `ast.parse()` over arbitrary,
untrusted entrypoint source would be a scope change (and a new failure mode — a syntax error in
the target file would need to degrade gracefully, mirroring `code.py::_read_source`'s existing
try/except around `.ipynb` JSON parsing). **Recommendation: stay text/regex-based**, consistent
with the existing family and with D-16 (`dsx/spec.py`'s "single condition" principle — one
detection mechanism, not two disagreeing ones).

### Alternatives Considered

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Regex line-scan over entrypoint text | `ast.parse()` + AST walk for structural certainty (e.g. resolving what `df` is bound to) | Correctly resolves aliasing (`train = df; train.fit(...)`), but breaks on `.ipynb` fragments and any non-parseable snippet the current tool tolerates; would be a genuine architecture change the roadmap doesn't ask for. Text-scan false negatives are an accepted, named limitation elsewhere in this project (README "a frame that lies passes") |
| Individual `_D05_ALLOWLIST_CODES` enumeration | Add `DSX-CODE-` / `DSX-ML-` to `_D05_ALLOWLIST_PREFIXES` | Prefix addition retroactively requires all ~14 legacy `DSX-CODE-*` and `DSX-ML-*` codes to carry `Citation:`/`Reference value:` docstring lines and `# D-05:` test markers they don't have today — `scripts/check.sh`'s `--check` step would fail on files this phase doesn't touch. D-20's own inline comment explicitly warns against this |

### Pattern 1: Line-based idiom detection with a "before split" guard

**What:** `code.py` finds the first line index matching a marker tuple, then compares indices
— `first_fit is not None and (first_split is None or first_fit < first_split)`.
**When to use:** Any check that cares about *ordering* between two textual events in the same
file (a cleaning idiom vs. a split marker).
**Example:**
```python
# Source: dsx/checks/code.py:63-84 (existing, read directly)
first_split = _first_line_matching(lines, SPLIT_MARKERS)
first_fit = _first_fit_leak_line(lines)
if first_fit is not None and (first_split is None or first_fit < first_split):
    report.add("DSX-CODE-001", "CRITICAL", "...", ...)
```
REQ-P11.1-01's new "full-frame cleaning idiom **before** the split" check is the same pattern,
applied to a new marker tuple (`.fillna(` co-occurring with `.mean()`/`.median()`/`.mode()` on
the same or a recent line; a row filter using `.std()`/`.quantile(`). REQ-P11.1-01's second half
— "`.fit`/`.fit_transform` **at or after** the split whose first argument is not a training
frame" — inverts the comparison (`first_split is not None and index >= first_split`) and adds a
first-argument-token check, which is new logic; nothing in `code.py` today inspects the
argument passed to `.fit(`.

### Pattern 2: First-argument extraction from a fit call

**What:** REQ-P11.1-01's second clause needs the literal text between `.fit(`/`.fit_transform(`
and its closing paren (or up to the first comma), to compare it against a training-frame name
list.
**When to use:** Distinguishing `imputer.fit(X_train)` (clean) from
`imputer.fit(df)`/`imputer.fit(data)` (leaky) when both occur textually after a split marker.
**Example (proposed, not yet in the codebase):**
```python
# Proposed — extends dsx/checks/code.py's existing regex family
FIT_CALL_RE = re.compile(r"\.fit(?:_transform)?\s*\(\s*([A-Za-z_][A-Za-z0-9_.\[\]'\"]*)")
# match.group(1) is the first-argument token, e.g. "X_train", "df", "data[['Balance']]"
```
The existing `PIPELINE_FIT_TRAIN_RE` (`Pipeline\(...\)\.fit\(\s*X_train\b`) already hardcodes
exactly one accepted training-frame token (`X_train`) for exactly one call shape
(`Pipeline(...).fit(...)`). REQ-P11.1-01 generalises this to *any* `.fit`/`.fit_transform` call,
against a *lexicon* of accepted first-argument tokens (see "Training-Frame Name Lexicon" below),
not one hardcoded literal.

### Pattern 3: Statistical-test-sees-target scan (new)

**What:** REQ-P11.1-02 — detect a call to a statistics function whose argument list contains a
reference to the declared `model.target` column, independent of whether any `.fit(` call is
present at all. This is the exact idiom the source paper's Hypothesis Subagent emits (Table 1 in
`references/The AI Data Scientist.md`):
```python
# Source: references/The AI Data Scientist.md, Table 1 code sample (verbatim from the paper)
contingency_table = pd.crosstab(active_member, dataset['Exited'])
chi2, p, _, _ = chi2_contingency(contingency_table)
```
`Exited` is the paper's churn target column. No `.fit(` appears anywhere in this snippet — the
existing `FIT_LEAK_MARKERS` regex family is structurally blind to it, which is exactly why
REQ-P11.1-02's description calls it "the marker no fit-scan can see."
**When to use:** Detecting leakage that manifests as *evaluation* rather than *training* — a
statistical test computed over the full (unsplit) frame using the target directly, whose result
(a p-value / significance flag) is then folded back into the feature set for modelling (the
paper's own §2.2: "Accepted hypotheses ... are appended to the dataset for downstream
subagents").
**Proposed detection shape:**
```python
# Proposed — a new marker tuple in dsx/checks/code.py
STAT_TEST_CALLS = (
    r"chi2_contingency\s*\(", r"ttest_ind\s*\(", r"ttest_rel\s*\(", r"pearsonr\s*\(",
    r"mannwhitneyu\s*\(", r"f_oneway\s*\(", r"kruskal\s*\(",  # scipy.stats surface
)
# fire when a STAT_TEST_CALLS match's containing statement (or the pd.crosstab/groupby
# feeding it, within N preceding lines) references model.target's column name as a
# bracket/attribute access: df['Exited'], df.Exited, dataset["Exited"]
```
This needs `model.target` (already a required field, `DSX-SPEC-052`) threaded into `code.check()`
— currently `code.check(spec, phase_dir)` reads only `reproducibility.entrypoint` and
`section(spec, "model")` for the boolean `has_model`; it does not read `model.get("target")`.
That is a small, contained signature change.

### Anti-Patterns to Avoid

- **Hardcoding one training-frame literal (`X_train`) as the only accepted name:** the existing
  `PIPELINE_FIT_TRAIN_RE` already does this and REQ-P11.1-01 explicitly widens past it. Do not
  ship a second single-literal special case; ship a lexicon (see below).
- **Adding `DSX-CODE-`/`DSX-ML-` to `_D05_ALLOWLIST_PREFIXES`:** retroactively obligates every
  legacy code in those families to carry citations they don't have — use
  `_D05_ALLOWLIST_CODES` instead, per D-20's own documented rationale.
- **Silently degrading the `prediction_time_definition` fix into "still gated, just on a
  different field":** REQ-P11.1-04's wording is explicit — "no longer gated on the features
  list" — the fix must move the check *out* of `_check_features`'s early-return path entirely,
  not relax the condition that triggers the early return.
- **Introducing `ast.parse()` for the target entrypoint without a fallback:** would regress
  `.ipynb`/malformed-file tolerance the existing scan deliberately has (`_read_source` swallows
  `OSError`/`json.JSONDecodeError` and returns `None`, which short-circuits the whole check
  cleanly rather than crashing the gate).

**Key insight:** every mechanism this phase needs (entrypoint resolution, D-05 enforcement,
decision-record emission, gate registration, vocabulary registries) already exists and is
exercised by 8+ shipped phases. The work is *extending existing functions with new branches and
constants*, not building new subsystems. The one genuinely new piece of machinery is the
first-argument-token extraction for `.fit(`/`.fit_transform(` calls (Pattern 2 above) — even
that is a narrow regex, not a parser.

## Common Pitfalls

### Pitfall 1: D-05 allowlist scope (family prefix vs. exact code)

**What goes wrong:** Adding `"DSX-CODE-", "DSX-ML-"` to `_D05_ALLOWLIST_PREFIXES` instead of
enumerating the *new* codes in `_D05_ALLOWLIST_CODES`.
**Why it happens:** The prefix list looks like the "obvious" place to register a new family,
and three of the four already-shipped v2.0.0 families (`DSX-PAR-`, `DSX-VAL-`, `DSX-INT-`,
`DSX-PRE-`) *are* whole new families registered by prefix.
**How to avoid:** `DSX-CODE-*` and `DSX-ML-*` are not new families — they are v1.0.0/v1.3.0
families this phase adds *new codes inside*. `_D05_ALLOWLIST_CODES`'s own comment documents
exactly this exception path ("A single code that lives inside a pre-existing family ... is
named individually in `_D05_ALLOWLIST_CODES` instead"), and Phase 6 already used it for
`DSX-SPEC-080`-`086` (new codes inside the pre-existing `DSX-SPEC-*` family). Follow that
precedent.
**Warning signs:** `scripts/check.sh`'s `--check` step starting to fail on `DSX-CODE-001`/
`DSX-ML-020` (pre-existing codes) demanding citations that were never written for them.

### Pitfall 2: `_check_features`'s early return hides `prediction_time_definition`

**What goes wrong:** `dsx/checks/ml.py::_check_features` (lines ~230-297, read directly) returns
immediately after emitting `DSX-ML-030` when `model.features` is blank — the
`prediction_time_definition` check (`DSX-ML-033`) is the *last* statement in that same function,
so it never runs when features are undeclared. REQ-P11.1-04 requires the opposite: the check
must fire even with no `features:` list.
**Why it happens:** The function was written to "screen features," and `prediction_time_definition`
was appended to the bottom of that function opportunistically (it needs no feature list to be
meaningful — it is a text field, not derived from `features`).
**How to avoid:** Extract the `prediction_time_definition` check into its own call in
`ml.check()`'s top-level dispatch (alongside `_check_split`, `_check_preprocessing`, etc.),
independent of `_check_features`, so it runs whenever `model:` is present at all.
**Warning signs:** A fixture with `model:` declared but no `features:` list still passing clean
on `prediction_time_definition` after the fix ships — the regression the requirement exists to
prevent.

### Pitfall 3: `DSX-ML-041`'s undeclared-positive-rate gap

**What goes wrong:** `_check_metric_choice`'s imbalance branch is gated
`if task in DECISION_TASKS and positive_rate is not None:` — an *undeclared* `positive_rate`
currently produces **no finding at all**, not even the `ok()` line. REQ-P11.1-04's second clause
("undeclared positive rate under an imbalance-unsafe primary metric fires") needs a new branch
(and, per Pitfall 1, a new code) for exactly this `positive_rate is None` case.
**Why it happens:** The existing code was written to evaluate a declared imbalance ratio, not to
audit the absence of the declaration itself — mirrors the same shape as `DSX-ML-020` (declared
value wrong) vs. an as-yet-nonexistent "value not declared" sibling for this specific field.
**How to avoid:** Add the sibling branch inside `_check_metric_choice`, following the
`DSX-ML-020`/`preprocessing_fit_on`-not-declared pattern already present two functions away
(`_check_preprocessing`).

### Pitfall 4: Regex catastrophic backtracking (ReDoS) on untrusted entrypoint text

**What goes wrong:** The entrypoint file is analyst-authored code, not a trusted internal
config — the project's own Phase 7 security review flagged this exact class of risk for
free-text spec fields (`T-7-03`, `dsx/spec.py`'s `_FALSIFIER_NUMBER_RE`/`_PLACEHOLDER_RE`,
mitigated with "bounded, non-nested, linear patterns" plus a 20,000-character timing test).
`code.py` does not currently size-cap the entrypoint file it reads (`_read_source` has no length
guard), and this phase adds several *new* regexes over that same unbounded text.
**Why it happens:** Existing `code.py` regexes (`SCALER_FULL_RE`, `RESAMPLE_BEFORE_RE`,
`PIPELINE_FIT_TRAIN_RE`) are already simple/linear, so this risk hasn't surfaced yet — but the
new first-argument-extraction pattern (Pattern 2 above) has a `[...]*` repetition inside a
character class that must stay non-nested.
**How to avoid:** Keep every new pattern to the same shape discipline Phase 7 already
established and tested (bounded quantifiers, no nested `(...)*` inside `(...)*`). Add a timing
test mirroring `tests/test_dsx.py:789-798`'s pattern if a new pattern's complexity is not
obviously linear by inspection.
**Warning signs:** A new regex containing two or more `*`/`+` quantifiers where one's matched
character class overlaps the other's.

### Pitfall 5: Decision records are a standing per-phase deliverable, not opt-in

**What goes wrong:** Shipping the new checks without emitting `DecisionRecord`s at their key
judgment points, because neither `code.py` nor `ml.py` emits any decision records today (grep
confirms zero `DecisionRecord` usage in either file, unlike `dsx/spec.py` and `dsx/frame/val.py`,
which emit them at every shape-validator judgment point).
**Why it happens:** `code.py`/`ml.py` predate the decision-record machinery (Phase 6, v2.0.0);
nothing in those modules was retrofitted when Phase 6 shipped.
**How to avoid:** `STATE.md`'s "Standing per-phase deliverables" section is explicit: "Emit
decision records at each family's key judgment points (D-04)." This applies to *this* phase's
new logic even though it lives in pre-Phase-6 files — the standing deliverable is scoped to the
milestone (v2.0.0), not to which module a check happens to live in. Confirm this reading at plan
time; it is the one item in this pitfall list not settled by direct code inspection (the standing
deliverables list does not explicitly enumerate "except code.py/ml.py").

## Corpus Case Design (REQ-P11.1-07 / REQ-P11.1-08)

`references/The AI Data Scientist.md` (arXiv 2508.18113v1) is committed in-repo and is, by
internal dating (`created: 2026-08-20` in its own frontmatter) and by `ROADMAP.md`'s repeated
"2026-08-20 paper evaluation" phrasing, the actual source of the reproduction this phase exists
to close. Concrete transcription material, verified by direct read of the paper text:

1. **Full-frame cleaning before any split** (§2.1, Data Cleaning Subagent): "For numerical
   columns, the Subagent applies imputation techniques such as the mean or median... To identify
   outliers in numerical data, the Subagent applies statistical checks such as z-score
   thresholds and interquartile range (IQR) analysis." No split marker exists anywhere before
   this stage in the paper's own pipeline ordering (Data Cleaning -> Hypothesis -> Preprocessing
   -> Feature Engineering -> Model Training). The first split-shaped operation the paper
   describes is "$k$-fold cross-validation" inside the *Model Training* Subagent (§2.5) — four
   stages downstream of the imputation.
2. **Statistical test directly on the target, pre-split** (§2.2 + Table 1, verbatim code):
   `contingency_table = pd.crosstab(active_member, dataset['Exited'])` then
   `chi2, p, _, _ = chi2_contingency(contingency_table)` — `Exited` is the paper's own declared
   churn target (confirmed by §4's case study, "identifying customer churn drivers"). This is
   the literal REQ-P11.1-02 trigger, taken from the paper rather than invented.
3. **`.fit_transform` on the full frame, not a training frame** (§2.3 + Table 2, verbatim code):
   `data['normalized_Balance'] = min_max_scaler.fit_transform(data[['Balance']])`,
   `data['standardized_Age'] = scaler.fit_transform(data['Age'])` — `data` is the full dataframe
   at this pipeline stage, never `X_train`. This is REQ-P11.1-01's second clause.
4. **Large-roster model selection with no declared ledger** (§2.5 + Table 4): "the Subagent
   includes a broad set of supervised learning algorithms" — 18 regression + 18 classification
   candidates enumerated by name — "Models are selected based on the dataset's characteristics,"
   evaluated by k-fold CV, hyperparameters "tuned through grid or random search," and the best
   "combined into a single ensemble" (stacking/voting). No `candidates_evaluated`,
   `configurations_tried`, or `selected_on` concept exists anywhere in the paper's own
   description — this is REQ-P11.1-06's trigger and REQ-P11.1-08's "large-roster heuristic"
   referent (18-candidate rosters, searched via grid/random search, feeding an ensemble
   selection, is exactly the shape Cawley & Talbot (2010) and Varma & Simon (2006) warn produces
   optimistic bias when the selection and the final evaluation share the same held-out data).
5. **Discretisation-is-information-loss note** (§2.3, prose, not code): the paper explicitly
   states that Age was deliberately kept continuous ("cleanly scaled and retained, rather than
   grouped into broad categories like 18 to 30 or 31 to 50") *because* the Hypothesis Subagent
   found a strong numeric relationship, and that "binning might have been acceptable ... if no
   significant numerical relationship had been found." Table 2 elsewhere shows the binning idiom
   itself in active use (`bucketed_Age` via `pd.cut`). This is the exact "discretisation is
   information loss" phenomenon REQ-P11.1-08 asks to be noted: binning is applied *contingent on
   a full-frame (pre-split) hypothesis test result*, compounding leakage type 1 (target-adjacent
   feature) with leakage type 3 (preprocessing) in one step — the ensemble sub-case's
   "type 3, cross-ref from 7" note in the requirement text: type 3 is "Preprocessing leakage"
   and type 7 is "Test-set contamination through iteration" (both defined in
   `references/leakage-taxonomy.md`, read in full) — the large model roster searched via
   grid/random search across candidates, then ensembled, is simultaneously a preprocessing
   decision point (feature/model selection surface) and an iterative test-set-informed selection
   process.

**Recommendation:** name the fixture pair to match the requirement's own phrase — e.g.
`examples/known-bad/full-frame-cleaning-ANALYSIS-SPEC.yaml` /
`-POSTMORTEM.md` / an accompanying entrypoint file — and build the entrypoint from items 1-3
above nearly verbatim (adapted variable names as needed), with `model.algorithm` and no
selection ledger to trip REQ-P11.1-06, and `validity_frame`/`inference` blocks cloned from an
existing good fixture per the established "full-shape clone" pattern (`06-08` decision, STATE.md
line 143) so only the target defect fires, not unrelated `DSX-SPEC-08*` noise.

## Training-Frame Name Lexicon (Open Item — proposed, not locked)

lexicon, surveyed from (a) this repo's own existing single-literal precedent (`X_train` in

Design considerations for whichever list is locked at plan/discuss:

- **Case sensitivity:** existing `code.py` markers are case-sensitive except `SCALER_FULL_RE`
  (`(?i)`) — recommend case-sensitive matching for the training-frame lexicon, since Python
  identifiers are case-sensitive and a case-insensitive match risks false-negatives on unrelated
  identifiers that happen to share letters.
- **Suffix tolerance:** real code frequently chains (`X_train_scaled`, `X_train.values`,
  `X_train[cols]`). A prefix-match (`^X_train\b` allowing a following `.`, `[`, `_scaled`, etc.)
  is more robust than exact-token match; recommend `re.match(r"(?:" + "|".join(lexicon) + r")\b")`
  against the extracted first-argument token, not full equality.
- **Scope boundary:** do not attempt to resolve aliasing (`train = df[mask]; train.fit(...)`) —
  that requires real AST/data-flow analysis, explicitly out of scope per "Alternatives
  Considered" above. The lexicon is a **name-based heuristic**, with the same accepted
  false-negative rate as every other `code.py` check (documented project-wide limitation: "a
  frame that lies passes").
- **Where it lives:** as a plain tuple/frozenset constant in `dsx/checks/code.py`, following
  `SPLIT_MARKERS`'s pattern — **not** a `dsx/spec.py` closed vocabulary (see "Don't Hand-Roll"
  above; the spec never declares this name, the code does).

## D-06 Numbering Precedent (how prior phases assigned codes)

Direct read of `references/finding-codes.md` (231 codes, generated from source) and
`scripts/gen-finding-catalogue.py::extract`/`PREFIX_GROUPS` establishes the mechanical pattern
every prior phase has followed:

1. **One prefix per family** (`DSX-CODE-`, `DSX-ML-`, `DSX-VAL-`, ...), registered in
   `PREFIX_GROUPS` (already covers `DSX-CODE`/`DSX-ML` — no new prefix-group entry is needed for
   this phase).
2. **Codes are grouped in "decades"** — a new *logical check group* inside a family starts at
   the next unused multiple-of-10 (or nearby round number), and closely related sub-checks
   within that group increment by 1. Evidence, read directly from `finding-codes.md`:
   - `DSX-ML-*`: 001 (no model block) / 010-015 (split group) / 020-022 (preprocessing group) /
     030-033 (features group) / 040-042 (metric-choice group) / 050-051 (baseline group) /
     060-061 (overfit group) / 070-072 (test-hygiene group) / 080 (calibration group, currently
     one code). **Next free decade: 081-089** (calibration group has room), or **090+** for a
     wholly new group (e.g. selection ledger).
   - `DSX-CODE-*`: 001-003 (fit-before-split group) / 010 (split-marker-absent, standalone).
     **Next free decade: 004-009** (extends the existing group) or **020+** for a new logical
     group (e.g. fit-after-split-wrong-frame, or statistical-test-sees-target).
3. **Codes are never renumbered** (`finding-codes.md`'s own header: "Codes are never renumbered,
   so a suppression or a reference in a review stays valid across versions") — this is why D-06
   ("final numeric code assignments... makes numbering irreversible") is called out as a locked,
   discuss-time decision in every phase's Open Items, not a planner's free choice to revisit
   later.
4. **Severity is assigned per-finding, not per-decade** — e.g. `DSX-ML-051` (baseline not beaten)
   is CRITICAL while `DSX-ML-050` (baseline not declared) is HIGH, both in the same decade.
5. Prior phases' own D-06 resolution pattern (Phase 10's discuss, `STATE.md` line 71): codes were
   assigned in review at discuss, with an explicit design note for *why* one code was "deliberately
   unspent" (`DSX-PRE-011`) — i.e., gaps in the numeric sequence are an accepted, intentional
   pattern when semantics warrant it (e.g. reserving a slot, or an exit-2 case that carries no
   code at all).

## Open Questions

1. **Exact severities for REQ-P11.1-02, REQ-P11.1-05's advisory clause, and REQ-P11.1-06's
   ledger-absent case**
   - What we know: REQ-P11.1-03's two severities (CRITICAL/HIGH) and REQ-P11.1-06's two
     severities (CRITICAL/HIGH) are stated explicitly in REQUIREMENTS.md; several others are not.
   - What's unclear: whether "advisory" (REQ-P11.1-05) maps to MEDIUM or LOW in this project's
     four-tier ladder, and what severity an absent selection ledger gets when an algorithm is
     merely declared (as opposed to the two explicitly-severed sub-cases).
   - Recommendation: resolve at plan time by analogy — "advisory" without further qualification
     in this codebase's own vocabulary (`references/finding-codes.md`'s severity ladder: "LOW —
     presentation and hygiene") most often maps to MEDIUM ("a real defect that should be stated
     as a limitation if not fixed") rather than LOW; a fold-spread-vs-margin comparison is closer
     to a real defect than a hygiene issue.

2. **Whether `DSX-CODE-*` needs `model.target` threaded into `code.check()`'s signature**
   - What we know: `code.check(spec, phase_dir)` today reads `reproducibility.entrypoint` and
     a boolean `has_model` — it does not currently read `model.get("target")`.
   - What's unclear: whether the planner prefers passing the resolved target string into
     `code.check()`, or having `code.check()` re-derive it via `section(spec, "model").get("target")`
     internally (avoiding a signature change, consistent with how `has_model` is already derived
     internally).
   - Recommendation: derive internally (`section(spec, "model").get("target")`) — avoids a
     signature change to `code.check()` that `dsx/cli.py::run_checks`'s `elif name == "code":`
     call site would otherwise need updating too.

3. **Whether the discretisation-is-information-loss note becomes a new finding code or stays
   documentation-only**
   - What we know: REQ-P11.1-08's wording ("discretisation-is-information-loss note") reads as
     documentation, not a gate check — contrasted with the rest of the requirement, which names
     concrete code/agent changes.
   - What's unclear: whether "note" means a `references/leakage-taxonomy.md` prose addition only,
     or also a docstring/finding-text addition somewhere a `DSX-CODE-*`/`DSX-ML-*` check already
     fires (e.g. appended to the full-frame-cleaning finding's `detail` text when a `pd.cut`/
     `pd.qcut` idiom is also present).
   - Recommendation: treat as documentation-only (leakage-taxonomy.md + agent prompt) unless
     plan-time review finds a concrete gate-checkable trigger — the requirement's own phrasing
     groups it with "the ensemble sub-case" (also prose/fixture-level, not code-level) rather than
     with the requirement's code-level bullets.
