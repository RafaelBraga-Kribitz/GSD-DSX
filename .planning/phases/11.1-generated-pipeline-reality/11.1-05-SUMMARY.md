# Phase 11.1 Plan 05: Per-Step Cleaning Boundary Declaration (DSX-ML-023/024) Summary

**Added an optional `data[].cleaning[].fit_on` declaration so a specification can state where each cleaning step's statistics were fitted; a step fitted outside training rows draws DSX-ML-023 at CRITICAL, and a declaration that contradicts an already-honest whole-pipeline boundary of training rows only additionally draws DSX-ML-024 at HIGH — with one shared `TRAIN_ONLY_FIT_VALUES` constant so the two boundary checks (whole-pipeline and per-step) can never disagree about what counts as training rows only.**

## Accomplishments

- `TRAIN_ONLY_FIT_VALUES = frozenset({"train_only", "train_fold_only", "none"})` extracted from `_check_preprocessing`'s inline tuple into a module-level constant in `dsx/checks/ml.py`; `_check_preprocessing`'s own membership test now reads `fit_on not in TRAIN_ONLY_FIT_VALUES` with no other change, proven behaviour-identical by its pre-existing, unmodified test suite still passing.
- `_check_cleaning(spec, report)` added: reads `data[]` via the standard `items()` list-section accessor (skips malformed dataset entries), and for each dataset's `cleaning` list (skipped unless a list; non-mapping elements skipped) reads `column`, `method` and `fit_on`. A blank or absent `fit_on` is a silent skip — documented in a code comment as deliberate, so an incomplete declaration is never punished harder than no declaration at all.
- `DSX-ML-023` (CRITICAL) fires per leaky step, naming the dataset, the column, the method if declared, and the declared boundary verbatim. `DSX-ML-024` (HIGH) fires at most once per report, when `model.preprocessing_fit_on` normalises to a member of `TRAIN_ONLY_FIT_VALUES` while any cleaning step's boundary does not — verified directly with two leaky steps across two datasets producing two `DSX-ML-023` findings and exactly one `DSX-ML-024`.
- `_check_cleaning` is called from `check()`'s dispatch *before* the no-model early return, so a data-only specification (no `model:` block at all) that declares a leaky cleaning step still produces `DSX-ML-023`.
- `_check_cleaning`'s docstring (shared by both codes, since both `report.add` calls live in the same function) carries the Kaufman, Rosset, Perlich & Stitelman (2012) "Leakage in Data Mining" citation and a structural-criterion paragraph naming both codes as membership/agreement tests against `TRAIN_ONLY_FIT_VALUES`; the exact section/page locator for the paper's attribute-legitimacy formulation is marked UNVERIFIED rather than invented, per D-05.
- A deterministic decision record (`layer="deterministic"`) is appended once per report whenever any cleaning step is declared at all, covering the fired/contradicted/cleared outcomes — mirrors `_check_metric_choice`'s precedent from plan 11.1-04 that a cleared judgment is still a recorded judgment.
- `templates/ANALYSIS-SPEC.yaml` gained a commented-out cleaning scaffold inside the dataset entry (column/method/fit_on, with the three accepted `fit_on` values inline-commented in the same convention `validity_frame.dependence.structure` uses), plus a sentence stating the block is optional and firing nothing when absent. Confirmed by reading `dsx/spec.py` that neither `REQUIRED_TOP_LEVEL` nor `_VALIDITY_FRAME_ALWAYS_REQUIRED`/`_VALIDITY_FRAME_CAUSAL_REQUIRED` reference `cleaning` or `data` at all — no required-fields list needed a change. `dsx gate plan` against the template still exits 0.

## Decisions Made

- Read `_check_preprocessing`'s three literal `fit_on` values directly from its source (not retyped from memory) before defining `TRAIN_ONLY_FIT_VALUES`, then replaced the inline tuple with the constant — `_check_preprocessing`'s existing, unmodified test suite is the proof the substitution changed nothing about its behaviour.
- Placed `_check_cleaning`'s call site before `check()`'s no-model early return (not inside the post-model dispatch block with the other `_check_*` calls) — the requirement is explicit that a data-only specification with a leaky cleaning step still blocks, and the early return exists specifically to skip model-dependent checks, not data-dependent ones.
- Chose to skip (not flag) a blank or absent `fit_on`, documented inline as deliberate: the alternative — treating an incomplete declaration as automatically leaky — would punish an operator who declared `column`/`method` but left `fit_on` unset harder than one who declared nothing at all, which is the opposite of what an optional field is meant to encourage.
- Emitted `DSX-ML-024` at most once per report even when multiple cleaning steps are leaky, naming all leaky dataset/column pairs in one `detail` string — the code exists to flag the two-declaration contradiction itself, not to duplicate the per-step signal `DSX-ML-023` already carries once per step.
- Appended the `_check_cleaning` decision record for every call where at least one cleaning step is declared (including an all-blank declaration, which reads as "cleared"), following plan 11.1-04's precedent that a cleared or not-applicable judgment is still worth recording.
