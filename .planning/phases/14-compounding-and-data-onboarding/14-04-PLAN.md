<objective>
Give a CSV-first conversation a start as simple as a data-analysis assistant, without knowing GSD
phase names and without a `data_storage/` special folder (REQ-P14-04 / D-05), and resolve the
REQ-P14-05 file-drop-hook fork to the documented-skip branch, honestly (REQ-P14-05 / D-06). This is
the sole wave-2 plan: it is the single writer of every DSX skill's `description` frontmatter after
wave 1's body edits land, which is how the overlap on the three shared skill files
(dsx-scope-analysis, dsx-explore-data, dsx-narrate) is avoided.

Purpose (REQ-P14-04): the portable, `supported:["*"]`-compatible mechanism is a documented alias
convention — a canonical alias table in the operating guide plus CSV-first trigger phrases in each
DSX skill's `description` — so intent routes to the right skill on any host that reads skill
descriptions. Host-native `.claude/commands/*.md` shims are optional Claude-Code-only sugar, never the
sole path. A `capability.json` `aliases` key is rejected: not grounded in the installed GSD Core
schema, and the repo's Tool Version Grounding rule forbids a key that may silently no-op. The alias
takes the CSV as an argument, so no `data_storage/` folder is needed.

Purpose (REQ-P14-05): the file-drop-hook fork was decided against the installed GSD Core — binding
`FileChanged` breaks `supported:["*"]` (silent no-op on non-Claude-Code runtimes, uncaught), rests on
unverified host behaviour, and re-introduces the watched folder REQ-P14-04 rejects. So the documented
skip is the rigorous branch, made honest by naming `DSX-DQ-001` as the compensating control and
stating the four D-06 claims in the operating guide. `capability.json` `hooks` stays `[]`.

Output: the alias table + "why no file-drop hook" subsection in `docs/operating-guide.md`, CSV-first
`description` triggers on all 13 DSX skills, and two optional `.claude/commands/*.md` shims.
</objective>
