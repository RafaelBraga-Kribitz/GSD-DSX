## Critical Issues

### CR-01: Purpose-gate marker `"to"` matches every infinitive, firing DSX-CLM-011/DSX-COH-010 CRITICAL on ordinary non-recommendation prose

**File:** `dsx/spec.py:104` (`_PURPOSE_MARKERS`), `dsx/spec.py:116-122` (`_CAUSAL_VERBS_PURPOSE_GATE_RE`), consumed at `dsx/checks/claims.py:107-141` and `dsx/checks/coherence.py:93-111`

**Issue:** The purpose-gated tier is documented (spec.py:78-82, 103) to fire "only inside a purpose/recommendation construction (`to reduce churn`, `in order to increase…`)". But `_PURPOSE_MARKERS` includes the bare token `"to"`, and the compiled pattern is `\b(?:to|…)\b[\s\w]{0,30}?\breduce\b`. `"to"` introduces *every* English infinitive, not only purpose clauses, so the gate fires on raising/complement/negated infinitives that assert nothing causal.

Reproductions (all produce exactly one **DSX-CLM-011 CRITICAL** — trace: `causal_verb_matches` returns `["increase"]`/`["reduce"]`, `_check_causal_language` sees `ctype != "causal"` and no `HEDGE_TERMS`, so it falls through to the `report.add("DSX-CLM-011","CRITICAL",…)` at claims.py:127):

- `{"text": "Enterprise usage tends to increase after onboarding", "type": "association"}` — a valid associational claim → blocked CRITICAL.
- `{"text": "The pilot failed to reduce error rate", "type": "descriptive"}` — states the *opposite* of a causal effect → blocked CRITICAL.
- Decision-rule path: a `descriptive` question with `decision.decision_rule = "continue to increase sampling frequency"` fires **DSX-COH-010 CRITICAL** via the same shared matcher (coherence.py:94).

Because `claims`/`coherence` run at verify and ship (threshold HIGH), each of these blocks a legitimate spec, and every one of them is exactly the false-positive class Phase 12's FP-rate measures. The existing negative test only covers the *bare-noun* case (`"sales increase in Q4"`, `test_causal_verb_tiers.py:110`); no test exercises `"to <verb>"` in a non-purpose infinitive, so the over-match is unguarded.

**Fix:** Drop bare `"to"` from `_PURPOSE_MARKERS` and keep only unambiguous recommendation heads, or require a recommendation head token before the infinitive. A minimal, test-preserving change (still matches "…to reduce churn" when preceded by a recommendation verb, drops "tends to increase"):

```python
# dsx/spec.py — replace bare "to" with recommendation-anchored purpose heads
_PURPOSE_MARKERS = ("in order to", "so as to", "aimed at", "designed to")
_RECOMMENDATION_HEADS = ("recommend", "should", "offer", "roll out", "launch",
                         "introduce", "in order to", "so as to")
# purpose-gated pattern: a recommendation head, then within the bounded window, "to <verb>"
_CAUSAL_VERBS_PURPOSE_GATE_RE = {
    verb: re.compile(
        rf"\b(?:{'|'.join(re.escape(m) for m in _RECOMMENDATION_HEADS)})\b"
        rf"{_PURPOSE_GATE_WINDOW}\bto\s+{re.escape(verb)}\b"
        rf"|\b(?:{'|'.join(re.escape(m) for m in _PURPOSE_MARKERS)})\b"
        rf"{_PURPOSE_GATE_WINDOW}\b{re.escape(verb)}\b"
    )
    for verb in CAUSAL_VERBS_PURPOSE_GATED
}
```

Then add the two negative cases above as pinned tests. Note the known-bad fixture ("…**to reduce** churn", preceded by "Offer bundled incentives") still matches via the `offer`/recommendation head, so `test_known_bad_corpus.py` stays green.

## Warnings

### WR-01: DSX-CLM-011 is identification-blind and mis-messaged for prescriptive claims, so a well-identified prescriptive recommendation fires CRITICAL against the DSX-CLM-020/021 clean path

**File:** `dsx/checks/claims.py:104-141` (specifically the exemption at line 111, `if ctype == "causal": return`)

**Issue:** `_check_causal_support` (claims.py:151) was widened this phase to treat `prescriptive` as a causal superset (D-03) and route it to DSX-CLM-020/021, which has an explicit clean path (`report.ok`, claims.py:234-235) for a prescriptive claim backed by strong identification. But `_check_causal_language`'s early-return exempts only `ctype == "causal"`, not `prescriptive`. Consequences:

1. **Contradiction / false positive.** A prescriptive claim with strong identification clears DSX-CLM-020/021 but is still blocked by DSX-CLM-011 CRITICAL the moment its text names its effect with a lexicon verb. Repro: `{"question_type":"prescriptive", "claims":[{"text":"Roll out the redesign to reduce churn","type":"prescriptive","identification":"randomized_experiment","evidence":"R.md#1"}]}` → DSX-CLM-020/021 clear, **DSX-CLM-011 CRITICAL fires** (via "to reduce"). The two checks disagree about whether a well-identified prescriptive claim is acceptable.
2. **Incoherent message.** DSX-CLM-011's title says the claim "asserts causation while the spec does not classify it as a causal claim" — false; it *is* classified (prescriptive, a rung above causal). Its remedy ("retype the claim as causal…") tells the operator to **downgrade** a prescriptive claim, which is nonsensical.

This is in genuine tension with an *intended* behaviour: `test_known_bad_corpus.py:234-235` hard-codes `DSX-CLM-011` as an expected catch on the (identification-less) prescriptive fixture. So firing on prescriptive is deliberate — but it was only ever exercised against a claim that is *also* DSX-CLM-020-bad, so the false positive on a *well-identified* prescriptive claim was never surfaced. Flagging so the author can adjudicate: as written, no natural prescriptive recommendation that states its effect can pass.

**Fix:** Decide the contract explicitly. Either (a) exempt prescriptive like causal — `if ctype in {"causal", "prescriptive"}: return` at claims.py:111, relying on DSX-CLM-020/021 for the identification gate and DSX-COH-001 for the ceiling (then update `_TARGET_DEFECT_CODES["prescriptive-churn-recommendation"]` to `{DSX-CLM-020}` and the fixture header/POSTMORTEM prose); or (b) keep firing on prescriptive but rewrite DSX-CLM-011's title/remedy with a prescriptive-specific branch (as DSX-CLM-020/021 already do) so it no longer tells the operator to downgrade, and make it identification-aware so a strongly-identified prescriptive claim does not fire.

### WR-02: DSX-COH-040's discriminator is satisfied by the time-window's own digits, so a metric-less/threshold-less revisit trigger clears a check whose message demands both

**File:** `dsx/spec.py:579-589` (`falsifier_is_discriminating`), `dsx/spec.py:627-639` (`revisit_when_is_discriminating`), fired at `dsx/checks/coherence.py:175-194`

**Issue:** `revisit_when_is_discriminating(x) = falsifier_is_discriminating(x) AND _has_window_token(x)`. `falsifier_is_discriminating` returns True on *any* numeric via `_FALSIFIER_NUMBER_RE = \d+(?:\.\d+)?\s*(?:%|pp)?` (spec.py:561, 589). Every date window (`2026-Q4` → matches "2026") and every duration window (`30 days` → matches "30") therefore satisfies the numeric half *by themselves*. So a revisit trigger that names **no metric and no threshold** clears DSX-COH-040:

- `revisit_when: "revisit at the 2026-Q4 review"` → `falsifier_is_discriminating` True (digits "2026"), `_has_window_token` True (date) → **passes**, no DSX-COH-040.
- `revisit_when: "reassess in 30 days"` → passes (this one is even asserted as accepted, `test_revisit_when.py:58`).

Yet DSX-COH-040's own detail and remedy state it needs "a named metric, a threshold, and a time anchor" (coherence.py:183-192). The gate is materially weaker than its message promises: any bare date/duration defeats the discriminator requirement — a false-negative surface on a CRITICAL check, exactly the catch-rate direction Phase 12 measures. It is also internally inconsistent: a recurring-token window (`_WINDOW_RECURRING_TOKENS`, spec.py:607-610) carries no digit, so a recurring-review-only trigger ("revisit at the quarterly review") *fails* the numeric half and correctly fires DSX-COH-040, while the digit-bearing date/duration equivalents pass.

**Fix:** Require the discriminating token/number to be *distinct from* the window match, or tighten the message. Concretely, strip the window match before testing the discriminator, so the year/duration digits cannot double as the threshold:

```python
def revisit_when_is_discriminating(value: Any) -> bool:
    text = str(value)
    if not _has_window_token(text):
        return False
    # Remove the window span(s) before checking for an independent metric/threshold,
    # so a bare date/duration cannot satisfy the numeric discriminator by itself.
    stripped = _WINDOW_DATE_RE.sub(" ", text)
    stripped = _WINDOW_DURATION_RE.sub(" ", stripped)
    return falsifier_is_discriminating(stripped)
```

If accepting bare time-only triggers ("reassess in 30 days") is genuinely intended (per `test_revisit_when.py:58`), then instead reword DSX-COH-040's detail/remedy so it no longer claims a metric and threshold are required — the current message is a promise the code does not keep.

**Fix:** If both phrasings should be documented, extend the generator to keep per-branch titles for a code; otherwise make the two sites share one parameter-free title and carry the claim-type distinction in `detail` only.
