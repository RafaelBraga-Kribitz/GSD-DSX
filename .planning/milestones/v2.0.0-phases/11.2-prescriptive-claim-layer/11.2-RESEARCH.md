## The three hard landmines (research_focus §2)

### (a) D-02 ordering precondition — verified mechanism, not just verified claim

Traced the exact failure path CONTEXT.md describes, end to end in source:

1. A claim declares `type: prescriptive`.
2. `dsx/spec.py::_validate_claims_shape` (`:824-852`) normalizes the type and checks
   membership in `CLAIM_TYPES` (`:833,843`). Since `CLAIM_TYPES` today is
   `{"descriptive", "association", "predictive", "causal"}` (`:50`), the check hits the
   `elif ctype not in CLAIM_TYPES:` branch (`:843`) and fires `DSX-SPEC-062` HIGH,
   "unrecognised type" (`:844-851`), quoting the stale remedy "Use one of the four claim
   types." (`:849`).
3. Separately, `dsx/checks/coherence.py::_check_claim_ceiling` (`:55-80`) normalizes the
   same claim's type and checks membership in `CLAIM_STRENGTH` (`:61`). Since
   `CLAIM_STRENGTH` today is `{descriptive:0, association:1, predictive:2, causal:3}`
   (`:31-36`, `prescriptive` absent), it hits `if ctype not in CLAIM_STRENGTH: continue`
   (`:61-62`) — the claim is **silently skipped**, no `DSX-COH-001` finding at all, even
   if the claim strength genuinely exceeds the question strength.
4. Net effect if only REQ-02 (identification-strength enforcement) ships without REQ-01's
   vocabulary edit landing in the same slice: a prescriptive claim fires ONE HIGH finding
   (`DSX-SPEC-062`, a structural "you spelled the type wrong" complaint) but ZERO CRITICAL
   coherence-ladder finding — exactly the silent pass this gate exists to prevent, because
   an operator who suppresses or ignores the HIGH "unrecognised type" finding (a
   plausible action — it looks like a typo warning, not a ladder violation) walks away
   with a gate-passing prescriptive claim that was never held to any strength ceiling.

**Guard for the planner:** the plan slice that adds `prescriptive` to `CLAIM_TYPES`
(`spec.py:50`) MUST, in the same slice/commit: (i) add `"prescriptive": 4` to
`CLAIM_STRENGTH` (`coherence.py:31-36`); (ii) update both remedy strings at `spec.py:840`
(`"...descriptive, association, predictive, causal, or prescriptive."`) and `:849`
(`"Use one of the five claim types."`). A plan that ships (i) without (ii), or vice
versa, still leaves a `DSX-SPEC-06x` message quoting a stale count even though the
silent-pass hazard itself is closed — cosmetic but worth catching at plan-check.

### (b) D-07 falsifier-sharing hazard — verified both callers and the good-fixture collision

Confirmed both call sites of `falsifier_is_discriminating()`:
- `dsx/frame/val.py:236` inside `_check_estimand_completeness`/falsifiability wiring —
  computes `discriminating` for the manifest's decision-record `choice` string.
- `dsx/frame/val.py:637` inside `_check_estimand_falsifiability` itself, which fires
  `DSX-VAL-011` when the predicate is `False` (docstring cites Popper 1959/2002, Part I
  Ch.1 §6).

Confirmed the good fixture's estimand falsifier (`examples/good-ANALYSIS-SPEC.yaml:303`)
reads exactly: `"95% CI on the activation uplift includes zero, or its lower bound sits
below +1.0pp"` — a comparison predicate (`includes zero`, matches
`FALSIFIER_DISCRIMINATORS`) with **no duration, date, or recurring-event token
anywhere in the string**. If `falsifier_is_discriminating()` itself were extended to
require a window clause, this exact fixture would newly fire `DSX-VAL-011` at
`val.py:637` — a shipped-firing-set regression on the canonical good fixture, which
violates this phase's own D-06 corpus-green constraint and Phase 6's binding "good
fixture passes every gate" invariant (`REQ-P1-11`/`REQ-P6-12`).

**Guard for the planner:** implement `revisit_when_is_discriminating(x)` as a NEW
function in `dsx/spec.py` (sibling to, not inside, `falsifier_is_discriminating`) that:
(1) calls the existing `falsifier_is_discriminating(x)` for the core comparison-or-numeric
test, unchanged; (2) additionally requires a window token match (duration/date/recurring
event) via a new, separate regex/token set. Do not touch `falsifier_is_discriminating`'s
body, signature, or the `FALSIFIER_DISCRIMINATORS` tuple it reads. This keeps both
`val.py:236` and `val.py:637` byte-for-byte unaffected.

## Landmines beyond the three named ones — new findings from this research pass

### (d) `InvocationHeader` dataclass field-ordering hazard (D-08 implementation risk)

`InvocationHeader` is a `@dataclass(frozen=True)` with four required fields, no
defaults (`decisions.py:91-108`: `invocation_id`, `gate_point`, `dsx_version`,
`frame_digest`). Grep confirms 9 distinct construction sites across the tree:
`dsx/cli.py:374` (the real writer), `tests/_trail_seed.py:47`, and 7 sites across
`tests/test_frame_prereg.py`, `tests/test_dsx.py`, `tests/test_decisions.py`. All use
keyword arguments exclusively; none pass a `spec_id`.

**Guard for the planner:** `spec_id` MUST be added as a defaulted field
(`spec_id: "str | None" = None`), and — because Python dataclasses require all
non-default fields to precede all default fields — it must be added AFTER
`frame_digest`, not interleaved. Adding it as a required (no-default) field, or
inserting it before `frame_digest`, breaks all 9 existing construction sites at import
time (a `TypeError` on dataclass definition itself for the ordering case, or a
missing-argument `TypeError` at every one of the 9 call sites for the no-default case).
This is not stated in CONTEXT.md and should be called out explicitly in the plan task
that touches `decisions.py`.

### (e) `RECORD_TYPES` is decorative, not enforced — D-10's new record type needs a real dataclass

`RECORD_TYPES = {"invocation", "decision"}` (`decisions.py:61`) reads as a closed
vocabulary, but grep confirms nothing in the codebase actually validates a record's
`record_type` field against this set at write or read time. `DecisionRecord.to_dict()`
(`:85-88`) and `InvocationHeader.to_dict()` (`:105-108`) each hardcode their own literal
string (`"decision"` / `"invocation"`) — `RECORD_TYPES` is documentation, not a runtime
guard.

**Guard for the planner:** D-10's new `record_type: "amendment"` entry needs either (i) a
new frozen dataclass (e.g. `AmendmentRecord`) with its own `to_dict()` hardcoding
`"amendment"`, mirroring the existing two classes' pattern exactly, or (ii) a documented,
deliberate exception if the plan instead reuses `DecisionRecord` with a sentinel
`choice`/`layer` value (NOT recommended — D-10 explicitly wants a distinct record shape
carrying `spec_id`, `prev_frame_digest`, `new_frame_digest`, `reason`, none of which fit
`DecisionRecord`'s existing field set cleanly). Also update `RECORD_TYPES` to
`{"invocation", "decision", "amendment"}` for documentation accuracy even though nothing
currently enforces it — a future reader trusts that set as authoritative.

### (f) The committed `examples/known-bad/DECISIONS.jsonl` fixture is already 5,633 lines / 4.8MB

This file accumulates one invocation header + N decision records per historical
`dsx gate` test run against that fixture directory, and nothing resets it —
`next_invocation_id()` (`decisions.py:164-184`) counts existing records to derive the
next ID, so this file has been growing across every phase's test suite runs to date.

**Guard for the planner:** any new test asserting D-09's amendment-counter/distinct-
`frame_digest` behaviour, or D-08's `spec_id` fail-closed behaviour, MUST use an isolated
`tempfile.TemporaryDirectory()` per test (the pattern already established in
`tests/_trail_seed.py::seed_plan_header`, confirmed present and documented in
`10-04-SUMMARY.md`), never assert against the shared, already-bloated
`examples/known-bad/DECISIONS.jsonl`. Asserting against the shared file would (a) be
slow to parse at 4.8MB, (b) inherit years of prior invocation headers with unpredictable
`frame_digest`/`spec_id` values, making a clean "exactly N distinct digests" assertion
impossible without filtering logic the plan would then have to write and maintain.
