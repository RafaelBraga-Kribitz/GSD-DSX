<objective>
Read the plan-time content lock and reconcile it against the verify-time bytes.

Purpose: REQ-P10-02 and ROADMAP Success Criterion 4 require that where a content lock over
`validity_frame:` plus `inference:` is captured at plan, reconciliation compares the recorded bytes
rather than the declared string. That lock already ships — `frame_digest()` in `dsx/decisions.py` is
written on every gate run. Phase 10 reads it. This plan builds the read side and the two behaviours
that hang off it, while `prereg` is still unregistered and therefore still has no blast radius.

Output: `_check_content_lock`, the `DSX-PRE-020` finding, and the missing-header exit-2 that keeps the
grandfather path walkable.
</objective>

## Settled decision: which recorded header the digest is compared against

CONTEXT leaves "most recent or earliest plan header" to the planner's discretion and asks for the
choice to be stated rather than left implicit. The answer taken here is **neither** — the comparison
is set membership over every recorded plan-gate-point digest, asking "was this exact frame content
ever registered at plan?" rather than "what was the last thing registered?".

The reason is a property of the record shape, verified by direct read rather than inferred:
`InvocationHeader` (`dsx/decisions.py:91-104`) carries `invocation_id`, `gate_point`, `dsx_version`
and `frame_digest`, and **no spec identity of any kind**. A single trail file therefore accumulates
headers from every spec ever gated with that root. `scripts/check.sh` lines 15-23 gate the good
fixture and then the bad fixture at each point in turn against the same `examples/` root, so under a
most-recent rule the good fixture's `verify` would compare against the bad fixture's plan digest and
`DSX-PRE-020` would fire on a spec that did nothing wrong — breaking the suite entrypoint's
good-spec-passes-everywhere assertion. Under an earliest rule the comparison pins to whatever
historical header happens to sit at the top of a long-lived local file.

Set membership dissolves both problems without adding a spec-identity field to a shipped record
shape. Its residual limit is the same one the most-recent rule has and is documented rather than
pretended away in plan 06: an operator who re-runs `dsx gate plan` after seeing results can register
the edited frame and clear the check. That is the same honesty this project already gives
`declared_at: post_data`.
