## Warnings

### WR-01: DSX-CRV-011 matches the literal placeholder `X/10`, not real 10-point scores

**File:** `dsx/checks/chart_review.py:26,163`
**Issue:** `FORBIDDEN_SCALE_SUBSTRING = "X/10"` and the check is `if FORBIDDEN_SCALE_SUBSTRING
not in text`. A *real* violation of the mandated 1–4 scale reads `8/10`, `7/10`, `visual: 9/10`
— none of which contain the literal substring `X/10`. The only input that fires DSX-CRV-011 is
one that copies the schema's placeholder verbatim (which is exactly, and only, what the
`ten-point-scale` fixture does: `CHART-REVIEW.md:56` literally writes `X/10`). A genuinely-bad
report using actual numeric 10-point scores passes silently — the highest-severity class this
phase names.
**Reproduction:** a CHART-REVIEW.md whose Overall Scores table reads
`| Visualization Quality | 8/10 | ... |` → `check()` emits no DSX-CRV-011 (fixture flip:
change `X/10` → `8/10` in `tests/fixtures/chart-review/ten-point-scale/CHART-REVIEW.md` and the
finding disappears).
**Caveat — not an implementation deviation:** the schema's own Orchestrator-validation rule is
literally "No substring `X/10`" (`references/chart-review-schema.md:102`) and D-13 lists "the
absence of `X/10`" as the allowed structural input, so the code *faithfully* implements the
settled criterion. I am flagging the resulting catch-rate gap so Phase 12 is not surprised, not
relitigating the code choice.
**Fix (requires amending the settled schema/D-13 criterion, not just the code):** replace the
literal test with a bounded, CRLF-safe scan for an actual out-of-1–4 ten-point score, e.g.
`re.search(r"\b([5-9]|1\d)\s*/\s*10\b", text)` (anchored, no nesting, no backtracking risk),
which catches `5/10`..`19/10` while leaving legitimate `1/10`..`4/10`-free prose alone. Keep the
literal `X/10` fixture as one case and add a numeric-score fixture.

### WR-02: DSX-CRV-013 false-positives on nested evidence sub-bullets

**File:** `dsx/checks/chart_review.py:249-254` (`_untokenised_finding_lines`)
**Issue:** the scan flags *every* line under an Issues heading that starts with `- ` and lacks a
`DSX-`/`UNMAPPED` token (except the literal `- None`). A conformant report that nests an evidence
bullet under a tokenised finding line — a common and schema-legal shape ("Every score needs ≥1
evidence bullet") — trips a spurious DSX-CRV-013 (MEDIUM) on the child bullet.
**Reproduction:**
```
## Critical Issues

- [ANALYTICAL] mislabeled y-axis — DSX-VIZ-010
  - evidence: axis starts at 40, not 0
```
The child line `- evidence: axis starts at 40, not 0` (stripped → starts with `- `, contains no
`DSX-`/`UNMAPPED`) fires DSX-CRV-013 at that line number, even though the finding it belongs to
is properly tokenised on the parent line. On the good fixture this is latent (its findings are
single-line, `examples/good-CHART-REVIEW.md:74,78`) but real `dsx-viz-critic` output with evidence
sub-bullets will false-positive.
**Fix:** only treat a bullet as a *finding* line when it is at the Issues-section base indent
(track the indent of the first bullet after the heading, or require `- [CATEGORY]`), and skip
deeper-indented continuation/evidence bullets. Alternatively restrict the token requirement to
top-level bullets: compute `len(raw_line) - len(raw_line.lstrip())` and only test bullets whose
indent equals the section's first-bullet indent.

### WR-03: DSX-EXP-053 `set(family)` raises TypeError on a non-scalar family (gate-path traceback)

**File:** `dsx/checks/design.py:388`
**Issue:** `absent = sorted(reported - set(family))` assumes every `multiplicity.family` member is
hashable (a metric string). The canonical corpus declares string lists
(`good/bad-ANALYSIS-SPEC.yaml`), but nothing upstream enforces member scalar-ness. If a spec
declares `family` as a list of mappings (or lists), `set(family)` raises
`TypeError: unhashable type: 'dict'` on the gate path — an uncaught exception rather than a
finding. The branch is reachable whenever `isinstance(family, list) and family and len(family) <
len(tests)` (`design.py:386`), i.e. a non-empty unhashable family shorter than the reported tests.
**Reproduction:**
```yaml
design:
  multiplicity:
    family:
      - {metric: churn}       # list of mappings
results:
  tests:
    - {metric: churn}
    - {metric: arpu}
```
`len(family)=1 < len(tests)=2` → enters DSX-EXP-053 → `set([{...}])` → TypeError → check crashes
(exit 2 / traceback) instead of degrading to a finding.
**Fix:** normalize members to hashables before the set op, e.g.
`family_metrics = {m for m in family if isinstance(m, str)}` and `absent = sorted(reported -
family_metrics)`; or guard the branch with
`all(isinstance(m, str) for m in family)`. This also makes the "absent" naming honest when a
family mixes strings and non-strings.

### IN-01: `good-CHART-REVIEW.md` is a production lookup name

**File:** `dsx/checks/chart_review.py:23`
**Issue:** `CHART_REVIEW_NAMES = ("CHART-REVIEW.md", "good-CHART-REVIEW.md")` bakes a fixture/example
filename into the artifact resolver. Harmless today (the schema file at `{phase_dir}/CHART-REVIEW.md`
is the real artifact), but it means a stray `good-CHART-REVIEW.md` sitting in `cwd`/phase_dir would
be picked up and gated in a real run. Recommend restricting production lookup to `CHART-REVIEW.md`
and passing the `good-` variant explicitly in tests.

### IN-02: DSX-STA-012 treats an explicitly-null `effect_size_kind` as unrecognised

**File:** `dsx/checks/stats.py:287`
**Issue:** `normalize(test.get("effect_size_kind", "d"))` returns `"d"` only when the key is
*absent*. If the key is present but null (`effect_size_kind:`), `.get` returns `None` →
`normalize(None) == "none"` → not in `EFFECT_SIZE_KINDS` → DSX-STA-012 fires for kind `'none'`.
Whether that is desired (an explicit-but-empty kind is arguably a real gap) or a mild
false-positive is a judgement call; flagging the asymmetry with the absent-key case for
awareness. If undesired, treat blank/null identically to absent (default to `"d"`).

### IN-03: DSX-EXP-053 fires on a count trail even when the family covers every reported metric

**File:** `dsx/checks/design.py:386-408`
**Issue:** the fire condition is count-based (`len(family) < len(tests)`) while `absent` is a
set difference. When `tests` contains duplicate metrics all present in the family (e.g. family
`[A,B]`, tests report metrics `[A,B,B]`), the check fires HIGH with the "name no metric outside the
family" wording even though the declared family does cover every reported metric. This matches the
settled count semantics of D-01 (`max(len(family), len(tests))`) and the else-branch wording is
graceful, so it is likely intended — noted only so the count-vs-set distinction is a conscious
choice, not an oversight.
