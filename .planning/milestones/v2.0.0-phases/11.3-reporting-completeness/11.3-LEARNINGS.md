# Phase 11.3 Learnings: Reporting Completeness

## Decisions

### DSX-EXP-053 minted; multiplicity family count fixed to max(family, tests)
`_check_multiplicity` previously undercounted `n_tests` when a non-empty family was declared
smaller than `results.tests` (silently letting the family suppress the results-based count).
The fix replaces the undercount with `n_tests = max(len(family), len(tests))` and mints
`DSX-EXP-053` HIGH, which fires when the declared family is non-empty but shorter than the
reported test set, naming the absent metrics (`set(reported metrics) - set(family)`).

**Rationale:** A declared family that is a strict subset of what's actually reported is exactly
the "declare one hypothesis, report five" multiplicity-laundering pattern the check exists to
catch; the old undercount let that pattern buy silence.
**Source:** 11.3-CONTEXT.md (D-01), 11.3-01-PLAN.md, 11.3-01-SUMMARY.md

### DSX-EXP-051 reused and rebased to fire independent of family presence
Rather than minting a new code, REQ-02 reuses `DSX-EXP-051` by dropping the `multiplicity.family`
early-return in `_check_exploratory_looks` and rebasing the comparison base to
`max(len(family), len(tests))`, so `comparisons_looked_at` exceeding that base fires even when no
family is declared at all.

**Rationale:** Reuse doctrine (PROJECT.md M-02/M-09) — one concept, one code; this is the same
"examined more than reported" concept whether or not a family exists, verified verdict-neutral on
the canonical good fixture (max(3,3)=3, looked=3 → no fire).
**Source:** 11.3-CONTEXT.md (D-02), 11.3-01-PLAN.md, 11.3-01-SUMMARY.md

### Missingness-rate reconciliation deferred (Option B) rather than shipped in 11.3
A Statistician-led, Auditor-concurring persona round unanimously deferred reconciling declared
`missingness.rate` against the profile's actual null rates, closing the ROADMAP open item without
shipping a check. `missingness.rate` remains read by no check, as before.

**Rationale:** The concrete defect ("more nulls than declared") is already covered by
`DSX-DQ-030` + `DSX-VAL-060`; under MAR+MI the rate governs efficiency not bias, so there is no
contradiction to flag; no principled tolerance survives (max-column false-positives on the
benign `country` 1.2% null rate; analysis-columns-only is vacuous and un-joinable); and Option A
would force re-baselining the canonical good fixture, "the tell of a mis-specified check." A
four-part entry condition (machine-resolvable column join, checks/dq-layer placement, cited
tolerance, good fixture passes without loosening) gates any future backlog admission.
**Source:** 11.3-CONTEXT.md (D-07), 11.3-DISCUSSION-LOG.md (Decision 1)

### single_imputation under MAR reclassified to CRITICAL via per-method severity split
`_MISSINGNESS_METHOD_VALIDITY`'s MAR deny set, previously one severity per mechanism, was re-keyed
per method: `{complete_case, available_case}` stay HIGH (unchanged), and a new CRITICAL subset
`{single_imputation}` (plus as-if-observed instances) fires a third `DSX-VAL-060` branch that
blocks at plan, carrying its own Rubin (1987) §3.1 citation rather than reusing the White & Carlin
(2010) complete-case citation.

**Rationale:** Single imputation fabricates precision — treating imputed values as observed forces
Rubin's variance-decomposition term `B` to 0, producing anti-conservative CIs/p-values. Complete-case
under MAR only sacrifices power while reporting honest uncertainty and has a documented unbiased
sub-case; single imputation has none. Corrupting calibrated uncertainty in the anti-conservative
direction is the gate's "north-star sin" — a structural defect no downstream evidence rescues.
**Source:** 11.3-CONTEXT.md (D-05, D-06), 11.3-03-PLAN.md, 11.3-03-SUMMARY.md

### validity_frame.exclusions placed under validity_frame, guarded by a new DSX-SPEC-083 closed-key check
The new `exclusions` sub-block (`rule, action, applied_before_split, justification`) was
deliberately placed UNDER `validity_frame` (never top-level) so `frame_digest`'s recursive hash
covers it "for free," and a new closed-key guard (`DSX-SPEC-083` HIGH, `_EXCLUSIONS_ALLOWED_KEYS`)
was minted scoped ONLY to this sub-block, not retrofitted to the legacy tolerant `inference` block.

**Rationale:** A top-level `exclusions` field (like `spec_id`) would sit outside the digest and
escape the content lock. Separately, the existing shape validator silently accepts unknown keys
(honor-system only) — leaving "row counts never in the frame" as a silent no-op would let a
hand-added `n_excluded` count slip in, trip `DSX-PRE-020` on every data refresh, and train
operators to reflexively re-register, eroding the very control REQ-04 relies on.
**Source:** 11.3-CONTEXT.md (D-08, D-09), 11.3-04-PLAN.md, 11.3-04-SUMMARY.md

### New DSX-CRV-* family minted (not DSX-FIG-*) to avoid Gate-D circularity
Chart-review structural conformance got a brand-new prefix (`DSX-CRV-010/011/012/013`) in a new
module `dsx/checks/chart_review.py`, and `references/chart-review-schema.md`'s Gate-proxy table
was edited (D-14) to route `DSX-CRV-*` as a report-acceptance precondition — explicitly NOT folded
into Gate D's `DSX-FIG-*` wildcard.

**Rationale:** The schema's own Gate-D proxy wildcards `DSX-FIG-*` at CRITICAL/HIGH; minting a
`DSX-FIG-*` code for the chart-review report's OWN structural defects would sweep the report into
the very gate it is reporting on (circular, unreliable). Chart-review conformance is
orthogonal-new (report structure ≠ figure byte-seal), so the reuse doctrine does not bar a new
family; only 4 codes were minted, reserving 001-009 for a future "report missing/unparseable" code.
**Source:** 11.3-CONTEXT.md (D-12, D-14), 11.3-DISCUSSION-LOG.md (Decision A), 11.3-05-PLAN.md

### DSX-STA-012 severity set to MEDIUM, guard placed strictly before interpret_effect, no try/except
An unrecognised `effect_size_kind` fires `DSX-STA-012` at MEDIUM (not LOW, not HIGH), from a
membership guard that precedes any call to `interpret_effect`, with the recognised set
single-sourced as `EFFECT_SIZE_KINDS` in `dsx/mathx.py` and imported by `dsx/checks/stats.py`.

**Rationale:** LOW was rejected as too close to the silent skip it replaces (would leave the
`DSX-STA-011` magnitude guard effectively disabled); HIGH was rejected as over-claiming ("we could
not check" is not "the effect is negligible"). A try/except around `interpret_effect` was
explicitly forbidden because it still routes an exception through the gate path — the guard must
decide membership before the call is ever made.
**Source:** 11.3-CONTEXT.md (D-11), 11.3-DISCUSSION-LOG.md (Decision 3), 11.3-02-PLAN.md, 11.3-02-SUMMARY.md

## Lessons

### The sanctioned DSX-EXP-051 rebase legitimately fired on two out-of-scope corpus fixtures
Plan 01's D-02 rebase (family-independent firing) made `DSX-EXP-051` correctly fire on two known-bad
fixtures (`full-frame-cleaning`, `post-hoc-procedure-switch`) that declare `comparisons_looked_at: 5`
with no family and no `results.tests` — but documenting this in the baseline-lock files
(`tests/test_causal_verb_golden.py`, `tests/test_known_bad_corpus.py`) required editing files
outside the plan's declared `files_modified`, blocking the wave-merge gate.

**Context:** A two-persona round (Statistician + Auditor) ruled it a TRUE POSITIVE (total
non-disclosure of a comparison family, naive FWER ≈23%), not a false fire, and unanimously chose
"accept the firing" over a `base >= 1` guard that would perversely exempt total non-disclosure
while still firing on partial disclosure. Applied as a loud, vetoable scope-extension commit after
the three in-scope task commits, rather than silently swallowing the verdict change.
**Source:** 11.3-01-SUMMARY.md

### The DSX-EXP-053 naming set-difference crashed on non-scalar family members (found in code review)
`absent = sorted(reported - set(family))` assumed every `multiplicity.family` member was a hashable
string. A spec declaring `family` as a list of dicts/lists triggered an uncaught `TypeError` on the
gate path instead of degrading to a finding — reachable whenever `isinstance(family, list) and
family and len(family) < len(tests)`.

**Context:** The reviewer named one crash site; the orchestrator independently confirmed and fixed
all three identical instances of the same crash class together (not just the one named), filtering
to string members before the set operation, and added 3 regression tests. The count-based fire
condition itself (untouched) was reconfirmed correct per D-01's `max()` semantics.
**Source:** 11.3-REVIEW.md (WR-03)

### An explicitly-null effect_size_kind is treated as unrecognised, distinct from an absent key
`normalize(test.get("effect_size_kind", "d"))` only defaults to `"d"` when the key is absent; an
explicit `effect_size_kind: null` resolves to `"none"`, which is outside `EFFECT_SIZE_KINDS` and
fires `DSX-STA-012`.

**Context:** Flagged in code review as a possible false positive; a persona round ruled it BY-DESIGN
— an explicitly-null kind is a MORE deliberate reporting gap than silence, and defaulting it to
`"d"` would re-open the exact silent skip DSX-STA-012 exists to close. A 2-test pin was folded into
the fix commit to document the asymmetry as an invariant rather than an incidental behavior.
**Source:** 11.3-REVIEW.md (IN-02)

### DSX-CRV-011's literal "X/10" substring match is a real catch-rate hole, but faithfully correct
The check fires only on the literal placeholder substring `X/10`; a genuine violation like `8/10`
or `visual: 9/10` passes silently. This is not an implementation bug — the schema's own rule is
literally "no substring `X/10`," and D-13 lists exactly that as the allowed structural input — but
it means the check catches only reports that copy the placeholder verbatim.

**Context:** Deferred to Phase-12 backlog rather than fixed inline, because widening to a numeric
regex would amend a settled D-13/schema decision, requiring a reversal record + operator veto +
corpus evidence under D-14, not a reviewer-driven code edit. CRV-011 is MEDIUM (non-blocking), so
zero gate verdicts change today.
**Source:** 11.3-REVIEW.md (WR-01)

### The catalogue generator only writes to disk with an explicit --write flag
A bare `python scripts/gen-finding-catalogue.py` run prints the regenerated catalogue to stdout
without touching `references/finding-codes.md`; only `--write` persists it.

**Context:** Discovered mid-plan-04 execution when the catalogue count didn't tick up as expected
after a bare run; re-running with `--write` produced the expected 252-code result and a passing
`--check`.
**Source:** 11.3-04-SUMMARY.md (Issues Encountered)

### An assumption-analyzer's finding-code-band claim was wrong and caught by independent verification
The `gsd-assumptions-analyzer` agent claimed "the SPEC family max is 082," which would have made
`DSX-SPEC-083` "merely next free." The orchestrator's own independent verification (never trusting
a subagent claim for an irreversible code assignment) found this false — the SPEC family already
extends to 085/086 — and placed `DSX-SPEC-083` deliberately in-band (080-082 validity_frame-shape
band) rather than at the literal tail.

**Context:** This is why the phase's D-06 code-assignment table carries an explicit
"orchestrator-verified free repo-wide" column separate from the analyzer's confidence ratings.
**Source:** 11.3-DISCUSSION-LOG.md (Method §3, D-06 Code Assignments table)

## Patterns

### Single-source a recognised-value frozenset so two consumers can't drift
`EFFECT_SIZE_KINDS = frozenset({"d", "h", "r"})` was hoisted to `dsx/mathx.py` module level;
`interpret_effect` derives its recognised set from it, and `dsx/checks/stats.py` imports the same
constant for its membership guard, rather than maintaining two separate tables asserted equal by a
test.

**When to use:** Whenever a guard needs to reject values before they reach a callee whose own
domain table would otherwise raise — hoisting one canonical constant eliminates the drift surface
entirely instead of merely testing for it.
**Source:** 11.3-02-PLAN.md, 11.3-02-SUMMARY.md

### Degrade to report.ok on any malformed/missing/undecodable artifact input, never raise
`dsx/checks/chart_review.py`'s `check()` catches decode/read/parse errors and returns
`report.ok(...)`, mirroring the existing `figures.check`/`val.check` pattern; the frontmatter
parser degrades to `({}, text)` on a `SpecParseError` instead of re-raising.

**When to use:** Any checks-layer or frame-layer reader of user- or agent-authored content that
sits on the gate path — a missing, truncated, or unparseable artifact must produce a finding (or
silence), never an uncaught exception that crashes the gate.
**Source:** 11.3-05-PLAN.md, 11.3-05-SUMMARY.md, 11.3-SECURITY.md (T-11.3-11)

### A closed-key allow-set guard is born strict on one new sub-block, never retrofitted to legacy
`_EXCLUSIONS_ALLOWED_KEYS = {"rule", "action", "applied_before_split", "justification"}` rejects
any unexpected key inside `validity_frame.exclusions` only; the sibling legacy `inference` block's
silent key tolerance is deliberately left untouched.

**When to use:** When a new sub-block needs strict shape enforcement but the codebase has an
established convention of tolerant/honor-system parsing elsewhere — scope the strict guard to the
new field only rather than widening it retroactively, which would be a regression-prone behavior
change to already-shipped, already-tolerant parsing.
**Source:** 11.3-CONTEXT.md (D-09), 11.3-04-PLAN.md, 11.3-04-SUMMARY.md

### Reuse a finding code's verbatim title + severity literal to avoid catalogue/pin drift
The new CRITICAL branch of `DSX-VAL-060` (single_imputation-under-MAR) reuses the EXACT existing
finding title string and the `"CRITICAL"` severity literal from the code's other branch — only the
`remedy`/`detail` text and the citation differ — so the rendered catalogue row and the
`_CANONICAL_DECLARATIONS` pin (a `(severity, title)` set) collapse into the same existing element
instead of registering as a new, drifted declaration.

**When to use:** When adding a new firing condition to an EXISTING finding code (not minting a new
one), and the catalogue/pin machinery keys on the literal `(severity, title)` pair — keep those two
strings byte-identical across all emit sites for that code.
**Source:** 11.3-01-PLAN.md, 11.3-03-SUMMARY.md

### A brand-new finding-code family needs BOTH catalogue registries in the same commit as the module
Minting `DSX-CRV-*` required adding the family to `PREFIX_GROUPS` (so its rows render under a
section, not just count toward the total) AND to `_D05_ALLOWLIST_PREFIXES` (so citation lines are
`--check`-enforced) — both edited alongside `dsx/checks/chart_review.py` in the same commit.

**When to use:** Any time a phase mints the FIRST code(s) in a genuinely new prefix family — check
both registries in `scripts/gen-finding-catalogue.py`, since each omission fails silently (a code
that counts but doesn't render; a code that isn't citation-checked) rather than erroring loudly.
**Source:** 11.3-05-PLAN.md ("key_links"), 11.3-05-SUMMARY.md, 11.3-SECURITY.md (T-11.3-14, T-11.3-15)

### Placing a new field under an already-hashed subtree gets the content lock "for free"
The `exclusions` sub-block was placed under `validity_frame` specifically because `frame_digest()`
already sha256-hashes the whole `validity_frame` subtree recursively — so a changed exclusion
cutoff automatically changes the digest and trips the existing `DSX-PRE-020` content lock with
zero new machinery, proven by a regression test rather than new detection code.

**When to use:** When adding any new declared field that needs tamper-evidence/content-locking and
a recursive hash over its parent structure already exists — placement under that structure is
cheaper and more reliable than writing a bespoke lock, but the placement choice itself must be
verified (not assumed) against the actual hash-input set.
**Source:** 11.3-CONTEXT.md (D-08), 11.3-04-PLAN.md, 11.3-04-SUMMARY.md

## Surprises

### Reusing DSX-FIG-* for chart-review conformance would have been silently circular
The obvious reuse choice for a report-conformance check would be the existing `DSX-FIG-*` family
(figures), but the chart-review schema's own Gate-D proxy table wildcards `DSX-FIG-*` at
CRITICAL/HIGH — so a malformed `CHART-REVIEW.md` minting a `DSX-FIG-*` code for ITS OWN structural
defects would be swept into the very Gate D verdict the report exists to narrate.

**Impact:** Forced a genuinely new family (`DSX-CRV-*`) and a schema edit (D-14) routing it as a
report-acceptance precondition evaluated separately from — and prior to trusting — the gates the
report itself computes.
**Source:** 11.3-CONTEXT.md (D-12), 11.3-DISCUSSION-LOG.md (Decision A)

### Task 3 of plan 05 was left uncommitted mid-firing, with no code drift on recovery
An earlier execution firing died after plan 05's GREEN commit but before committing Task 3
(`dsx/cli.py` + schema wiring) — leaving two commits unpushed and Task 3's edits sitting
uncommitted in the working tree with no SUMMARY or tracking update.

**Impact:** The closing firing independently re-verified the uncommitted state was genuinely green
(`bash scripts/check.sh` including the gate contract) before committing — the uncommitted edits
matched Task 3 exactly, requiring zero code changes to recover, only process completion (commit,
SUMMARY, tracking, push).
**Source:** 11.3-05-SUMMARY.md (Deviations from Plan #1)

### Only one of six code-review findings required an actual production code change
The deep code review (7 files) surfaced 3 warnings and 3 info findings, but the persona-round
resolution fixed exactly one (WR-03, the TypeError crash); the other five were dispositioned
BY-DESIGN (faithfully implementing already-settled D-13/schema criteria) or deferred to Phase-12
with explicit entry conditions, rather than relitigated as bugs.

**Impact:** Demonstrates the phase's checks were largely correct-as-specified on first
implementation — the review's value was mostly in surfacing catch-rate boundaries for Phase 12 to
measure, not in finding correctness defects that mis-verdict the canonical corpus.
**Source:** 11.3-REVIEW.md (Resolution table, resolution.fixed: 1 / by_design: 3 / deferred_phase12: 2)

### A fixture/example filename is baked directly into the production artifact resolver
`CHART_REVIEW_NAMES = ("CHART-REVIEW.md", "good-CHART-REVIEW.md")` in `dsx/checks/chart_review.py`
includes the example filename `good-CHART-REVIEW.md` as a first-class production lookup name, not
just a test fixture path.

**Impact:** Intentional wiring so the canonical `examples/good-CHART-REVIEW.md` resolves correctly
when the good spec is gated — but it also means a stray file literally named `good-CHART-REVIEW.md`
sitting in a real phase directory would be picked up and gated, and non-conventionally-named
chart-review corpus members could resolve to "no file found" and read as a false-clean verdict.
Routed to Phase-12 as a corpus-wiring entry condition rather than fixed now.
**Source:** 11.3-REVIEW.md (IN-01)

### Gating directly from repo root fails for reasons unrelated to the phase's own checks
Running `./bin/dsx gate verify --spec examples/good-ANALYSIS-SPEC.yaml` directly from the repo root
exits 1 — not because of any DSX-CRV or DSX-EXP/STA/VAL/SPEC finding from this phase, but because
of `DSX-PRE-041` firing on the ambient, ever-growing `examples/DECISIONS.jsonl` trail (an artifact
of Phase 11.2's uncleared-amendment floor).

**Impact:** `scripts/check.sh` isolates gate runs into a tmpdir copy with `DECISIONS.jsonl` deleted
specifically to avoid this; the authoritative corpus contract passes. This same non-regression
clarification recurs verbatim across plans 03, 05, and 06's summaries, indicating it's a persistent
environmental gotcha for anyone gating ad hoc from the repo root rather than through `check.sh`.
**Source:** 11.3-05-SUMMARY.md (Deviations from Plan #2), 11.3-06-SUMMARY.md (Issues Encountered)
