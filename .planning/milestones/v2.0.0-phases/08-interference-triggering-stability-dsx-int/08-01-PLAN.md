  <behavior>
    - Test 1: `diluted_effect` reproduces the naive overall effect Deng & Hu (2015) section 2.1
      publishes for its time-to-success example, from that example's own triggered effect and user
      trigger rate.
    - Test 2: the published naive value and the published true effect for that same example are
      different numbers — the additive-only scope boundary, asserted directly.
    - Test 3: a user trigger rate below 0 raises `ValueError`.
    - Test 4: a user trigger rate above 1 raises `ValueError`.
    - Test 5: a user trigger rate of exactly 1.0 returns the triggered effect unchanged, and a rate
      of exactly 0.0 returns 0.0 — the two closed-interval endpoints are admitted, not rejected.
  </behavior>

  <action>
    Add one module-level function to `dsx/mathx.py`, placed immediately after `design_effect` so
    the two pure-kernel additions of this milestone sit together. Name it `diluted_effect`. Its
    signature takes exactly two floats: `delta_triggered` and `user_trigger_rate`, in that order.
    It returns `delta_triggered * user_trigger_rate`.

    The parameter name `user_trigger_rate` is chosen deliberately and must not be shortened to
    `trigger_rate`. Decision D-10 records that `trigger_rate` is not a contract field at all — the
    contract field is `validity_frame.triggering.expected_trigger_rate` — and that the paper's own
    symbol `TR` means a different thing in its section 3.3 (a per-user denominator trigger rate).
    The paper writes the quantity this parameter carries as `N_Tr/N`, the share of the eligible
    population that triggered. Say that in the docstring.

    Validate before returning, one `if` per condition, copying `design_effect`'s idiom exactly:
    raise `ValueError` with an f-string that echoes the offending value with `!r`. The condition is
    `not 0.0 <= user_trigger_rate <= 1.0`. Both endpoints are admissible — a rate of 1.0 means every
    eligible unit triggered, which is what `examples/good-ANALYSIS-SPEC.yaml` declares, and a rate of
    0.0 means none did. Do not add a range check on `delta_triggered`; a treatment effect is signed
    and unbounded, and the paper's own worked case is negative.

    The docstring carries two labelled paragraphs, in this order, matching `design_effect`:

    A `Citation:` paragraph naming Deng, A. & Hu, V. (2015), "Diluted Treatment Effect Estimation
    for Trigger Analysis in Online Controlled Experiments", WSDM '15, Formula (1) in section 2.1,
    derived in section 3.2; camera-ready at
    `https://alexdeng.github.io/public/files/wsdm2015-dilution.pdf`, ACM Digital Library DOI
    10.1145/2684822.2685307. State the formula as printed, `∆overall = ∆Tr × N_Tr/N`. State its
    three preconditions in the same paragraph: additivity of the metric, no treatment effect for
    untriggered units, and no effect on the trigger complement.

    A `Reference value:` paragraph naming the paper's own time-to-success counterexample from
    section 2.1 — a true effect of −26 msec against the naive formula's −18 msec. State plainly
    that time-to-success is a ratio metric, that the paper prints this pair precisely to show the
    additive formula does not hold there, and that this function is therefore scoped to additive
    metrics only. State that the ratio case is Formula (3) in section 3.3, that it sums over
    individual users and has no closed-form scalar multiplier, and that it is deliberately not
    implemented here.

    Obtain the two input numbers behind the published −18 msec — the triggered effect and the user
    trigger rate of that example — by reading section 2.1 of the paper at the URL above. If both
    numbers are readable, Test 1 asserts `diluted_effect` returns −18 msec to the precision the
    paper prints. If either number is not readable in the paper's own text, do not invent it and do
    not back-solve a pair that happens to multiply to −18: instead mark the input pair `UNVERIFIED`
    in the docstring in the exact style `design_effect` already uses for the Kish section number
    ("... is UNVERIFIED — the page numbers above were confirmed, the section number was not. Do not
    invent one."), write Test 1 against the identity the paper does publish, and record the
    escalation in the plan summary. This branch is expected to be unnecessary; it exists so the
    executor never fabricates a number to make a test green.

    Do not use the paper's Appendix toy example (0.271 − 0.313 = −0.042). Decision D-10 rules it
    out by name: it is a real published number, but it describes the ratio path this function does
    not cover.

    Add the tests to the existing `TestMath` class in `tests/test_dsx.py`, immediately after the
    five `design_effect` tests. Place a standalone comment line reading exactly `# D-05: DSX-INT-030`
    on its own line directly above the first new test, mirroring the `# D-05: DSX-VAL-020` line
    already above `test_design_effect_matches_cochrane_worked_example`. That marker is what
    `scripts/gen-finding-catalogue.py --check` will look for once plan 08-04 ships `DSX-INT-030`;
    placing it now is harmless because `check_d05` only requires markers for codes that already
    exist and ignores markers for codes that do not.

    Name the tests so a `-k` filter finds them: every new test method name contains the word
    `dilut`. Use `assertAlmostEqual` for the float comparison, matching the `design_effect` tests,
    and `assertRaises(ValueError)` for the two range tests.

    Do not import `diluted_effect` anywhere outside `tests/test_dsx.py` in this plan. Decision D-09
    forbids it being called from the gate path, and plan 08-04 will reference it by name in a
    docstring rather than importing it, so an unused import never appears in `dsx/frame/`.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test author to shipped docstring | A citation in a docstring is read as verified fact by anyone auditing the check that points at it. A number invented to make a test pass would be indistinguishable from a published one. |
| caller to math kernel | `diluted_effect` accepts two floats from any future caller. Nothing validates them upstream. |
