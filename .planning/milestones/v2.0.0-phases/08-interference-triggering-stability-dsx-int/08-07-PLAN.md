<deferrals>
**IN-01, quoted-string YAML booleans, is deferred, with the review's own rationale.**
`dilution_adjusted is not True` and `novelty_primacy_assessed is not True` are deliberate identity
comparisons, written that way so the literal boolean `false` still fires the check. The same
strictness means a quoted scalar such as `dilution_adjusted: "true"` parses to the Python string
`"true"`, fails the identity test and fires the check even though the author clearly meant yes.
08-REVIEW.md classifies this as a pre-existing, codebase-wide convention that Phase 8 did not
introduce — the same pattern appears for boolean fields outside this module — and whose failure mode
is "the check fires when it arguably should not", never a silent pass. The review states in writing
that it is not required to fix in this phase. Changing it here would widen a boolean-coercion
convention across the whole codebase from inside a gap-closure plan, which is the wrong place for
that decision. Deferred, unchanged, and recorded here so it is a decision rather than an oversight.

**The unchecked REQ-P8-* boxes in .planning/REQUIREMENTS.md are not planned.** The verifier examined
them and determined the pattern matches the standing Phase 7 convention, where checkboxes are flipped
at a later milestone step rather than at phase-verification time, and explicitly did not score it as
a gap. That file is also single-writer in this project, so a plan must not touch it.
</deferrals>

The work is sequenced by risk rather than by file.

The CR-01 fix changes which findings fire on a class of input, so the first thing that must exist is
a test that fails today for the right reason, and the second thing is the surrounding guards that
would notice if the fix broke the other direction. WR-01's tripwire matters more than a warning-level
item usually would: DSX-INT-030's firing behaviour on the weak-identification-mmm fixture is asserted
today only in a comment, and the CR-01 fix touches the same module. Landing that tripwire before the
fix is what turns "the corpus still passes" into evidence.

Every committed fixture in `examples/` declares `mitigation: none`, so the CR-01 fix is expected to
change no committed fixture's gate behaviour at all. That expectation is itself an acceptance
criterion in Task 2 rather than an assumption: if the corpus map needs an edit after the fix, the
fix did something it was not supposed to do.
</why_this_ordering>
