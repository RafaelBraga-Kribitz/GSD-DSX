<why_this_ordering>
The regression tests land before the fix, in their own commit, for the same reason plan 08-08 does
it: the verifier recorded that several plans in this phase have green commits with no matching red
commit, so nothing in the history proves those tests could ever have failed.

The vocabulary contract test rides in the same red commit even though it passes immediately. It is
what makes the corrected guard honest. The guard names `triggered` as a literal because
`ANALYSIS_POPULATIONS` has exactly two members; that reasoning is only safe while the vocabulary
stays at two. Landing the assertion alongside the tests that force the guard to change means a future
third member turns a test red instead of silently widening what DSX-INT-030 adjudicates.

The weak-assertion fix comes last, after both guards are correct, because tightening it requires
running the tightened test against an input where `DSX-SPEC-082` genuinely does not fire — and the
cleanest such input is the unmutated fixture, whose behaviour must be stable before it can be used as
a control.

Every committed fixture under `examples/` and `templates/` declares an in-vocabulary
`analysis_population` — five declare `eligible`, `interference-shared-budget` declares `triggered` —
so this fix is expected to change no committed fixture's gate behaviour at all. That expectation is
an acceptance criterion in Task 2, not an assumption.
</why_this_ordering>

<threat_model>
Application Security Verification Standard (ASVS) level 1. Blocking severity: high.

The artifact under repair is itself a safety gate, so the useful threat framing is control bypass and
fail-open behaviour, not the web and authentication categories that do not apply to a local, offline
command-line validator. This tool opens a local YAML file, decides whether it blocks, and exits. There
is no network call, no subprocess spawned on the gate path, no secret, no session, no privilege
boundary and no third-party dependency. Threat identifiers continue the phase series, which reaches
`T-8-33` in plan 08-08.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| spec author to gate | An `ANALYSIS-SPEC.yaml` is untrusted input written by the person the gate exists to check. Any field value can be malformed, misspelled or chosen adversarially. |
| vocabulary membership to check logic | Whether a declared string is a recognised member of a closed vocabulary decides which check judges it. A value read as a member it is not is judged by the wrong branch. |
| finding severity to gate threshold | Only a CRITICAL finding blocks `dsx gate plan`. A HIGH finding is reported and the gate still exits 0. A defect that leaves only HIGH findings standing is a bypass even though nothing was silenced. |
| rendered report text to structured findings | An assertion against rendered text cannot tell a finding that fired from a finding code quoted inside another finding's prose. A test that reads the wrong one is a control that is absent while reading as present. |
| code to its own decision trail | `dsx explain` reports the `DecisionRecord` rule text, not the code. If they disagree, an operator auditing a blocked or cleared spec is given a false account of why. |
