<why_this_ordering>
The regression tests land in their own commit before the fix, for a reason the verifier already
recorded once about this phase: plans 08-01, 08-04 and 08-05 have green commits with no matching red
commit in the git log, so nothing in the history proves those tests could ever have failed. Plan
08-07 corrected that habit with a red-then-green pair, and this plan keeps it.

The gate-level test is written against the structured finding list from the start, not against
rendered report text. This is not a stylistic preference. `DSX-INT-010`'s own `detail` text contains
the literal string `DSX-SPEC-082` unconditionally, which is what made the equivalent mitigation-field
assertion vacuous (08-REVIEW.md WR-01). A new text-substring assertion on the risk field would be
born with the same disease. Writing it structurally costs one helper and closes the hole before it
opens.

Every committed fixture under `examples/` and `templates/` declares an in-vocabulary `risk` value —
five declare `none` and two declare `shared_budget` — so this fix is expected to change no committed
fixture's gate behaviour at all. That expectation is an acceptance criterion in Task 2, not an
assumption: if a corpus test goes red after the fix, the fix did something it was not supposed to do,
and the right response is to re-read the trace in 08-REVIEW.md CR-01, not to edit an expectation map.
</why_this_ordering>
