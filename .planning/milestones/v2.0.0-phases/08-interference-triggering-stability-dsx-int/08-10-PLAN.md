<objective>
Close the one gap 08-VERIFICATION.md still scores against Phase 8. A spec that misspells
`interference.risk` while declaring a real, recognised mitigation produces zero `DSX-INT-*` findings
and clears `dsx gate plan` with exit 0.

Purpose: plan 08-08 fixed `_check_interference_unaddressed`'s risk guard, which closes the sub-case
where the misspelled risk is paired with an absent, `none` or unrecognised mitigation. It deliberately
left `_check_interference_mitigation_admissibility`'s risk guard untouched, on the recorded rationale
that judging an out-of-vocabulary risk there would make DSX-INT-011 double-report what DSX-INT-010
now reports. That rationale is false, and both the code reviewer and the verifier falsified it
independently with combination sweeps. The consequence is live: misspelling `risk` is still cheaper
at a CRITICAL-threshold gate than declaring the same risk honestly, which is the exact failure mode
this finding family exists to close. It blocks REQ-P8-01 and REQ-P8-02.

Output: one clause removed from one guard, three pieces of prose corrected to match, two regression
tests that fail before the fix and pass after it, and two disjointness grid tests that turn the
"they never both fire" invariant from a claim in a summary into an executable check at both unit and
gate level.
</objective>

`08-VERIFICATION.md` does not state, recorded so the executor does not have to rediscover them and
does not act on a wrong premise.

1. **The phrase the review quotes is not in the file.** `08-REVIEW.md` CR-01 says
   `_check_interference_mitigation_admissibility`'s docstring "currently states DSX-INT-011 requires a
   real, recognised risk". Searched: that sentence does not appear verbatim anywhere in
   `dsx/frame/interference.py`. It is a fair paraphrase of two real sentences that do appear, in two
   different docstrings, and Task 2 names both by their actual wording. Do not go looking for the
   quoted phrase and conclude the item is already done.

2. **The import block stays exactly as it is.** After the clause is dropped,
   `INTERFERENCE_RISKS` is no longer referenced by any executable statement in the module — only by
   comments, docstrings and one `DecisionRecord.rule` string. That is not a reason to remove the
   import. `METRIC_TYPES` is already imported on the same statement under exactly the same terms: it
   is referenced only in the commentary that anchors `_ADDITIVE_METRIC_TYPES` and
   `_RATIO_METRIC_TYPES` to the parent vocabulary. Keeping `INTERFERENCE_RISKS` for the same reason —
   it anchors `_RISK_MITIGATION_MAP`'s "keyed by every member" contract — is consistent with the
   file's existing convention, keeps this plan's diff to the guard alone, and breaks nothing:
   `scripts/check.sh` runs no linter. An acceptance criterion in Task 2 pins the import list so this
   stays a checked decision rather than a silent one.

3. **`_RISK_MITIGATION_MAP.get()` can never receive an unhashable key.** `dsx.spec.normalize()` is
   `str(value).strip().lower()...`, so it returns a string for any input, including a list or a
   mapping. The guard's fall-through is therefore safe for a non-string risk value, which is why the
   grounding sweep's integer case raises nothing.

4. **The remedy text for an out-of-vocabulary risk will read oddly, and that is deliberately left
   alone.** For a risk with no map cell, `admissible_listed` degrades to `(none admissible)`, so the
   emitted remedy tells the author to declare an admissible mitigation while stating none exists. The
   real remedy is to fix the spelling, and `DSX-SPEC-082` fires beside it saying exactly that.
   Rewording operator-facing message text is a message-contract change; plans 08-08 and 08-09 both
   recorded the same call for the same reason. Task 2 requires the executor to *observe and record*
   the rendered remedy so it is on the record rather than unknown, and prohibits changing it.
</planner_findings>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| spec author to gate | An `ANALYSIS-SPEC.yaml` is untrusted input written by the person the gate exists to check. Any field value can be malformed, misspelled or chosen adversarially. |
| one check's guard to its sibling's guard | Two checks that between them are supposed to cover an input space each assume the other handles what they return early on. An input that both return early on is judged by neither, and neither check's own tests can see it. |
| vocabulary membership to check logic | Whether a declared string is a recognised member of a closed vocabulary decides which check judges it. A string belonging to no vocabulary can fall between two checks and be adjudicated by neither. |
| finding severity to gate threshold | Only a CRITICAL finding blocks `dsx gate plan`. HIGH, MEDIUM and INFO findings are reported and the gate still exits 0. A defect that leaves only sub-CRITICAL findings standing is a bypass even though nothing was silenced. |
| a recorded rationale to the code it justifies | A scoping decision written into a plan and repeated in a summary becomes the reason a later round does not look again. If the rationale is false and untested, it protects the defect it was written about. |
