<objective>
Give the contract somewhere to say where each cleaning step's statistics were computed, and check
that declaration against the whole-pipeline boundary the specification already carries.

Purpose: the reproduction declares a whole-pipeline boundary of training rows only, honestly, and
then imputes over the full frame during a cleaning stage that boundary was never understood to
cover. Until the contract can carry a per-step boundary, an operator who wants to declare the truth
has no field to declare it in.

Output: an optional per-dataset cleaning declaration, two new finding codes, a shared accepted-value
constant, template scaffold, tests, a decision record and a current catalogue.
</objective>

<assumption_delta_decision>
Noun: the fit boundary declaration.

Decision: add-alongside.

Rationale: this plan generalises a single whole-pipeline fit boundary, the model section's
preprocessing boundary, into an optional per-step boundary on each dataset's cleaning list.
Promoting the per-step form to the primary declaration would newly break every specification
outside this repository that declares only the whole-pipeline field, and would contradict the
requirement's own statement that absence of the block alone fires nothing.

Accepted debt: two fit-boundary declarations can now disagree with each other. That is exactly what
DSX-ML-024 exists to catch, so the debt is visible in the output rather than silent in the schema.

Suggested invariant test: a specification declaring a whole-pipeline boundary of training rows only
and a per-step boundary outside training rows must never clear the gate. Task 1's automated check
asserts this directly.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| specification author to gate | The cleaning list, its column names and its fit boundaries are analyst-supplied and untrusted. A malformed list must degrade, not raise. |
| two declarations to one truth | The whole-pipeline boundary and the per-step boundary can disagree. Which one the gate believes is a policy decision, not an implementation detail. |
| template to every future specification | The template is what every new specification starts from. A field added there uncommented becomes a de facto requirement. |
