# Phase 11.1: Code Review Report

**Reviewed:** 2026-08-20T00:00:00Z
**Depth:** deep

## Summary

The shipped test suite (438 tests across `tests/test_dsx.py`, `tests/test_known_bad_corpus.py`)
passes, `scripts/gen-finding-catalogue.py --check` reports the catalogue current with no D-05
violations, and a live `dsx gate execute` run against the new `full-frame-cleaning` fixture
reproduces exactly the CRITICAL/HIGH codes the paired POSTMORTEM.md claims
(`DSX-CODE-020`/`021`/`030` CRITICAL, `DSX-ML-090` HIGH). That is where validation stops and
adversarial review starts.

Empirical testing (not just reading) of the two new regexes in `dsx/checks/code.py` that this
phase's own docstrings describe as immune to catastrophic backtracking (threat T-11.1-01) found
that one of them, `FULL_FRAME_SPREAD_FILTER_RE`, is in fact **cubic** in line length on a
non-matching line (measured: 200 chars → 0.025s, 1600 chars → 12.5s, consistent with O(n³)), and
its sibling `FULL_FRAME_IMPUTE_RE` is quadratic (measured: 5,000 chars → 0.02s, 40,000 chars →
1.6s). Both contradict their own docstring's explicit claim of linear, non-catastrophic scanning.
Given these run once per line of an analyst-supplied entrypoint file with no length cap, a single
long line (very plausible in generated or wide-feature-list code, not only adversarial input) can
hang `dsx check`/`dsx gate` for minutes.

Direct execution also found two silent detection-bypasses in the same file's fit-before-split
scanning: a single extra space before a `.fit(` call's parenthesis defeats `DSX-CODE-001`
entirely, and a `.fit(X=…, y=…)` keyword-argument call — an idiomatic style, and specifically
plausible for LLM/agent-authored pipelines, which is this phase's own stated threat model —
is invisible to `DSX-CODE-021`'s argument extractor. A third, narrower gap (a semicolon-joined
line with two `.fit(` calls only ever yields the first) and a portability defect in
`dsx/decisions.py`'s append-only writer (documented as writing `\n`-terminated lines; measured to
actually write `\r\n` on this platform) round out the findings below.

## Critical Issues

### CR-01: `FULL_FRAME_SPREAD_FILTER_RE` is cubic in line length — a real ReDoS, not the "linear" scan its own docstring claims

**File:** `dsx/checks/code.py:64-66` (pattern), `dsx/checks/code.py:53-60` (docstring claim), used by `_first_full_frame_cleaning_line` (`dsx/checks/code.py:510-524`), invoked once per non-comment/non-import line of every scanned entrypoint.

**Issue:** The comment above this pattern (and `FULL_FRAME_IMPUTE_RE`) states: "Two independent
lookaheads each, one bounded scan per lookahead — not a nested quantifier — so co-occurrence on
the line is order-independent and linear... a nested quantifier here would expose the gate to
catastrophic backtracking on adversarial, analyst-authored entrypoint text." This claim is false
for `FULL_FRAME_SPREAD_FILTER_RE`:

```python
FULL_FRAME_SPREAD_FILTER_RE = re.compile(
    r"(?=.*\w+\s*\[)(?=.*\.(?:std|quantile)\s*\()"
)
```

The first lookahead's `.*\w+` has overlapping character classes (`.` matches every `\w` character
too), which is the textbook regex-backtracking-blowup shape. Combined with `re.search()` retrying
the whole (zero-width) pattern at every start position when it fails, this becomes cubic on a
non-matching line. Measured directly against the shipped code (`code_mod.FULL_FRAME_SPREAD_FILTER_RE.search("x" * n)`):

| n (chars) | time |
|---|---|
| 200 | 0.025s |
| 400 | 0.21s |
| 800 | 1.6s |
| 1600 | 12.5s |
| 10000 | still running after 120s in this review |

This is invoked on every non-comment line of any declared `reproducibility.entrypoint` file
(`.py` or `.ipynb`), with no line-length cap. A single long line with no `[` character — a wide
`pd.get_dummies([...])` column list, a long chained pandas expression, a generated/minified line,
or simply a very long string literal — hangs `dsx check code` / `dsx gate execute|verify|ship`
for minutes to longer, well within reach of ordinary (not just adversarial) analyst code, directly
defeating the "D-01: gate never blocks the pipeline it's meant to protect" spirit the module's own
threat-model comment claims to uphold.

**Fix:**
```python
# Replace the ambiguous .*\w+ lookahead construction with two independently-scanned,
# unambiguous sub-patterns (no leading .*, no overlapping character classes), ANDed
# in Python rather than combined into one regex via sequential lookaheads:
_SPREAD_SUBSCRIPT_RE = re.compile(r"\w\s*\[")
_SPREAD_STAT_RE = re.compile(r"\.(?:std|quantile)\s*\(")

def _is_full_frame_spread_filter(line: str) -> bool:
    return bool(_SPREAD_SUBSCRIPT_RE.search(line) and _SPREAD_STAT_RE.search(line))
```
Add a timing regression test in the same style as `test_fit_call_re_timing_no_catastrophic_backtracking`
(already present for `FIT_CALL_RE`) against a long non-matching line, so this class of regression
is caught mechanically rather than by manual review.

### CR-02: `FULL_FRAME_IMPUTE_RE` is quadratic in line length — same "linear" claim, same shape of bug, lower severity

**File:** `dsx/checks/code.py:61-63`

**Issue:** Same root cause as CR-01 (two `.*`-prefixed lookaheads combined via sequential
zero-width assertions, retried by `re.search()` at every start position on failure), one degree
less severe because this pattern's `.*` is followed by a fixed multi-character literal
(`.fillna`) rather than an ambiguous `\w+`. Measured:

| n (chars) | time |
|---|---|
| 5,000 | 0.02s |
| 10,000 | 0.09s |
| 20,000 | 0.38s |
| 40,000 | 1.6s |

Growth is consistent with O(n²), not the "linear" the docstring claims. Lower urgency than CR-01
(a much longer line is needed to reach multi-second hangs) but the same DoS class against the
same untrusted input (an analyst-supplied entrypoint file with no length cap), and it sits right
next to CR-01 under the same threat-model comment, so fixing one without the other leaves the
comment's blanket claim false for the sibling pattern.

**Fix:** Same pattern as CR-01 — split into two unambiguous, independently-`.search()`ed
sub-patterns ANDed in Python:
```python
_IMPUTE_FILLNA_RE = re.compile(r"\.fillna\s*\(")
_IMPUTE_STAT_RE = re.compile(r"\.(?:mean|median|mode)\s*\(")

def _is_full_frame_impute(line: str) -> bool:
    return bool(_IMPUTE_FILLNA_RE.search(line) and _IMPUTE_STAT_RE.search(line))
```

### CR-03: A single space before `.fit(`'s parenthesis completely bypasses `DSX-CODE-001`

**File:** `dsx/checks/code.py:492-507` (`_first_fit_leak_line`)

**Issue:** `_first_fit_leak_line` re-checks a redundant literal substring after the regex already
matched:
```python
for pattern in FIT_LEAK_MARKERS:          # r"\.fit\s*\(" tolerates a space before "("
    if re.search(pattern, line):
        if "fit(" in line or "fit_transform" in line or "partial_fit" in line:
            return index
```
`FIT_LEAK_MARKERS`' own regex (`\.fit\s*\(`) intentionally tolerates whitespace before the
parenthesis. The redundant literal check does not — `"fit(" in line` requires the parenthesis to
immediately follow "fit" with zero characters between. Confirmed directly:
```python
>>> code_mod._first_fit_leak_line(["model.fit (df)"])
None
```
End-to-end: an entrypoint containing `model.fit (df)` before `train_test_split(df)` produces
**zero findings** — `DSX-CODE-001` (CRITICAL, "fit before split") does not fire, even though this
is the exact leak the code exists to catch. (Note: `.fit_transform (` and `.partial_fit (` are
*not* affected, because their literal-substring fallbacks — `"fit_transform" in line` /
`"partial_fit" in line` — don't require the parenthesis to be adjacent; only the bare `.fit (`
case is silently bypassed.)

**Fix:** Delete the redundant, inconsistent literal re-check — the regex already fully determines
the match:
```python
def _first_fit_leak_line(lines: list[str]) -> int | None:
    for index, line in enumerate(lines):
        stripped = line.strip()
        if stripped.startswith("#"):
            continue
        if re.match(r"^(from|import)\b", stripped):
            continue
        if PIPELINE_FIT_TRAIN_RE.search(line):
            return index
        for pattern in FIT_LEAK_MARKERS:
            if re.search(pattern, line):
                return index
    return None
```

### CR-04: `.fit(X=…, y=…)` keyword-argument calls are invisible to `DSX-CODE-021`'s argument extractor

**File:** `dsx/checks/code.py:90-92` (`FIT_CALL_RE`), used by `_fit_call_arguments` (`dsx/checks/code.py:527-548`)

**Issue:** `FIT_CALL_RE` requires the captured token to start immediately after the call's opening
parenthesis:
```python
FIT_CALL_RE = re.compile(
    r"\.fit(?:_transform)?\s*\(\s*([A-Za-z_][\w.\[\]'\"]*)\s*[),]"
)
```
A call passing its first argument by keyword — `model.fit(X=data, y=target)` — never matches at
all, because the character immediately after `(` is `X`, then `=`, and `=` is not in the allowed
character class, so the whole match attempt for that `.fit(` occurrence fails and `.search()`
finds nothing else to match on the line. Confirmed directly:
```python
>>> code_mod.FIT_CALL_RE.search("model.fit(X=data, y=target)")
None
>>> code_mod._fit_call_arguments(["model.fit(X=data, y=target)"])
[]
```
End-to-end, with a split marker present and `model.fit(X=data, y=target)` occurring after it
(`data` being the untouched full frame — the textbook leak `DSX-CODE-021` exists to catch): the
check emits **zero findings**. This is a real detection blind spot, not just a syntactic edge
case — explicit keyword arguments are a common, readable style, and are specifically plausible in
autonomously-generated pipeline code (the exact "AI Data Scientist"-style reproduction this phase
targets), which tends toward verbose, explicit argument naming.

**Fix:** Allow (and skip) an optional leading `identifier=` before the captured token:
```python
FIT_CALL_RE = re.compile(
    r"\.fit(?:_transform)?\s*\(\s*(?:[A-Za-z_]\w*\s*=\s*)?([A-Za-z_][\w.\[\]'\"]*)\s*[),]"
)
```
Add a test alongside the existing `FIT_CALL_RE`/`_fit_call_arguments` cases in
`tests/test_dsx.py::TestPhase11_1Code` asserting `model.fit(X=data, y=target)` after a split
fires `DSX-CODE-021`.

## Warnings

### WR-01: `_fit_call_arguments` only ever extracts the first `.fit(`/`.fit_transform(` call per line

**File:** `dsx/checks/code.py:527-548`

**Issue:** `match = FIT_CALL_RE.search(line)` finds at most one match per line (not
`finditer`). A semicolon-joined line with two fit/fit_transform calls after the split — e.g.
`imputer.fit(X_train); scaler.fit_transform(data)` — only ever yields the first call's token
(`X_train`, the legitimate one); the second, leaky call (`data`, the untouched full frame) is
silently dropped and never reaches `DSX-CODE-021`'s membership test. Confirmed directly:
```python
>>> code_mod._fit_call_arguments([
...     "imputer.fit(X_train); scaler.fit_transform(data)",
... ])
[(0, 'X_train')]
```
This is not a hypothetical code style: this same file's own test suite
(`tests/test_dsx.py::TestPhase11_1Code.test_call_on_same_line_as_split_marker_is_at_or_after`,
and several `DSX-CODE-030`/`031` tests) constructs semicolon-joined one-liners deliberately,
confirming the pattern is expected in the corpus this tool screens.

**Fix:** Use `finditer` and yield every match on the line, not just the first:
```python
def _fit_call_arguments(lines: list[str]) -> "list[tuple[int, str]]":
    results: "list[tuple[int, str]]" = []
    for index, line in enumerate(lines):
        stripped = line.strip()
        if stripped.startswith("#"):
            continue
        if re.match(r"^(from|import)\b", stripped):
            continue
        for match in FIT_CALL_RE.finditer(line):
            token = match.group(1)
            if token:
                results.append((index, token))
    return results
```
(The caller in `check()` already takes the first non-training-frame match `>= first_split` in
line order, so this change is backward compatible with every existing single-fit-per-line test.)

### WR-02: `dsx/decisions.py::append()` writes `\r\n` on Windows, contradicting its own documented "single `\n`" contract

**File:** `dsx/decisions.py:111-119` (`append`), contract stated at `dsx/decisions.py:13-15`

**Issue:** The module docstring states the append contract normatively: "Each line is
`json.dumps(record.to_dict(), sort_keys=True)` followed by a single `\n`." `append()` opens the
file in default text mode with no `newline=` argument:
```python
with Path(path).open("a", encoding="utf-8") as fh:
    fh.write(line + "\n")
```
On Windows, text-mode writes translate every `\n` to `os.linesep` (`\r\n`) unless `newline=""` or
`newline="\n"` is passed. Confirmed directly — writing one record and reading the raw bytes back:
```python
>>> raw
b'{"...":"...", ...}\r\n'
```
`read_all()` tolerates this today only because `Path.read_text()` also performs universal-newline
translation by default, so the round trip inside this codebase is silently fine. But the
docstring's claim is a normative contract "for any future writer of this file", and this repo's
own `CLAUDE.md` explicitly calls out CRLF as a first-class hazard for exactly this kind of
line-oriented, append-only artifact. Any other consumer that reads the file in binary mode, hashes
it, diffs it, or is written in a language/tool without Python's universal-newline default will see
`\r\n` where the contract promises `\n`.

**Fix:**
```python
with Path(path).open("a", encoding="utf-8", newline="\n") as fh:
    fh.write(line + "\n")
```

### IN-01: `SPLIT_MARKERS` carries a dead, redundant entry

**File:** `dsx/checks/code.py:23-33`

**Issue:** `"TimeSeriesSplit"` and `"TimeSeriesSplit("` are both present in the tuple. Since
`_first_line_matching` tests membership via plain substring (`marker in line`), any line matching
`"TimeSeriesSplit("` already matches `"TimeSeriesSplit"` first (it's a prefix), making the second,
more specific entry unreachable dead weight.

**Fix:** Drop `"TimeSeriesSplit("` from the tuple (or, if the intent was ever to require the
call-form specifically for this one marker, use a matching scheme consistent with that intent
across all entries rather than one asymmetric duplicate).
