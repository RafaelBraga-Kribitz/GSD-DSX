# Phase 11.1 Plan 07: Selection Ledger and Model-Selection Bias (DSX-ML-090/091/092) Summary

**Added an optional `model.selection_ledger` field — `{candidates_evaluated, configurations_tried, selected_on}` — owed once `model.algorithm` is declared; an incomplete ledger draws `DSX-ML-090` at HIGH naming each missing field, a complete ledger selected on the test set draws `DSX-ML-091` at CRITICAL, and a complete ledger selected on the same folds as the reported score draws `DSX-ML-092` at HIGH, with an unrecognised selection basis (including a misspelling) folded into the missing-field case rather than buying silence.**

## Accomplishments

- `SELECTION_BASES = frozenset({"train", "validation", "test", "cv_same_fold", "nested_cv"})` added to `dsx/checks/ml.py` beside `SCORE_SOURCES`, with a comment stating the two vocabularies describe different things (where a selection choice was made, versus where a reported score came from) and must not be merged.
- `_check_selection_ledger(model, report)` added and wired into `check()`'s dispatch immediately after `_check_baseline`:
  - Returns immediately when `model.algorithm` is blank — no ledger is owed when no choice was declared.
  - Reads `model.selection_ledger` through the shared `section()` mapping idiom, so a ledger declared as a list or any other non-mapping value degrades to "no ledger" instead of raising.
  - Collects missing fields (`candidates evaluated`, `configurations tried`, `selection basis`) via `is_blank()` for the first two and `is_blank()`-or-out-of-`SELECTION_BASES` for the third; any missing field fires `DSX-ML-090` (HIGH), naming each missing field individually in the finding's detail.
  - A declared `configurations_tried: 0` counts as present (not missing) — `is_blank()` reads a declared `0` as present, matching the plan's explicit zero-count requirement.
  - An unrecognised `selected_on` (blank or out-of-vocabulary, including a misspelling like `"tset"`) is folded into the same `DSX-ML-090` missing-field branch — never a distinct outcome — closing the same bypass class `_check_cleaning`'s `fit_on` test and `_check_metric_choice`'s metric-vocabulary test already close.
  - When the ledger is complete, branches on the normalised basis: `"test"` fires `DSX-ML-091` (CRITICAL); `"cv_same_fold"` fires `DSX-ML-092` (HIGH); every other accepted value (`train`, `validation`, `nested_cv`) fires neither and records a `report.ok()` acknowledgement line naming the basis.
  - A shared deterministic decision record is appended once per report whenever an algorithm is declared, naming the three ledger fields as inputs and a complete nested-protocol ledger as the counterfactual.
- `_check_selection_ledger` carries a docstring with the Cawley & Talbot (2010) *JMLR* citation (the paper's central over-fitting-in-model-selection result, stated in its own Abstract; the exact section locator for the fuller nested-CV remedy treatment is marked UNVERIFIED per D-05, matching this file's three other citations' own precedent) and a structural-criterion paragraph: three declared fields, a completeness test, then one membership branch — no statistic computed.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 4-adjacent — discovered plan contradiction, not a code bug] `SELECTION_BASES`/`SCORE_SOURCES` disjointness acceptance criterion is unsatisfiable as written**

- **Found during:** Task 1, running the plan's standalone acceptance-criteria command:
  `python -c "from dsx.checks import ml; assert ml.SELECTION_BASES == frozenset({'train','validation','test','cv_same_fold','nested_cv'}); assert not (ml.SELECTION_BASES & ml.SCORE_SOURCES); ..."`.
- **Issue:** This single command asserts two things that cannot both be true. `SCORE_SOURCES` — shipped in plan 11.1-06 and locked by that plan's own `test_score_sources_vocabulary_is_locked` and `test_accepted_score_sources_produce_no_052` (the latter iterating `"nested_cv"` as one of three accepted score sources) — already contains the string `"nested_cv"`. This plan's own `<action>` text ("the training set, a validation set, the test set, the same cross-validation folds the reported score came from, and a nested protocol") and its embedded `<automated>` verify commands (which construct a "complete, clean" ledger using `'selected_on': 'nested_cv'` to prove the no-code-fires branch) both require `SELECTION_BASES` to contain `"nested_cv"` too. The two vocabularies use the same word for the same real-world concept — a nested cross-validation protocol — in two different roles (where a score came from vs. where a selection choice was made), and that shared vocabulary term makes the sets intersect by construction. No implementation choice can make `{'train','validation','test','cv_same_fold','nested_cv'}` and `{'cv_mean','holdout','nested_cv','best_fold','unknown'}` disjoint while both are required to contain `'nested_cv'`.
- **Fix:** Implemented `SELECTION_BASES` with its full, literal, plan-specified five-member set (verified directly by the plan's own `<automated>` verify commands, which are the load-bearing, functionally-tested requirement). Left `SCORE_SOURCES` byte-identical to its plan-11.1-06 state, because rewriting it to drop `"nested_cv"` would break `test_accepted_score_sources_produce_no_052`, an already-shipped test this plan's own `must_haves.prohibitions` explicitly forbids weakening, deleting or rewriting. Amended my own RED-phase test (originally written to mirror the plan's literal acceptance-criteria assertion) to drop the unsatisfiable disjointness check, replacing it with a comment explaining why, and renamed it `test_selection_bases_vocabulary_is_locked` to describe what it actually asserts.
- **Files modified:** `dsx/checks/ml.py`, `tests/test_dsx.py`
- **Commit:** `45d21c8`
- **Not silently resolved:** this is surfaced here, in the frontmatter's `key-decisions`, and in the amended test's own inline comment, rather than treated as passing. Running the plan's exact standalone acceptance-criteria one-liner (as literally written) will still report the intersection `frozenset({'nested_cv'})` and fail its `assertFalse`/`assert not (...)` clause — that failure is expected and does not indicate a defect in the shipped code; it indicates the acceptance criterion itself cannot be met given plan 11.1-06's already-shipped `SCORE_SOURCES`.
