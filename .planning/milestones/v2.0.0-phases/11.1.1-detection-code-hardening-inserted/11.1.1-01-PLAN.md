<decisions_settled_here>
Nine calls, made here so no executor has to guess. Six of them close blockers raised against
`11.1.1-AST-DESIGN.md` by adversarial review; those are marked **[blocker]**.

**Decision 1 — one line axis, `_source_lines`, not `str.splitlines()`. [blocker]**
`ast` line numbers index the CPython tokenizer's line partition. `str.splitlines()` also
splits on `\x0b \x0c \x1c \x1d \x1e \x85 \u2028 \u2029`; the tokenizer does not. One such
character anywhere in the entrypoint — including inside a string literal — desynchronises
every AST-derived index from every text-derived one, and `cleaning_index < first_split` then
compares two different axes. Measured this session: with one form-feed line above the split,
`splitlines()` reports 6 lines where the tokenizer sees 5, `ast` gives the fit call
`lineno` 5, `splitlines()[4]` is the split line and the normalised `[4]` is the fit line.
So `check()` builds `lines` from

```
_source_lines(source) -> list[str]
```

which replaces `\r\n` and lone `\r` with `\n`, splits on `\n`, and drops a single trailing
empty element. That is exactly the tokenizer's partition, so AST and text indices coincide
**by construction** rather than by luck. Every existing index arithmetic in `check()` is
untouched. This is also where the repo's CRLF rule is discharged — no pattern in this module
gains `\r?\n`.

**Decision 2 — notebook markdown cells are blanked CHARACTER-WISE, not line-counted. [blocker]**
`_read_source` stops whitelisting `{"code", "markdown"}`. Code cells contribute their source
verbatim; a markdown cell contributes `re.sub(r"[^\r\n]", "", chunk)` computed on the SAME
`chunk = "".join(src)` string the reader builds today; other cell types are dropped exactly
as today. Chunks are still joined with `"\n"`.

The design proposed `max(1, len(src.splitlines()))` blank lines. That under-counts by one
whenever a markdown cell's text ends in a newline — which is the common nbformat shape — and
miscounts again for `\r`, `\x0c` and `\u2028`. Since preserving line geometry is the SOLE
reason blank-padding was chosen over simply dropping markdown cells, an arithmetic that does
not preserve it defeats its own purpose. Character-wise blanking preserves it by
construction: every newline survives, every other character does not.

Measured this session against three markdown shapes:

| markdown shape | `max(1,len(splitlines()))` | true line slots | char-wise | code-cell fit index today / after |
|---|---|---|---|---|
| list, trailing `\n` | 2 | 3 | 3 | 5 / 5 |
| list, no trailing `\n` | 2 | 2 | 2 | 4 / 4 |
| plain string, trailing `\n` | 2 | 3 | 3 | 5 / 5 |

**Decision 3 — an unreadable entrypoint is never silently a pass. [blocker]**
Two separate changes.

(a) `.py` is read with `encoding="utf-8-sig"` (a real in-repo BOM file,
`examples/analysis/charts.py`, fails `ast.parse` today), and a decode failure is handled by
**re-reading with `errors="replace"`**, not by returning `None`. Today an undecodable
entrypoint raises out of `check()` and produces exit 2; the design proposed swallowing it to
`None`, which converts a loud failure into exit 0 with zero findings, zero pass lines and
zero decision records. Neither is acceptable. A replacement-character scan still finds the
leak on the lines that decoded, and the degraded read is named on the pass line.

(b) On every remaining early return — blank entrypoint declared, path unresolvable,
unsupported suffix, `OSError`, unparseable notebook JSON — `check()` emits
`report.ok("entrypoint NOT scanned — <reason> (no leak scan ran)")` before returning.

**Deliberately deferred, with the reason:** the two `record_decision` calls are NOT extended
to the skip paths. D-04 records one judgment per *reached* call site, and a skipped scan
reaches neither; emitting a record whose every input is `none` would assert a judgment that
was never made, and three committed tests constrain the record count. The skip is instead
visible in `passed_checks`, and task 1 commits an exit-code test for an unscannable
entrypoint, of which there is none today.

**Decision 4 — Rule B of the prose mask spares BOTH boundary lines. [blocker]**
`_prose_line_indices(tree)` masks (A) every line of an `ast.Expr` whose value is a string
constant — docstrings and bare string statements — and (B) only the STRICTLY INTERIOR lines
of a multi-line string constant, `lineno .. end_lineno - 2` zero-based. The design masked
the closing line too. The opening line is spared because it can carry real code (`sql = """`);
the closing line carries real code exactly as often (`"""; data = ...`), and masking it
deletes true-positive CRITICAL findings on the same statement shape SC3 exists to catch.
Review reproduced two: a `DSX-CODE-020` and a `DSX-CODE-030` silently lost. Masking whole
lines only — never "any line a string touches" — is also load-bearing: three single-line
string constants sit on `df['Age'] = df['Age'].fillna(df['Age'].mean())`.

**In this wave the mask has exactly one consumer**, the split-marker text scan (Decision 5).
Extending it to DSX-CODE-002/003/020/030's loops is plan 02's work; the rule is fixed here
so plan 02 inherits it rather than re-deciding it.

**Decision 5 — `first_split` is a UNION of the call-node set and the text-marker scan.**
The design made split detection AST-only. Review measured what that costs: a split reached
through an alias (`splitter = train_test_split`), a bare class reference, a helper or a
`functools.partial` stops counting as a split at all. DSX-CODE-021 is gated on
`if first_split is not None:`, so losing the split does not make 021 stricter — it deletes
021's entire domain; and DSX-CODE-010 then reports "no declared split marker" against a file
whose splitter is on the page. Five shapes were measured moving from `{DSX-CODE-021}` to
`{DSX-CODE-001, DSX-CODE-010}`.

So `first_split = min(ast_split_index, text_split_index)` over the values that exist, where
the text half is the shipped `_first_line_matching(lines, SPLIT_MARKERS)` with masked lines
skipped as well. The consequences, both intended:

- an aliased, wrapped or bare-name split keeps counting — pre-change behaviour, the
  conservative direction for a blocking gate;
- a split marker that appears only inside a DOCSTRING stops counting, because the mask
  removes that line. That is stricter and is a true positive: prose stops deciding verdicts
  in either direction. It is announced.
- a split marker inside a single-line string assigned to a variable (`s = "train_test_split"`)
  still counts, unchanged from today. Named in `<uncaught_after_this_plan>`.

**Decision 6 — call sites sort by `(line, col_offset, end_col_offset)`.**
The design claimed `(lineno, col_offset)` is a total order. It is not: nested and chained
calls collide on both keys — `ast.parse("m.fit(x).fit(y)")` gives two calls at `(0, 0)`, and
`examples/analysis/leaky_model.py` has `fit_transform` and `StandardScaler` both at line 6
column 4. Determinism would then rest on `sorted` being stable and `ast.walk` being
breadth-first, an accident no test could catch. Ascending `end_col_offset` breaks the tie
towards the innermost/leftmost-ending call, which is what today's left-to-right `finditer`
reports. Measured: `m.fit(full_frame_a).fit(full_frame_b)` reports `full_frame_a` both
before and after. Pinned by name, not merely by repeatability.

**Decision 7 — the fallback is whole-file, and the interpreter is recorded.**
One `ast.parse` per `check()` call; one flag; no per-code fallback and no partial tree. Two
scanners would otherwise disagree about `first_split` inside one run, and a gate whose codes
disagree about where the split is cannot be used as evidence. The guard is
`(SyntaxError, ValueError, RecursionError, MemoryError)`.

`ast.parse` accepts the RUNNING interpreter's grammar, so an entrypoint using `match`,
`except*` or PEP 695 syntax takes the AST path on a 3.12 runner and the fallback on a 3.9
one. That is a hidden input to a pinned determinism guarantee, and this repo already runs two
interpreters (`./scripts/check.sh` uses `python3` 3.14.6; the house quick command uses
`python` 3.12.10). Option "pass `feature_version=(3, 9)`" was rejected — it would push every
modern file onto the weaker scan on every machine, trading real coverage for uniformity.
Instead the dependency is DISCLOSED: both decision records gain
`python:{major}.{minor}` alongside `scan_path:`, and the module docstring states that the
scan path depends on the interpreter's grammar version. The human-readable `report.ok` line
keeps stable text so the markdown report does not vary by machine.

**Decision 8 — the DSX-CODE-002 quadratic is fixed in this wave.**
It is not this plan's check, but it is on the PRIMARY path, it already exceeds the house
budget, and the design's proposed mitigation for T-11.1-01 (per-pattern timing pins on
non-matching input) is structurally blind to it, because the cost is not in a pattern. The
loop rebuilds `prior = "\n".join(lines[:index])` per match and its `break` sits inside the
inner `if`, so it keeps going after a suppressed match. Measured today: 0.0228 / 0.0869 /
0.3454 / **1.6003** seconds at 2,000 / 4,000 / 8,000 / 16,000 matching lines. Hoisting the
`break` out of the inner `if` is provably behaviour-preserving — `lines[:j]` is a prefix
superset of `lines[:i]` for `j > i`, so once `X_train` is in `prior` it is in every later
`prior`, and the loop is dead after the first suppressed match. Pinned by a timing test whose
INPUT IS THAT SHAPE, not by a non-matching-input pin.

<uncaught_after_this_plan>
Written here so that task 1 can pin it and plan 03 can re-derive the README section from it.
Nothing in this plan makes DSX-CODE-001 sound. A clean scan is not proof that no leak exists.

**Real leaks this plan still does not see, on the PARSED path:**

1. Dynamic dispatch — `getattr(model, "fit")(data)`, `handlers["fit"](data)`. The callee
   resolves to `""` and matches nothing.
2. A bound method held in a variable — `f = model.fit` then `f(data)`.
3. A fit inside a helper the entrypoint imports. Only the declared entrypoint file is read.
4. **`exec`/`eval`'d source — and this is a REGRESSION, not a standing limit.** Measured by
   review: `src = "scaler.fit(data)"` then `exec(src)` before a split draws DSX-CODE-001
   CRITICAL today through the text scan and draws NOTHING under a call-node walk, on a file
   that parses, so no fallback and none of the four degrade channels fire. It must be
   announced in the LOOSER direction, not filed under "what remains uncaught", and pinned by
   an `..._stays_uncaught_by_design` test carrying the promotion protocol.
5. A fit call quoted in a TRAILING comment (`z = 1  # scaler.fit(data)`) is correctly silent
   on the parsed path and still fires on the fallback — every text guard in this module tests
   only for a LEADING `#`.
6. A split marker inside a single-line string constant assigned to a variable still counts as
   a split (Decision 5).

**On the FALLBACK path, everything the regex era missed comes back, plus the docstring false
positive.** The fallback is a per-physical-line text scan: it cannot see across a newline, it
does not resolve chained-call arguments, and it still blocks CRITICAL on prose. It is
signalled on four channels and deliberately not narrowed further in this wave. Backslash line
continuation is caught on the parsed path and NOT on the fallback — the joining helper was
deliberately never written.

**Notebooks reach the fallback more often than `.py` files do.** Line magics, cell magics and
shell escapes are repaired by blanking; NOT repaired, and named: `?`/`??` introspection
lines (`df.head?`), and a cell magic whose BODY is not Python (`%%bash`, `%%sql`, `%%R`,
`%%writefile`) — blanking the magic line leaves a non-Python body behind, so the notebook
still fails to parse. Do not describe notebooks as "largely repaired".

**Coordinate-space caveat.** For a `.ipynb`, `Line N` indexes the reconstructed cell
concatenation, not any file the user can open at that offset. This plan preserves that
numbering exactly rather than fixing it, and does not claim to fix it.
</uncaught_after_this_plan>
