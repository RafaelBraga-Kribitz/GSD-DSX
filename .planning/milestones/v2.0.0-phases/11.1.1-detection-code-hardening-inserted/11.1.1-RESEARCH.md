preprocessing step, verified below, not just the literal-check deletion the review
proposed.

**Primary recommendation:** Make three surgical edits to `dsx/checks/code.py` —
(1) delete the redundant literal re-check in `_first_fit_leak_line` and add a
logical-line join step for backslash continuation; (2) widen `FIT_CALL_RE` to
tolerate an optional `identifier=` prefix before the captured token; (3) switch
`_fit_call_arguments` from `.search()` to `.finditer()`. Ship (2) and (3) as one
plan/commit (roadmap's own ordering constraint — both live in the same function and
both widen the same check). Add regression tests for every whitespace/keyword/
semicolon variant plus a timing test for the new `FIT_CALL_RE`, all of which are
verified linear and correct in this research session.

### Pattern 1: Delete-the-redundant-check (CR-03 fix, DSX-CODE-001)

**What:** `_first_fit_leak_line` currently re-checks a hardcoded literal substring
(`"fit(" in line`) *after* the regex (`\.fit\s*\(`) has already matched, and the
literal check is stricter than the regex it gates — it silently defeats the
regex's own whitespace tolerance.
**When to use:** Whenever a function computes a match with a general pattern and
then re-validates it with an ad-hoc, narrower literal check "just to be sure" — the
second check is usually the actual bug, not a safety net.
**Verified current code (HEAD, `dsx/checks/code.py:519-534`):**
```python
def _first_fit_leak_line(lines: list[str]) -> int | None:
    for index, line in enumerate(lines):
        stripped = line.strip()
        if stripped.startswith("#"):
            continue
        if re.match(r"^(from|import)\b", stripped):
            continue
        if PIPELINE_FIT_TRAIN_RE.search(line):
            return index
        for pattern in FIT_LEAK_MARKERS:
            if re.search(pattern, line):
                if "fit(" in line or "fit_transform" in line or "partial_fit" in line:
                    return index
    return None
```
Note: the roadmap's success criteria (written before `06ff2d7`) cite this literal
check at line 505 — the correct current line is **532** (see Pitfall 1).
**Verified fix (probe run this session, `python -c` against the live module):**
```python
def _first_fit_leak_line(lines: list[str]) -> int | None:
    for index, line in enumerate(lines):
        stripped = line.strip()
        if stripped.startswith("#"):
            continue
        if re.match(r"^(from|import)\b", stripped):
            continue
        if PIPELINE_FIT_TRAIN_RE.search(line):
            return index
        for pattern in FIT_LEAK_MARKERS:
            if re.search(pattern, line):
                return index
    return None
```
Confirmed empirically (this session): with the redundant check removed,
`"model.fit (df)"`, `"model.fit  (df)"` and `"model.fit\t(df)"` (tab) all now match
at index 0. `.fit_transform (` and `.partial_fit (` were never affected (their
literal fallbacks don't require adjacency) — confirmed by inspection, unchanged
by this fix.

### Pattern 2: Optional keyword-prefix in the argument-token regex (CR-04 fix, DSX-CODE-021)

**What:** `FIT_CALL_RE` requires the first character after `(` to open the captured
identifier token directly — a keyword form (`X=data`) puts `X`, `=` there instead,
so the whole match attempt fails silently and `.search()` reports no match for that
call at all.
**When to use:** Any first-argument-extraction regex over Python call syntax should
explicitly decide whether it accepts keyword arguments — silently failing to match
is worse than an explicit "keyword calls are out of scope" comment, because a
silent failure here means a real leak passes the gate with an affirmative "OK" line
rather than a documented limitation.
**Verified current code (`dsx/checks/code.py:114-116`):**
```python
FIT_CALL_RE = re.compile(
    r"\.fit(?:_transform)?\s*\(\s*([A-Za-z_][\w.\[\]'\"]*)\s*[),]"
)
```
**Verified fix (probe run this session — functional correctness AND timing both
confirmed against the live pattern, see Pitfall 5):**
```python
FIT_CALL_RE = re.compile(
    r"\.fit(?:_transform)?\s*\(\s*(?:[A-Za-z_]\w*\s*=\s*)?([A-Za-z_][\w.\[\]'\"]*)\s*[),]"
)
```
Confirmed matches, this session, direct `re.search`:
`model.fit(X=data, y=target)` -> group(1) `'data'`;
`model.fit(data=data)` -> group(1) `'data'`;
`scaler.fit_transform(X=data[['Age']])` -> group(1) `"data[['Age']]"`;
unchanged on the three malformed-call negatives (`model.fit()`, `model.fit(`,
`model.fit(42)` -> all `None`, so `T-11.1-02`'s mitigation — "no exception on
malformed/truncated calls" — is preserved unmodified).

### Pattern 3: `finditer` instead of `search` for multi-match-per-line (WR-01 fix, DSX-CODE-021)

**What:** `_fit_call_arguments` calls `FIT_CALL_RE.search(line)` (first match only)
instead of `FIT_CALL_RE.finditer(line)` (every match), so a semicolon-joined line
with two fit calls only ever yields the first token.
**When to use:** Whenever a scanner's own test suite already constructs
semicolon-joined multi-statement lines as a deliberate corpus idiom (confirmed
true here — `test_call_on_same_line_as_split_marker_is_at_or_after` and several
`DSX-CODE-030`/`031` tests already do this), a `search`-based single-match
extractor is a latent bug waiting on that exact idiom recurring with a leaky
second call.
**Verified current code (`dsx/checks/code.py:554-575`):**
```python
def _fit_call_arguments(lines: list[str]) -> "list[tuple[int, str]]":
    results: "list[tuple[int, str]]" = []
    for index, line in enumerate(lines):
        stripped = line.strip()
        if stripped.startswith("#"):
            continue
        if re.match(r"^(from|import)\b", stripped):
            continue
        match = FIT_CALL_RE.search(line)
        if match is None:
            continue
        token = match.group(1)
        if not token:
            continue
        results.append((index, token))
    return results
```
Note: the roadmap cites the first-match-only `.search()` call at line 541 — the
correct current line is **568** (see Pitfall 1).
**Verified fix (probe run this session):**
```python
def _fit_call_arguments(lines: list[str]) -> "list[tuple[int, str]]":
    results: "list[tuple[int, str]]" = []
    for index, line in enumerate(lines):
        stripped = line.strip()
        if stripped.startswith("#"):
            continue
        if re.match(r"^(from|import)\b", stripped):
            continue
        for match in FIT_CALL_RE.finditer(line):
            token = match.group(1)
            if token:
                results.append((index, token))
    return results
```
Confirmed this session: `"imputer.fit(X_train); scaler.fit_transform(data)"` now
yields `[(0, 'X_train'), (0, 'data')]` (previously `[(0, 'X_train')]` only). The
caller in `check()` (`dsx/checks/code.py:252-257`) already takes the first
non-training-frame token `>= first_split` in list order — no caller change needed;
confirmed the caller loop is unaffected by reading it directly.

### Anti-Patterns to Avoid

- **Re-validating a regex match with a stricter ad-hoc literal check "as a safety
  net":** this is exactly what produced CR-03. If the literal check is stricter
  than the regex, it silently narrows the regex's own guarantee and nobody notices
  until an adversarial-shaped (or just idiomatic) input is missed. Delete rather
  than "harden" — the regex is already the source of truth.
- **Assuming "delete the redundant check" alone satisfies "every whitespace
  variant" in the roadmap's success criterion 1:** it satisfies the three
  single-physical-line variants (`.fit (`, `.fit  (`, tab) but not backslash line
  continuation, which spans two physical lines. See Pitfall 4 below — treat this
  as a fourth, distinct sub-fix, not a freebie from the CR-03 deletion.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Robustly extracting the first argument of a Python call across every syntactic form (multi-line, chained, `*args`, positional-after-keyword) | A progressively wider regex that tries to cover every remaining case one whitespace/keyword-shape at a time | `ast.parse` + `ast.walk` over the entrypoint text, as a scoped follow-up phase | Regex-over-lines has a hard ceiling: it cannot see across physical line boundaries without ad-hoc joining logic (Pitfall 4), and it cannot recognise a chained-call argument (`model.fit(loader.get_data())`) without effectively re-implementing a paren-balance parser inside the regex — which is exactly the shape of complexity that produced the two catastrophic-backtracking patterns (T-11.1-01) this file already had to fix once. This phase's own success criteria deliberately stop short of that ceiling (multi-line calls, chained calls and `partial_fit` are explicitly allowed to remain open per criterion 2's wording) — do not let scope creep past that line inside this phase. |

**Key insight:** every remaining gap this phase does *not* close (multi-line calls,
chained-call arguments, `partial_fit`) shares one root cause — a per-physical-line
regex cannot represent "the argument to this call, wherever its tokens land."
Closing all three cheaply is not possible with more regex; it needs the AST
rewrite this phase is explicitly scoped not to attempt. State this honestly in the
plan rather than adding one more regex patch per remaining variant, which is how a
file already bitten once by regex complexity accumulates a second latent ReDoS
surface.

### Pitfall 4: Deleting the CR-03 literal check does not, by itself, catch backslash line continuation

**What goes wrong:** A planner reads the review's proposed CR-03 fix (delete the
literal re-check) and assumes it satisfies success criterion 1's full list —
`.fit (`, `.fit  (`, tab, **and backslash line continuation**. It does not.
**Why it happens:** `_first_fit_leak_line` iterates `lines: list[str]`, one regex
`.search()` per *physical* line. A backslash-continued call —
```python
model.fit \
    (df)
```
— has `.fit` on one physical line and `(` on the next. `\.fit\s*\(` requires both
substrings on the *same* line string; `\s` inside a single split-line string never
contains a literal newline (Python's `str.splitlines()` already strips line
terminators before the regex ever runs), so this variant fails both before and
after the CR-03 literal-check deletion.
**Verified directly this session:** a simulated post-fix `_first_fit_leak_line`
(literal check removed) returned index `0` for `"model.fit (df)"`,
`"model.fit  (df)"` and `` "model.fit\t(df)" `` — but returned `None` for
`["model.fit \\", "    (df)"]` (the physical-line-split case).
**How to avoid:** Add a small logical-line join preprocessing step before the scan
loops run: when a stripped line ends in a lone (unescaped) `\`, concatenate it with
the following physical line (stripping the trailing backslash and the leading
whitespace of the continuation) before handing `lines` to `_first_fit_leak_line`
(and, for consistency, to `_first_full_frame_cleaning_line` and
`_fit_call_arguments` too, though only `DSX-CODE-001` is named in success
criterion 1). This is a pure string-join operation over already-terminator-free
lines (see Pitfall 5's CRLF note) — it introduces no new regex and no new
backtracking surface.
**Warning signs:** A test asserting `.fit (df)` fires but no test asserting a
literal backslash-continued `.fit \` / `(df)` two-line construction fires — that
gap is exactly this pitfall, silently passing review because the single-line
whitespace cases (the easy 3 of 4) look like "done."

### Pitfall 5: CRLF is a non-issue for the regex patterns themselves — verify it stays that way

**What goes wrong:** Given this repository checks out CRLF on Windows
(`.claude/CLAUDE.md`'s explicit warning), a planner might assume the existing or
new patterns need `\r?\n` handling.
**What we found:** They don't, and should not gain any. `_read_source` reads via
`path.read_text(encoding="utf-8")` (`.py`) or `json.loads` cell-source concatenation
(`.ipynb`), then `check()` calls `source.splitlines()` (`dsx/checks/code.py:205`).
Python's `str.splitlines()` treats `\r\n`, lone `\r`, and lone `\n` as equivalent
line terminators and strips them from every returned element — confirmed by
Python's own documented behaviour and consistent with every pattern in this file
already operating on terminator-free per-line strings (no pattern in the file
contains `\r`, `\n`, or `\\n` anywhere, confirmed by direct grep of the module).
**How to avoid:** Do not add `\r?\n` to any of this phase's new/edited patterns —
none of them ever sees a `\r` or `\n` character; `splitlines()` has already
removed it upstream. The one place this phase *does* need to reason about line
joining (Pitfall 4's backslash-continuation fix) is a pure Python string
concatenation of two already-terminator-free strings, not a regex — so it too
needs no `\r?\n` handling, and CRLF-normalizing it explicitly (e.g. joining with a
plain space, never re-inserting any terminator) keeps it that way.
**Warning signs:** Any new pattern in this file containing a literal `\n`, `\r`, or
`os.linesep` reference — that would indicate the code is (incorrectly) trying to
operate on multi-line joined text rather than the already-split `lines` list, and
should be reviewed for whether `splitlines()`'s CRLF-safety assumption still holds
for it.

### Pitfall 6: The widened `FIT_CALL_RE` must be re-timed, not assumed safe by analogy to Pattern 2's own test

**What goes wrong:** Because this file was already bitten once by a "linear by
inspection" claim that was false (T-11.1-01, CR-01/CR-02), any new or widened
pattern in this module needs its own timing test — analogy to a sibling pattern's
proven linearity is not sufficient evidence on its own, per the standing lesson
this phase is named to enforce.
**Verified directly this session** (not assumed): the CR-04 fix
`r"\.fit(?:_transform)?\s*\(\s*(?:[A-Za-z_]\w*\s*=\s*)?([A-Za-z_][\w.\[\]'\"]*)\s*[),]"`
measures linear on non-matching input — 2,000,000 characters of `a` in 0.08s
(compare the existing `test_fit_call_re_timing_no_catastrophic_backtracking`'s
budget: under 1.0s for 19,995 characters) — and on an adversarial repeating
`"x="` near-miss pattern (500,000 repeats, ~1,000,000 characters) in 0.0003s. The
`finditer`-based WR-01 fix was measured against 200,000 semicolon-joined fit calls
on one 2,000,000-character line in 0.078s, linear and correct (200,000 matches
extracted). Both additions have the shape the module's own comment block (lines
70-71) requires: "no leading `.*`, no overlapping character classes" — the added
`(?:[A-Za-z_]\w*\s*=\s*)?` group is a single bounded optional group with no nested
quantifier and no ambiguity with the group that follows it (the keyword-name
character class `\w*` and the token character class `[\w.\[\]'\"]*` cannot both
consume the same `=` character, so there is no backtracking ambiguity between
them).
**How to avoid:** Add a timing regression test for the widened `FIT_CALL_RE`
following exactly the shape of `test_fit_call_re_timing_no_catastrophic_backtracking`
(`tests/test_dsx.py:4735`) and `test_full_frame_cleaning_predicates_timing_no_catastrophic_backtracking`
(`tests/test_dsx.py:4746`) — a non-matching, non-subTest, hard-budget assertion
against a long input.

```python
def _join_backslash_continuations(lines: list[str]) -> list[str]:
    """Collapse a line ending in a lone backslash with the line that follows it,
    so a `.fit \\` / `(df)` split across two physical lines is scanned as one
    logical line. Pure string concatenation over already terminator-free
    strings (source: dsx/checks/code.py:205 splitlines()) — introduces no new
    regex and no new backtracking surface (Phase 11.1.1, roadmap SC 1)."""
    joined: list[str] = []
    pending = ""
    for line in lines:
        current = pending + line
        pending = ""
        if current.endswith("\\") and not current.endswith("\\\\"):
            pending = current[:-1].rstrip() + " "
            continue
        joined.append(current)
    if pending:
        joined.append(pending)
    return joined


def _first_fit_leak_line(lines: list[str]) -> int | None:
    for index, line in enumerate(lines):
        stripped = line.strip()
        if stripped.startswith("#"):
            continue
        if re.match(r"^(from|import)\b", stripped):
            continue
        if PIPELINE_FIT_TRAIN_RE.search(line):
            return index
        for pattern in FIT_LEAK_MARKERS:
            if re.search(pattern, line):
                return index
    return None
```
Note: the joined-lines list has fewer or equal entries than the original; if this
list is fed to `_first_fit_leak_line`, returned indices refer to the *joined*
list, not the original `lines` list, which the plan must account for in the
finding's reported line number (or apply the join only inside a local copy used
solely for the boolean fired/not-fired decision, keeping the original `index`
for user-facing line numbers — a plan-time design choice this research flags but
does not resolve).

### Widened `FIT_CALL_RE` (CR-04) plus `finditer` extraction (WR-01)

```python
FIT_CALL_RE = re.compile(
    r"\.fit(?:_transform)?\s*\(\s*(?:[A-Za-z_]\w*\s*=\s*)?([A-Za-z_][\w.\[\]'\"]*)\s*[),]"
)


def _fit_call_arguments(lines: list[str]) -> "list[tuple[int, str]]":
    results: "list[tuple[int, str]]" = []
    for index, line in enumerate(lines):
        stripped = line.strip()
        if stripped.startswith("#"):
            continue
        if re.match(r"^(from|import)\b", stripped):
            continue
        for match in FIT_CALL_RE.finditer(line):
            token = match.group(1)
            if token:
                results.append((index, token))
    return results
```

## Open Questions

1. **Where exactly should the backslash-continuation join happen, and does it
   shift reported line numbers?**
   - What we know: the join must happen before `_first_fit_leak_line` (and,
     for consistency, arguably before the other two per-line scanners) sees the
     `lines` list; verified that a naive join changes the list's length and
     index mapping relative to the original physical-line numbering used in
     every finding's `detail` text today (e.g. `f"Line {first_fit + 1}"`).
   - What's unclear: whether the plan should (a) join only for the boolean
     fired/not-fired decision and keep reporting the *original* physical line
     number of the `.fit` token, or (b) accept the joined line's number in the
     rare backslash-continuation case, since criterion 1 requires only that the
     finding fires, not a specific line-number contract for this one variant.
   - Recommendation: preserve the original physical line index for reporting
     (option a) — every other variant in this file already reports the exact
     line the fit-call token begins on, and changing that contract only for the
     backslash-continuation case would be an inconsistent user-facing surprise.
     This is a small bookkeeping detail for the implementing plan, not an
     open design question with more than one reasonable answer.

2. **Should the backslash-continuation join also apply to `_fit_call_arguments`
   and `_first_full_frame_cleaning_line`, or only to `_first_fit_leak_line`?**
   - What we know: success criterion 1 names only `DSX-CODE-001` (fit-before-
     split) for the whitespace/backslash-continuation fix. Success criterion 2
     (keyword arguments) is scoped to `DSX-CODE-021` and explicitly does not
     mention backslash continuation.
   - What's unclear: whether leaving `_fit_call_arguments` without the same
     join creates an inconsistency (a backslash-continued fit call *before* the
     split would now be caught by `DSX-CODE-001`, but the identical construction
     *after* the split would still be invisible to `DSX-CODE-021`).
   - Recommendation: scope the join helper to `_first_fit_leak_line` only, per
     the roadmap's literal wording of criterion 1 (bounded to the four stated
     criteria, and criterion 2 explicitly limits itself to the keyword-argument
     class). Note the resulting asymmetry explicitly in the plan's own comments
     so it reads as a scoped decision, not an oversight — matching this phase's
     own "known behaviour change... must be announced rather than slipped in"
     instruction.
